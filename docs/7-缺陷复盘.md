      而他往往不知道自己刚改坏了哪一行。错误文案是承诺不是装饰，

      与 `--clear`。
      **整个机制的重点是一条顺序不变量**：
      `默认值 + patch（不校验） → 叠加回滚覆盖层 → 校验`。
      反过来（先校验再叠加）意味着 patch 一坏 `resolveConfig` 就抛错，
      覆盖层永远没机会被应用 ⇒ 用户执行了回滚、命令报了成功、
      宿主下次启动**照样崩**。
      这条不变量在实现时真被踩了一次，探针 `.tmp/probe-f4-e2e.ts` 第 5 步抓到：
      第一版把「回滚基准」取成了校验失败后**退回的 `DEFAULT_CONFIG`**，
      于是 patch 里的 `-5` 被当成「当前值」、目标快照也是 0.18，
      **差异恒为空** ⇒ 回滚什么都不写 ⇒ patch 里的坏值原封不动。
      命令行报「已回滚」，宿主仍然抛 `absoluteThreshold … 实际为 -5`。
      正解是把基准定义为**「默认值 + patch、未校验、不含覆盖层」**——
      **「当前值」必须是「假如没有覆盖层，宿主会拿到什么」，
      不是「校验失败后我们退回的那个兜底值」**——后者是被降级过的，
      拿它当基准等于拿一个谎言去算差异。

- [x] 宿主实机验证 → **真缺陷十九：没有 `export const inject`，插件在真实宿主上一条都没激活**。
      这是本仓库唯一一条「假宿主测试永远绿、真实宿主必炸」的缺陷，也是「宿主实机验证」
      这一项存在的全部理由。

      **症状**（`dsh --profile memtest headless`）：

      ```text
      dsh: warning: 1 entry did not activate
      memory (dsh-memory): Error: cannot get property "systemPrompt" without inject
          at probeCapabilities (lib/host/adapter.js:91:41)
          at Object.apply [as callback] (lib/index.js:250:26)
      ```

      **根因**：真实 Cordis 的 `ctx` 是 Proxy，其 `get` 陷阱对任何**未在插件
      `inject` 里声明**的服务名**直接抛** `cannot get property "x" without inject`。
      而 `src/index.ts` 从未导出 `inject`，`src/host/adapter.ts` 里所有服务读取
      （`ctx.systemPrompt?.context`、`ctx.commands?.register`、`ctx.interval`、
      `ctx.goals`）都直接打在 Proxy 上。

      **`?.` 只能防 `undefined`，防不住抛错** —— 这是本条缺陷最值钱的一句话。
      代码里写着 `ctx.systemPrompt?.context`，读起来像是「没有就降级」，
      实际一读就炸。

      **为什么 1026 条测试全绿**：全部假宿主都是普通对象字面量，普通对象的
      `get` 永远不抛。**假宿主测试永远绿，因为普通对象不像 Proxy 那样抛错。**

      **为什么文档没救下它**：`docs/4-宿主接线API实证.md` §8.9（L2542）**早就写了**
      「建议：`inject` 只列 base 保证有的四个」，L1568 还给了真实先例
      `export const inject = ['commands', 'goals']`。这是教科书式的
      **「文档写了、代码没做」**，而且审计表（`docs/6`）把它标成了已覆盖。

      **五个探针才定下修法**（`.tmp/probe-cordis.mjs` / `probe-inject.mjs` /
      `probe-optional.mjs` / `probe-order.mjs` / `probe-members.mjs` /
      `probe-reflect.mjs`）：

      | 机制 | 防抛错 | 等就绪 | 缺服务时插件能否激活 |
      |---|---|---|---|
      | 硬 `inject` | ✅ | ✅ | ❌ 永不激活（违反 C8） |
      | `ctx.reflect.get(name, false)` | ✅ | ❌ | ✅ 但**静默永久降级** |
      | `ctx.inject([...], cb)` | ✅ | ✅（回调延后） | ✅ |
      | `ctx.on` / `ctx.effect` / `ctx.logger` | —— | —— | 核心方法，本来就不抛 |

      **被否决的两个方案，理由值得记住**：
      - **只用 `reflect.get`**：安全，但它在服务挂载前读到 `undefined` 并**就此定局**，
        没有任何重试。等于把「加载期崩溃」换成「静默永久降级」——
        **静默降级比加载期崩溃更坏**，因为崩溃会有人来修。
      - **只用硬 `inject`**：任何一项服务缺失 ⇒ `fiber.state 0`，`apply` 永不执行。
        而 `goals` 来自独立的 goal 插件，不在 base bundle 里，硬列它会让
        未装 goal 的 profile 整个失效 —— 直接违反 C8。

      **最终修法（两层）**：
      1. `src/index.ts` 加 `export const inject = ['systemPrompt', 'commands', 'timer']`
         —— 只列「缺了插件就没意义」且 base 保证有的三项。`timer` 是必须的，
         因为 `ctx.interval` 是它的 mixin 方法（服务名是 `timer`，调用点写 `interval`）。
      2. `src/host/adapter.ts` 新增 `readService`，三级回落：
         `reflect.get(name, false)` → 直接属性读 → 抛错时返回 `undefined`。
         **第二级不能省**：`on`/`effect`/`logger` 是 Context 核心方法而非服务，
         `reflect.get` 对它们恒返回 `undefined`，只靠第一级会把它们全判成缺失。

      **刻意不列的两项**：
      - `goals` —— 只影响 `goalScore` 一维，由 `readGoalText` 每轮**懒读**，
        服务晚到时下一轮自然取到，不存在静默降级；
      - `storageDomain` —— **生产代码零读取**（数据面走 `config.storage.dataDir`）。
        声明一个没有消费者的依赖，只会凭空拉高激活门槛：
        凡是没挂 storage-domain 的 profile，本插件都会无故失效。

      **四场景对照证明了 `inject` 的必要性**（`.tmp/verify-inject-value.mjs`）：

      | 场景 | `fiber.state` | 注册上下文 | 注册命令 |
      |---|---|---|---|
      | 有 inject + 服务早到 | 2 | 1 | 1 |
      | 有 inject + **服务晚到** | 2 | **1** | **1** |
      | 无 inject + 服务早到 | 2 | 1 | 1 |
      | 无 inject + **服务晚到** | 2 | **0** | **0** |

- [x] **缺陷二十：衰减被量化格永久卡死——机制在数学上停摆，而它不报错、不崩溃、日志正常**。

      症状：`decayEdges` 跑到边权 0.25 以下就再也不动了。不是变慢，是**冻结**。
      实测：`0.35` 起跑 35 夜就到 0（修好后），而修复前 **0.25 及以下的
      25 个权重值全部是不动点**。

      **根因是两套粒度的竞争**：`decayFactor = 0.98` 每夜把权重乘以 0.98，
      但权重还要被 `quantizeWeight` 圆到 0.01 的格子上。于是每夜的理论衰减量
      是 `0.02 × w`，而**圆整的半格是 0.005**：

      ```text
      w ≤ 0.25  ⇒  0.02 × w ≤ 0.005  ⇒  圆整后回到原值  ⇒  永久不动
      ```

      0.01 及以下的 25 个权重值全部成为**不动点**。这是一条纯粹的数学死锁：
      衰减因子与量化粒度不匹配时，机制在某个阈值以下完全失效。

      **为什么没人发现**：它不抛错、不写日志、`health` 报正常、测试全绿。
      表现是「边权稳定」——而边权稳定看起来**恰恰是期望行为**。
      **静默降级比加载期崩溃更坏**：崩溃至少会有人来修。

      **修法**（`src/core/graph.ts` + `src/core/spread.ts`）：
      引入 `EDGE_WEIGHT_STEP = 0.01`、`quantizeWeight`、`stepDownWeight`、
      `stepUpWeight`，并把衰减改成 `nextDecayedWeight`：

      ```ts
      export function nextDecayedWeight(weight: number, decayFactor: number): number {
        if (weight <= 0) return 0
        const scaled = quantizeWeight(weight * decayFactor)
        // 圆整没能推动权重时，强制走一格——衰减必须单调，不能停摆
        return scaled < weight ? scaled : stepDownWeight(weight)
      }
      ```

      判据是 **`scaled < weight`**：只要这一夜没能真的变小，就至少降一格。
      **衰减是单调的，所以「没变化」本身就是错误状态。**

      反向验证：把 `return scaled < weight ? scaled : stepDownWeight(weight)`
      变异成 `return scaled`，**fail=2**，且失败的正是
      「突触可塑性（FR-G1）」与新增的多夜连续衰减用例——精确命中，不红一片。

      踩坑两处：
      1. `Math.round(weight / EDGE_WEIGHT_STEP) * EDGE_WEIGHT_STEP` 得到
         `0.30000000000000004`。**浮点字面量算出来的期望值会把测试红在自己的错上。**
         改成 `Math.round(weight * 100) / 100`。
      2. 探测脚本 `import { nextDecayedWeight } from '../lib/core/graph.js'` 报
         `does not provide an export named`——它在 `spread.ts`。且 `lib/` 必须先
         `pnpm build` 才看得到新导出。

      测试：「衰减在任意权重上都不会停摆（缺陷二十：量化格比步长还粗）」
      （`tests/core/spread.test.ts`），遍历全部可表示权重 × 多个衰减因子，
      断言**每一步都严格变小**。断言 `<=` 等于没断言——这里必须是 `<`。

- [x] **缺陷二十一：边权不是持久状态，而是每夜重新推导的量——所以「衰减 + 剪枝」这对组合是错的**。

      **已确认，未修**。这条的价值在于**它否决了一个方向**，而不是它被修了。

      症状（结构性，不是数值）：`nightly.ts` 的连边步骤有一行过滤——

      ```ts
      const knownEdgeIds = new Set(replayed.edges.keys())
      const freshEdges = buildEdges(activeAfter, config, now)
        .filter((edge) => !knownEdgeIds.has(edge.id))
      ```

      它的意图是「只补尚不存在的边」（避免每夜重复写日志，ST-2 幂等）。
      但它与剪枝组合起来会形成**永动循环**：

      ```text
      夜 N：权重衰减到 0.10 → 剪枝删除该边
      夜 N+1：该边 id 已不在 edges 里 → filter 放行 → buildEdges 以**初始权重 0.30** 重建
      夜 N+2：又从 0.30 开始衰减……
      ```

      实测（`.tmp/probe-graph-death.mjs`，200 夜 / 20 条边）：**剪枝 91 次、
      重建 91 次**——每一次剪掉的边都被下一夜原样建了回来。平均权重在
      0.14~0.19 之间无规律游荡，**不是衰减，是复位。**

      **结构性结论**：只要 `buildEdges` 每夜都从卡片重新推导权重，边权就
      **不是状态**，而是**派生视图**。对派生视图做「衰减 + 剪枝」，等于对
      一个每次都被重置的东西做减法。

      决定性探针（`.tmp/probe-graph-death.mjs`，200 夜 / 20 条边 / 权重 0.15~0.35）：

      | 方案 | 结果 |
      |---|---|
      | 修舍入 + 剪枝重建 | 91 次剪枝 / 91 次重建，平均权重在 0.14~0.19 游荡 |
      | 修舍入 + 墓碑（不再重建） | **第 62 夜边集归零** |
      | 现状 | 0 次剪枝，停摆（即缺陷二十） |

      第二行是关键：**只接「衰减 + 剪枝」得到的是遗忘的假象，实际是单调消亡。**
      真正的遗忘必须有强化与之配对（用过的东西变强），否则每条边都只有死路。

      **而强化需要共激活信号**——`reinforceEdges` 至今**零生产调用方**，
      唯一可能的信号源 `confirmRecall` 也是**零调用方**。
      所以结论是：**可塑性必须「强化 + 衰减」成对接入，单独接任何一个都是错的；
      在共激活信号打通之前，可塑性保持未接线是对的。** 这条已写进
      `src/core/spread.ts` 头部与 `docs/3-架构设计.md` §B。

      **还撞到数据面的硬限制**：`JournalOp` 联合类型只有 8 个成员
      （`put`/`revise`/`touch`/`archive`/`restore`/`merge`/`edge`/`purge`），
      **没有删边的 op**。所以 `prunableEdges` 的结果**根本无法落盘**。
      要接剪枝必须先加一个 op（同步改 `KNOWN_OPS`），或给 `MemoryEdge` 加

- [x] **缺陷二十二：`same-topic` 边的作用域错了——用去重的阈值去连图谱的边，导致图谱恒空**。

      症状：真实使用中**图谱恒为空**。不是边少，是**零**。

      **根因**：`same-topic` 边读的是 `dedup.relatedSimilarity`（0.45）。这个
      数值是为**去重**标定的——它衡量「两张卡是不是在说同一件事」。而连边需要
      的是「两张卡有没有关系」，后者**弱得多**。

      实测（300 张真实中文卡，语料取自 `docs/*.md` 的长句，44850 对）：

      ```text
      相似度分位：99.9% = 0.2750   99% = 0.0870   95% = 0.0400   50% = 0.0000
      ```

      **0.45 落在分布的极尾——比 99.9 分位还高 0.175。** 门槛在数学上就已经
      把几乎所有对排除了。各门槛下的边数：

      | 门槛 | 边数 | 平均度数 |
      |---|---|---|
      | 0.45（原值） | 22 | 0.15 |
      | 0.20 | 86 | 0.57 |
      | 0.12 | 224 | 1.49 |
      | 0.08 | 563 | 3.75 |
      | 0.05 | 1513 | 10.09 |

      抽样读原文确认：0.45 只连出 2 条边，**两条都是前缀截断的近似重复**
      （不是语义关联）；而真正的跨层次关联出现在 0.08~0.20
      （例如「7. 记忆图谱：跨层次关联怎么落地」↔
      「起源第 4 条要求『建立记忆图谱，且能跨层次关联』」）。

      **修法：改成 k 近邻 + 绝对下限**，并拆出独立配置分区 `GraphPolicy`：

      ```ts
      export interface GraphPolicy {
        topicFloor: number      // 相似度下限，低于它一律不连
        topicNeighbors: number  // 每张卡最多连几条边
      }
      ```

      为什么是 k-NN 而不是「把绝对阈值调小」：

      1. **绝对阈值是 O(n²) 的函数**，边数随语料规模漂移——3000 卡 × 0.12
         门槛 ≈ 29000 条边，违反 P8「耗时可控」。k-NN 的边数上界是 `n × K`，
         **按构造封顶**。
      2. 同量级边数下的对照（280 卡）：

         | 方案 | 边数 | 精确率 | 孤立卡 |
         |---|---|---|---|
         | 绝对阈值 ≥ 0.12 | 290 | 50.7% | 143 |
         | **k-NN K=3 floor=0.08** | **320** | **57.5%** | **62** |

         精确率高 6.8 个点、孤立卡少 81 张。

      这与仓库在 `seedRatio` 上学到的结论同构：**绝对量卡不住分布，相对量才行。**
      但 k-NN 必须配 `topicFloor` 兜底——否则一张与全世界都无关的卡也会被
      强行连出 K 条假边，**假边会污染整张图，而孤立卡只是不参与扩散**。

      取值的来历（不是拍的）：`topicFloor = 0.08` 因为 0.05 对应平均度数 10.09
      ——那已经是全连接图，等于没有图；`topicNeighbors = 3` 因为 K=5 让孤立卡
      降到 11 张，但边数翻到 745、精确率反而从 57.5% 降到 55.7%，**多出来的
      是噪声**。

      **实现中途被测试抓到第二个错误**：第一版 k-NN 只限制**单向出度**
      （每张卡主动选 K 个邻居），但用户看到的度数是**入度 + 出度**。实测
      4 张卡 K=2 时卡 `a` 的度数到了 **3**——`topicNeighbors` 这个配置名
      承诺的是「每张卡最多连几条」，**配置项的名字就是承诺**。
      改成双向度数约束的贪心取边后才成立。

      反向验证 4/4 精确命中（`.tmp/reverse-knn.mjs`）：
      度数检查恒不触发、floor 判断恒真、floor 改读 `dedup.relatedSimilarity`、
      `duplicateSimilarity` 上界失效。
      其中一条变异是**等价变异**（把 `if (k > 0)` 改成 `if (true)`，fail=0）——
      k=0 时度数检查 `0 >= 0` 恒真，那个守卫是纯性能短路，**不是行为开关**。
      已删掉这条变异并在源码注释里写明，以免后来者重复尝试。

      **诚实边界**：k-NN 封住的是**边数**，不是**耗时**。候选对仍要两两算
      相似度，所以计算量是 O(n²)。实测 200/500/1000/2154 卡对应
      9/35/130/552 ms，边/卡 稳定在 0.83~1.12（证明边数与规模无关），
      但耗时随 n² 增长，万级约需 12 秒。真要压耗时得上倒排索引 + 前缀过滤，
      那是另一件事，**不在这里假装已经解决**。

      it('无引号纯中文专名仍然抽不出（已知能力边界，不是缺陷）', () => {

- [x] **缺陷二十四：一个参数承担两个方向相反的职责——调它修好一个，必然弄坏另一个**。

      `dedup.relatedSimilarity` 曾被**两处**读取，而两处要求的方向**相反**：

      | 位置 | 判据 | 阈值调低的后果 |
      |---|---|---|
      | `consolidate/graph.ts`（连边） | `相似度 >= 阈值` 才算同一话题 | 边**变多** |
      | `host/engine.ts`（冲突，FR-B5） | `相似度 < 阈值` 才算说法不同 | 冲突**变多** |

      **同一个旋钮动两个相反的机构，而两者都没有报错的机会。** 想让图谱连起来
      就得调低它，调低同时会让冲突判定变敏感——而这两个后果一个在夜整理里、
      一个在召回时，**没有任何日志会把它们联系起来**。

      修法是**拆参数，不是调值**：新增 `GraphPolicy.topicFloor`，连边只读它；
      `dedup.relatedSimilarity` 只保留冲突判定这一个用途（并在字段注释里写明
      「只有一个用途」，防止将来又被复用）。`configVersion` 10 → 11。

      顺带修正我自己的一个**错误预测**：我曾断言「调低 `relatedSimilarity`
      会让冲突泛滥」。实测相反——冲突数**随阈值降低而减少**：

      ```text
      阈值 0.45 / 0.30 / 0.20 / 0.15 / 0.10  ⇒  冲突 6 / 5 / 5 / 2 / 0
      ```

      原因很简单：`相似度 < 阈值` 是个**反向**判据，阈值越低条件越难满足。
      **我自己的预测也必须被探针检验。**

- [ ] **缺陷二十五：FR-B5 的冲突判据方向是反的——它筛出的是「不相关但同实体」，不是「矛盾」**。

      **已确认，未修**。这条是缺陷二十四的**下游真因**：拆参数解决了
      「一个旋钮两个机构」，但**冲突判定本身的判据仍然是错的**。

      现行判据（`src/core/extraction.ts` 的 `looksConflicting`）：

      ```ts
      // 共享实体 + 文本相似度低  ⇒  判定为冲突
      return shared && similarity < relatedThreshold
      ```

      决定性探针（`.tmp/probe-conflict-inversion.mjs`，6 张手写中文卡）：

      | 卡对 | 相似度 | 实际语义 | 判据输出 |
      |---|---|---|---|
      | 1 | 0.524 | **真冲突** | `false`（**漏判**） |
      | 2 | 0.300 | **真冲突** | `true` |
      | 3 | 0.150 | 无关 | `true`（**误判**） |
      | 4 | 0.176 | 无关 | `true`（**误判**） |
      | 5 | 0.188 | 无关 | `true`（**误判**） |

      **相似度最高的那对真冲突被漏掉了，而三对无关的被判成冲突。**
      方向是反的：真正的矛盾往往**用词高度重叠**（同一件事、同一个实体、
      同一个谓语，只是结论相反），而「不相关但共享实体」的对子恰恰相似度低。

      换句话说，`similarity < 阈值` 选出来的正是**「提到了同一个东西但说了
      不同的事」**——那是**无关**，不是**矛盾**。

      **为什么长期没被发现**：FR-B5 的验收只要求「冲突必须显式暴露」，
      没有要求「不误报」。而误报的表现是 `conflictOf` 字段被填上、召回时
      多出一句「与另一条记忆存在冲突」——**用户看到的是噪声，不是错误**。
      探针能抓到它，是因为这次真的把 6 组语义**人工标注**了。

      修法方向（未实现）：不能靠相似度这一个标量，需要**否定/反义标记**
      （「不要」「禁用」「改成」「而不是」等）与共享实体组合判定。
      这需要一份标记表——**又回到「写死参数」与「零依赖」的冲突**，
      与缺陷二十三第 5 项同源。所以这条与可塑性一样，**保持未接线比接错更好**。

      **不修的理由必须写清**：不是没时间，是**当前判据没有任何一个方向
      是对的**，调阈值只会在错的路上更精确。这与缺陷二十一（只接衰减不接
      强化）是同一类判断：**一个机制的两个半边都不到位时，接一半比不接更坏。**

- [x] **缺陷二十六：`absoluteThreshold` 既当闸门又当分数地板——「全低分时不硬塞」在数学上不可能失败**。

      **已修复**（`capConflictPenalty` 删除 + 新增 `relevance` 分量 + 闸门换尺子）。

      ### 两个耦合的缺陷，第一个把第二个藏了几个月

      **(26a) 冲突惩罚按绝对阈值封顶，于是那个阈值永远不生效。**

      `capConflictPenalty` 的公式是 `total = normalized − min(raw, headroom / w) × w`，
      其中 `headroom = normalized − absoluteThreshold`。只要 `raw ≥ headroom / w`，
      `total` 就被**精确钳在 `absoluteThreshold` 上**。

      实测（161 张真实卡，33 张带冲突）：

      | 观测 | 数值 |
      |---|---|
      | 总分恰好等于阈值的卡 | **10 / 161**，全部带冲突 |
      | 带冲突卡中被钳的比例 | 30.3% |
      | 封顶前的分差 | 0.031008 |
      | 封顶后的分差 | **0.000000** |
      | `semantic = 0.180` 与 `semantic = 0.000` 的卡 | 拿到**完全相同**的总分 |

      而那段代码的注释写的是「降权的语义完整保留」。实际发生的是
      **降权让区分度归零**。排序退化成按 `id`（内容哈希）——与相关性无关。

      **(26b) 总分本身不可分，所以任何阈值都没用。**

      `total` 里 0.48 的权重（importance 0.18 + recency 0.20 + confidence 0.10）
      **与查询无关**。于是一张完全无关但新鲜的卡也能拿 0.32 以上：

      | 样本 | 区间 |
      |---|---|
      | 无关卡（`semantic = 0`，n = 2331） | 0.313050 ~ 0.376728 |
      | 相关卡（`semantic > 0`，n = 84） | 0.345161 ~ 0.472320 |

      **重叠 33.3%，不可分。** 隔离探针（`relativeThreshold = 0`、`maxCards = 999`）
      显示绝对阈值只拒绝 **0 / 28**；全量扫描 173 张卡 × 15 个查询 = 2595 个样本，
      低于 0.18 的 **0 个**，而且**每个查询的最低分恰好是 0.180000**——
      那个精确到 1e-9 重复出现的数字，就是 (26a) 的钳位在留指纹。

      换一份异构语料复验（防止只是本语料的性质）：0.376728 vs 0.365951，重叠 27.8%。
      **结论与语料无关。**

      ### 为什么两个缺陷必须一起修

      只删掉封顶（修 26a）不够：`total` 依然不可分（26b），阈值照样恒真。
      只换判据（修 26b）也不够：封顶还在，阈值依然被当分数地板用。
      **26a 是「为什么没人发现 26b」的原因**——封顶让每张冲突卡恰好落在阈值上，
      于是「阈值有效」的假象被反复强化。

      ### 修法

      1. **删除 `capConflictPenalty`**。FR-B5「冲突不隐藏」改由**结构**保证：
         闸门看 `relevance`，而 `relevance` **完全不含冲突项**，
         所以冲突在数学上无法影响一张卡的去留，只影响它排第几。
         这比「算一个恰好不越界的上限」更可靠——后者依赖两个参数的具体数值。
      2. **新增 `ScoreBreakdown.relevance`**：`(semantic × w.semantic + goal × w.goal)
         / (w.semantic + w.goal)`。只含**与查询有关**的两个维度，无量纲。
      3. **绝对闸比对 `relevance`，相对闸比对 `total`**——两把尺子，别再合并。

      ### 为什么相对闸留在 total（这条是被实测逼出来的）

      我第一版把两道闸都挪到 `relevance`，理由是「统一尺子」。实测立刻误伤：

      ```
      SC-2 场景：目标卡 relevance 0.1113，相对闸 0.1121  →  差 0.0008 被挡出包
      同一张卡 total 0.3925，相对闸 0.2522              →  本该轻松通过
      ```

      根因是 `relevance` 的相对离散度比 `total` 大（同批候选 0.546 vs 0.856），
      同一个 `relativeThreshold` 在 relevance 尺度上苛刻得多。变体对照：

      | 变体 | 进包 | 噪声 | 无关组进包 | 空包 |
      |---|---|---|---|---|
      | A 旧（abs@total, rel@total） | 67 | 0 | **4** | 4 |
      | **B 最小改动（abs@rel, rel@total）** | **61** | **0** | **0** | 5 |
      | C 全挪（abs@rel, rel@rel 0.55） | 47 | 0 | 0 | 5 |

      C 比 B 多丢 16 张，其中包括「幂等键必须包含边权」从 7 张降到 1 张，
      以及 `semantic = 0.130` 的真相关卡。**⇒ 选 B。**

      **推论：两道闸不是「同一个判据写了两遍」，它们问的是不同的问题。**
      绝对闸问「有没有关系」（与查询有关），相对闸问「比本轮最好的差多少」
      （该含新鲜度/重要性）。把它们统一成一把尺子，等于强迫相对闸放弃自己的语义。

      ### 连带修的第三处：扩散护栏的尺子也错了

      `spreadActivation` 的护栏是 `selfScore >= absoluteThreshold × minSelfScoreRatio`，
      而 `selfScores` 里装的是 `total`。绝对阈值搬去 `relevance` 后，这行变成
      拿 0.06 去比一个取值 0.31~0.47 的数——**护栏恒真，等于没有**。

      值得注意的是：**同一个护栏坏过两次，两次都是单位/语义错。**
      第一次是 `capConflictPenalty` 把阈值当分数地板；第二次就是这次。
      所以这次除了改 `selfScores` 的来源，还在两处都写了「为什么尺子必须一致」。

      ### 顺带发现并否掉的两件事

      **(1) 扩散会不会因为闸门换尺子而失效？** 会。实测 12 张卡获得扩散加分，
      **0 张因此进焦点包**——因为扩散只改 `total`，闸门看 `relevance`。
      我一度加了「扩散可豁免相对闸」的补丁，但**相对闸回到 `total` 后这个补丁就不需要了**：
      扩散加分进 `total`，天然能改变成员。补丁删掉，少一个未测分支。

      **(2) 「允许扩散拉入池外邻居」的修法（缺陷二十七）被证伪**，见下一条。

      ### 有牙测试（每条都做了反向验证）

      | 测试 | 守什么 | 变异 | 结果 |
      |---|---|---|---|
      | `无关但新鲜的卡：total 拦不住它，relevance 必须拦住` | 缺陷二十六本体 | 闸门退回 `total` | 精确红 |
      | `applyThresholds 低于绝对阈值被丢弃` | 死卡必须被丢 | 同上 | 精确红 |
      | `applyThresholds 的死卡丢弃不是「全都丢」` | 配对阳性对照 | `applyThresholds` 恒返回 `[]` | 精确红 |
      | `冲突惩罚原样扣分，不按绝对阈值封顶` | 26a 本体 | 把钳位装回去 | 精确红 |
      | `无关查询不得硬塞焦点包`（端到端，三种模式） | 用户可见结果 | 闸门退回 `total` / 删掉绝对闸 | 精确红 |
      | `反向对照：问库里确实谈过的事，焦点包必须非空` | 不是无条件清空 | `applyThresholds` 恒返回 `[]` | 精确红 |

      `冲突惩罚原样扣分` 那条替换掉了原来的 `冲突惩罚封顶：扣分不会把卡从阈值上方
      打到下方`。**原测试的断言是 `A || B`，其中 B 恒真**——`total = normalized − penalty`
      且 `penalty ≥ 0`，所以 `normalized ≤ 阈值` 时 `total` 必然也 ≤ 阈值。
      **两个分支恒真，它在任何实现下都绿。** 它守的是一个已被判定为缺陷的行为，
      而且守的方式是同义反复。

      新测试钉住两件事：① 惩罚原样扣（从 `total` 反推的归一化分必须逐位吻合）；
      ② **把 `absoluteThreshold` 改成 0.01 / 0.06 / 0.18 / 0.5，同一张卡的 `total`
      必须完全不变**——这是「它不再是分数地板」的直接证明。

      `recall.absoluteThreshold`：`0.18` → `0.06`，**`MEMORY_CONFIG_VERSION` 11 → 12**。

      语义变更比新增字段更需要递增版本：旧快照里写着 `absoluteThreshold: 0.18`

      | 阈值 | 无关组进包 | 真相关卡损失 | 空包查询 |
      |---|---|---|---|
      | **0.06** | **0** | **0** | 5 |
      | 0.10 | 0 | 0 | 7 |
      | 0.15 | 0 | **3** | 7 |

      取 0.06 = 既能挡住全部噪声，又不在边界上误伤。

- [ ] **缺陷二十七：候选池闸门会挡住扩散——但「放开它」的修法被证伪，因为池外邻居按构造必然无关**。

      **已证伪，不实现。** 这一条记下来是因为**我自己的判断错了，而且拿到了用户批准**。

      ### 当初的判断

      `spreadActivation` 里有一行候选池闸门：

      ```ts
      const selfScore = selfScores.get(id)
      if (selfScore === undefined || selfScore < selfFloor) continue
      ```

      而 `selfScores` 只含候选池（倒排命中的卡）。所以**池外邻居永远拿不到扩散加分**。
      我据此判断：「与强命中相邻但自己没命中查询词」的记忆本该被想起，却被这道闸挡住了。
      探针 `.tmp/probe-pool-gate.mjs` 显示「有邻居被挡住」，用户批准了「允许拉入池外邻居，
      但必须自身过绝对阈值」。

      ### 证伪

      `.tmp/probe-structural-zero.mjs`（78 张卡 / 45 条边 / 15 个查询）直接测「池外邻居的
      `semantic` 是多少」：

      ```
      池外 semantic = 0 的：33（100.0%）
      池外 semantic > 0 的：0
      ```

      **100%，不是「多数」。** 原因不是语料，是结构：

      > 池外 ⟺ 倒排没命中 ⟺ 与查询**零词项交集** ⟺ `semantic === 0`

      倒排索引就是按词项建的，所以「池外」与「零词项交集」是同一个条件。
      而 `relevance` 只由 `semantic` + `goal` 合成，两者都来自词项。
      ⇒ **池外邻居的 `relevance` 恒为 0，任何阈值都只会给它排序，不会让它进包。**

      反事实重排也做了：放开池外后 +10 张全部 `semantic = 0.000`，
      而 −2 张 `semantic = 0.090`——**净变差**。
      另外 `distills` 边在真实语料上是 **0 条**（90 张卡 / 61 条边），
      所以「感受卡被事件卡唤起」这条唯一可能合法的用例，当前也不存在。

      ### 教训

      1. **「被挡住的邻居」不等于「被丢掉的召回」**，必须做反事实重排才能算损失。
      2. **结构性的零不能用调参解决**：若某类输入按构造必然取零，
         任何阈值、权重、倍数都只是在给零排序。
      3. **拿到批准不等于判断正确。** 用户批准的是「这个修法合理」，不是
         「这个缺陷存在」。证伪之后正确的动作是**不实现并说明**，而不是
         「既然批了就做」。

      剩下的诚实动作是把边界写进代码注释（已做，见 `mergeSpread` 里
      「结构性的零」那段），而不是加一个只会增加未测分支的开关。

- [x] **投影层曾静默改写事实**：`coerceCard` 的 kind 白名单把未知值降级成
  `fact`，导致日志写 A、重放得 B，破坏 ST-1 且事后无从发现。现改为「已知保留 /
  未知字符串透传 / 缺失才兜底」，见 `docs/3-架构设计.md` §4.2。
- [x] **CLI `query` 曾污染访问计数**：走 `engine.recall()` 会写 `touch` 日志，
  运维查一眼等于「使用」。现直接走 `engine.peek`（只读入口）。
  更早还有一份手写的 `readOnlyRecall`，与 `engine.peek` 并存——已删除，因为
  它返回的是**截断后**的候选数而 `peek` 返回完整候选池，同一个库在终端与
  会话里会报出两个不同的数字；且它的 `timeZone` 参数是死参数。**少一份
  实现就少一处漂移点**，手写实现已经开始腐烂了。
  配套有**配对**的对照测试：`peek`/`recall` 前后日志字节数不变（只读），
  `confirmRecall` 后必须变大（证明写库确实会发生，防止只读测试假绿）。
  两条都做过**反向验证**：把断言改坏后确实变红。
- [x] **人读渲染曾有两份实现**：`/memory explain` 与 CLI `query` 各写一遍，
  靠人肉同步。现收敛到 `src/core/render.ts` 的 `renderFocusPackExplain`。
- [x] **`confirmRecall` 已实现但零调用方**：`src/` 下无人调用它，实际行为是
  「只衰减、不强化」——`accessCount` 恒不涨，`importanceScore` 的访问频次项
  恒为 0。这是**有意的暂缓**而非遗漏：确认信号必须来自「这条记忆真的影响了
  输出」的可审计证据，而非「被展示过」。已否决的两个接法：让模型自报
  （它无法区分「看到」与「被影响」）、宿主文本匹配（判据无法稳定定义，误判
  会让错误的正反馈重新出现且事后无从审计）。**接入前不要以为正反馈已生效。**
- [x] **宿主漏传 `goalText` 曾让召回看起来更好**：`goalTokens` 为空时若把
  `w.goal` 从归一化分母摘掉，每张卡分数涨约 11%、更容易进焦点包——**缺陷
  伪装成改进，没人会去修它**。现改为分母恒含全部维度权重，缺目标时 goal 项
  贡献 0。理由比结论重要：看到「分母恒含 w.goal」会觉得多算一项，只有看到
  这个后果才不敢改。
- [x] **靠运气绿的测试**：原 `applyThresholds` 用例的分数余量只有 0.012，
  归一化分母一动就翻红——绿的时候说明不了任何事，红的时候也分不清是回归
  还是噪声。现改为构造真正死透的卡（各分项全 0），结果由规则决定；并加
  前提断言防止将来又变假绿。**让测试由规则决定而不是由巧合决定。**
- [ ] **`state.ts` 的时间来源不一致**：`revise`/`archive`/`restore` 用
  `record.at`，`touch` 用 `op.at`。生产路径 `store.append(op, undefined, now)`
  给两者同一个值所以看不出问题，但测试里只给 `op.at` 会测出非真实行为。
  暂不改（会动数据面语义），但写重放测试时必须从 `op.at` 推导 `record.at`。
- [x] **蒸馏排在去重之后，导致感受一条都产不出来**：感受的依据是「反复经历」，
  而夜整理的去重会把高度相似的卡合并成一张——三张「上线又出问题」去重后只剩
  一张，`distillMinRecurrence = 2` 永远达不到。端到端测试直接暴露
  `distilled = 0`。**顺序不是风格，是约束**：蒸馏必须在去重之前。
  这条只在端到端测出来，单测全绿（单测不经过夜整理的去重阶段）。
- [x] **摘要卡被自己的去重逻辑吃掉**：摘要文本是模板化统计句
  （`2023-11-15：7 条记忆，主要涉及工作，关键词 …`），任意两天的日摘要字面
  相似度极高，参与去重会被判重复合并——「每天一张日摘要」在去重后只剩一张，
  层级压缩被毁。实测两天的日摘要确实进了同一分组。现 `findDuplicateGroups`
  排除 `kind === 'summary'`；不能靠调高阈值绕开，那会同时放过真重复事件卡。
- [x] **压缩比测试曾绿在巧合上**：日摘要渲染出来只有 30 字，远小于任何预算，
  于是即便把 `charBudgetOf` 改成「恒等于层级上限」（彻底不做比例压缩），
  「压缩比 < summaryTargetRatio」那条断言**依然绿**。反向验证时只有
  `charBudgetOf` 单测变红，压缩比断言一条没红。现补了直接断言预算函数的
  规则级用例（来源翻倍预算翻倍、触上限截平、ratio 真的被乘进去）。
  **教训：反向验证不只是确认「会红」，它还能反过来暴露哪条测试是装饰。**
- [x] **感受文本曾替实现撒谎**：模板写「反复牵动情绪」以回避极性判断，
  但末尾拼了来源原文当例子，原文里的「特别开心」被读者当成了系统的情绪
  判断——模板说不表态，引用却替它表了态。现删除原文引用，只报主题与次数。
  有一条测试**故意断言这个局限存在**（极性相反、强度相同的两件事会被蒸馏成
  同一条感受），将来若引入极性它会变红，提醒同步更新文档。
- [x] **两个连续的 `/** */` 文档块会让第一块静默失效**：TypeScript 只把**紧邻
  声明**的那一块当文档注释，前一块既不属于任何声明、也不会报错，`tsc` 生成的
  `.d.ts` 里它还**原样保留**——所以「文件里能搜到」不等于「工具链会呈现它」。

  实测方式（`getQuickInfoAtPosition` 比读文件可靠）：

  ```js
  const ls = ts.createLanguageService(host, ts.createDocumentRegistry())
  ls.getQuickInfoAtPosition(file, src.indexOf('SpreadMode = '))
  // 只返回第二段；第一段的 FR-G1 归属说明、起源 L15 双锚定全部不可见
  ```

  危害与 `coerceKind` 同源：**文档写了但没人看得到，等于没写**，而且没有任何
  机制会提醒你。IDE 悬浮提示、`hover`、文档生成器全都只认最后一块。

  自查命令（数每个声明的前置文档块个数，**且两块之间没有空行**才算孤儿）：

  ```js
  const ranges = ts.getLeadingCommentRanges(src, node.getFullStart()) ?? []
  const docs = ranges.filter(r => r.kind === ts.SyntaxKind.MultiLineCommentTrivia
                                && src.startsWith('/**', r.pos))
  for (let i = 0; i + 1 < docs.length; i++) {
    const gap = src.slice(docs[i].end, docs[i + 1].pos)
    // 隔了空行 = 模块注释 + 声明注释，合法；紧邻才是孤儿
    if (!/\n[ \t]*\r?\n/.test(gap)) console.log('孤儿文档块', node.name?.text)
  }
  ```

  **判据必须区分「紧邻」和「隔空行」**：`/** @module ... */` 后面空一行再写
  声明的文档注释，是完全合法的写法（`src/core/text.ts` 与 `src/core/types.ts`
  开头都是这样）。若只数「前置文档块 > 1」就报警，这两个文件会被误报——
  我第一次跑自查就是这么误报的，差点去改两个本来正确的文件。
  **误报会让人去修不存在的问题，比漏报更浪费。**

  预防：写完一段新注释后，**往上看一行**——若紧邻的是 `*/`（中间没有空行），
  先合并或调整位置再走。这个错误在 diff 里极不显眼（两个块都是 `/**` 开头，
  绿字一片），但在 IDE 里是整段消失。

## 缺陷二十八：情绪通道被四道串联闸全部挡掉，情绪越强越写不进记忆

### 现象：起源里唯一带三个感叹号的那句话，在代码里没有任何入口

起源 L3（无编号·激素）原文：

> 激素是关键！！！大脑皮层只是记忆，激素控制情绪！！！

起源 L11（无编号·细节会忘）：

> 大多数细节都会忘记，只会留下感受。

这两条是同一个机制的两半：**激素决定什么被留下，感受是留下的那部分**。
它们指向同一个功能需求——情绪必须影响「什么能进记忆」。

实测这个入口**不存在**。

### 探针：10 句真实感情绪表达，通过率 1/10

```text
.tmp/probe-gate-emotional.mjs
（assistantText 留空，模拟用户单方面倾诉）

❌拒 emo=0.36 sig=[]  今天真的很开心
❌拒 emo=0.36 sig=[]  我有点难受
❌拒 emo=0.80 sig=[]  太难了，快崩溃了
❌拒 emo=0.18 sig=[]  这个结果让我很失望
❌拒 emo=0.18 sig=[]  心里有点慌
❌拒 emo=1.00 sig=[]  我今天特别开心，这个项目终于跑通了，感觉超级爽！！！
❌拒 emo=0.18 sig=[]  好累啊，不想动了
❌拒 emo=0.36 sig=[]  有点烦
❌拒 emo=0.18 sig=[]  松了一口气，总算搞定了
✅过 emo=0.36 sig=["明天"]  我很担心明天的面试

情绪句通过率 = 1/10
```

唯一通过的那条命中的是**「明天」（到期词）**，与情绪毫无关系。

更关键的是方向反了：

```text
高情绪组（emo>=0.28）通过率 = 17% (1/6)
低情绪组（emo<0.28）通过率 = 43% (3/7)
```

**情绪越强，越留不下来。** 这不是「参数没调好」，是判据的通道集合里
根本没有情绪这一项。

### 根因：四道串联闸，各自都「合理」

抽取链路上有四个独立的过滤点，每一个都有自己的正当理由，
但它们**全部**以「长度 / 信号词 / 实体」为判据，而情绪表达在这三项上恰恰是弱项：

| 闸 | 位置 | 判据 | 情绪句为什么过不去 |
|---|---|---|---|
| ① 门控 | `gateTurn` | 信号词 ∨ 到期词 ∨ 助手信号 ∨ 双方都长 | 四条通道无一是情绪；情绪句短，且不含决策词 |
| ② 逐句过滤 | `consume` | 有信号 ∨ 有实体 ∨ 长度 ≥ 40 | 「我快崩溃了」6 字、无实体、无信号词 |
| ③ 长度闸 | `consume` | `chars >= minTextChars`(6) | 「有点烦」3 字、「心里有点慌」6 字 |
| ④ 显著性 | `computeSalience` | 长度×0.42 + 信号×0.36 + 实体×0.22 | 短情绪句三项全低：`0.15×0.42 = 0.063 < 0.25` |

**只修任何一道，最终出卡仍然是 0。** 这是串联判据的典型形态：
四道闸串联时，`pass = 闸1 ∧ 闸2 ∧ 闸3 ∧ 闸4`，
任意一项恒假，整条路径恒假，而**每一个闸单独看都说得通**。

> 这正是 AGENTS.md 里那条教训的另一个形态：
> **「两个门槛相等 ⇒ 机制恒为空」**。这里是「四个门槛互不覆盖 ⇒ 机制恒为空」，
> 表现完全一样：不报错、不崩溃、日志正常、测试全绿。

### 修法：四条通道各加一条情绪理由，且不改变原有分数

| 闸 | 修法 |
|---|---|
| ① 门控 | 新增第五条通道 `emotional >= emotionalGateThreshold`（0.28） |
| ② 逐句过滤 | 情绪达标时豁免「无信号 + 无实体 + <40 字」 |
| ③ 长度闸 | 情绪达标时豁免 `minTextChars` |
| ④ 显著性 | 改成 `max(信息项, 情绪项)`，**不是加权相加** |

第 ④ 项为什么必须是 `max` 而不是加权：四项权重之和必须为 1，
加权就得从原有三项里各砍一刀。实测那样会让真正的决策句显著性下降 18%——
**为了修一个通道而弄坏另一个**。取 `max` 则原有分数一分不动，
情绪只负责把「本来进不来的」抬进来。

同时把两张情绪词表挪进配置：原实现只有 18 个词，「失望 / 慌 / 焦虑 / 委屈 /
疲惫 / 孤独 / 感激」全都不在表内。**词表漏词和判据方向错是同一类问题——
它不报错，只是安静地少记东西。**

### 效果

```text
修复前                          修复后
情绪句门控通过   1/10     →     8/10
情绪句最终出卡   0/10     →     8/10
高情绪组出卡率   17%      →     100%
低情绪组出卡率   43%      →     20%
反相关           存在     →     消除
决策句出卡       1/3      →     1/3（未受影响）
```

### 顺带修掉的一个噪声源：`splitSentences` 把 `！！！` 拆成孤立 `"！"`

原实现用零宽后视切分，「感觉超级爽！！！」被切成三句：
`"…超级爽！"` + `"！"` + `"！"`。那两个孤立的 `"！"` 各自拿到 0.12 的情绪分，
还会**稀释按句平均的情绪强度**——情绪越激烈，平均分反而越低。

旧测试 `splitSentences 过滤空白句` 断言 `splitSentences('  。  ') === ['。']`，
**把「纯标点也算一句」写成了契约**。这条测试保护的是缺陷本身，按规范改测试。

修法：逐字符累积，连续标点归入前一句；纯标点片段附加到前一句
（「真的吗？！」里的 `！` 属于前一句的语气，丢了会让情绪强度偏低，
独立成句则产生噪声句，两种都错）。

### 反向验证

```text
.tmp/reverse-28.mjs（纯函数层）
  ✅ M1 门控去掉情绪通道          — 红 11 条
  ✅ M2 consume 去掉情绪放行      — 红 9 条
  ✅ M3 长度闸不再豁免情绪        — 红 6 条
  ✅ M4 显著性回到纯信息项        — 红 10 条
  ✅ M5 情绪词表退化成只剩标点    — 红 10 条
  5/5 被抓住

.tmp/reverse-28-e2e.mjs（链路层）
  ✅ E1 门控恒假                  — 红 150 条
  ✅ E2 显著性恒低                — 红 148 条
  ✅ E3 长度闸取消豁免            — 红 6 条
  3/3 被抓住

.tmp/reverse-split.mjs
  ✅ 纯标点不附加到前一句          — 红 2 条
```

**E3 第一次没被抓住，暴露了我自己的一个无牙断言。**
端到端测试最初写的是 `cards.length >= 3`，而 4 轮实际产出正好 4 张——
拆掉长度闸豁免后只少 1 张（4→3），断言照样绿。
**上界远大于实际值时，它守的是巧合不是规则。**
改成逐轮断言（`perTurn.get(turn) > 0`）后立刻变红。

### 两条推论

1. **一个能力在文档里被列为「已实现」，但它的驱动信号在真实数据上恒为空集，
   那它和没实现没有区别，而后者至少不会骗人。**
   `computeEmotional` 一直存在、一直被测、一直有消费者（打分、遗忘半衰期、蒸馏），
   但它的输入在真实数据上几乎恒为 0（25 张卡均值 0.0216）——
   因为产出情绪值的那条路径，情绪句根本走不进来。

2. **门控的通道集合决定了什么能进入记忆。少一条通道，最该留的那类东西
   就会恰好被最先丢掉，而且它不报错。**
   这不是「阈值调高了」，是「这个维度不在判据里」。调任何数值都救不了它。

## 缺陷二十九：主题词按空格切整句，蒸馏桶数恒为 0

### 现象：5 张情绪全部达标，`distilled` 仍是 0

修好缺陷二十八之后，情绪卡终于能写进来了。实测：

```text
卡数 = 5，全部 emotional >= distillMinEmotional(0.28)
distillMinRecurrence = 2
桶数 = 0
distillFeelings 产出 = 0
distilled = 0
```

### 根因：`normalizeText` 把标点全换成空格，于是「按空格切」得到的是整句

```ts
// themeTerms 的回退分支
for (const token of card.normalized.split(' ')) { ... }
```

`normalizeText` 会把**所有标点与符号替换成空格**。于是：

```text
"我今天特别开心，这个项目终于跑通了，感觉超级爽"
→ "我今天特别开心 这个项目终于跑通了 感觉超级爽"
→ split(' ') = ["我今天特别开心", "这个项目终于跑通了", "感觉超级爽"]
```

切出来的是三个**整段长句**，不是词项。两张不同的情绪卡之间
几乎不可能共享一个整段长句，于是 `bucketByTheme` 的桶数**恒为 0**。

这和缺陷二十八是**两个独立缺陷**，但观测结果完全一样（`distilled = 0`）：

| 缺陷 | 机制 | 观测 |
|---|---|---|
| 二十八 | 情绪句写不进来 ⇒ 没有原料 | `distilled = 0` |
| 二十九 | 主题词粒度错 ⇒ 桶数恒为 0 | `distilled = 0` |
| 三十 | 判据用 `kind` 标签 ⇒ 原料被排除 | `distilled = 0` |

**三个零长得一模一样。** 所以「修好一处就以为蒸馏会动」是错的。

### 修法：`tokenize(card.normalized)` 而不是 `split(' ')`

`tokenize` 对中文产二元组、对英文产整词、过滤停用词，正是「主题词项」的粒度。

**注意入参必须是 `card.normalized` 而不是 `card.text`**：`tokenize` 的约定是
「已归一化的文本」（它按空格切段，并假定段内没有标点）。传原文会让标点留在
段里，二元组跨标点边界生成——实测产出 `"，这"`、`"了，"` 这种主题，
感受卡写成「『，这』这件事反复牵动我的情绪」。

那不只是难看：**主题词是判据，一个假主题会让两张本来无关的卡聚成桶。**

## 缺陷三十：判据用 `kind` 标签而不是数据层事实，修好上游之后下游又空了

### 现象：`hasFeelingSignal` 把原话情绪卡一起排除了

```ts
// 原实现
if (card.kind === 'feeling') return false
```

注释写的是「感受卡本身不参与再蒸馏，否则会形成感受生感受的自激循环」。
**注释承诺的是「感受卡本身」，实现判的却是 `kind` 标签。**

这两句话在旧数据上恰好等价——因为当时原话几乎不会被判成 `feeling`
（情绪通道被四道闸挡住，见缺陷二十八）。修好情绪通道之后：

```text
5 张卡情绪全部 >= 0.28
  → 4 张 kind === 'feeling' 被排除，剩 1 张
  → 1 < distillMinRecurrence(2) → 直接 return []
```

### 修法：用数据层可见的事实判断

派生感受卡的 `source.sessionId` 固定为 `'distill'`（见 `distillSource`），
`eventType` 为 `'consolidate/feeling'`。判据改成
`isDistilledCard(card)`，读的是**数据**，不是会被分类器改动的标签。

同时把 `'distill'` 和 `'consolidate/feeling'` 提成导出常量
`DISTILL_SESSION_ID` / `DISTILL_EVENT_TYPE`，让写入方与读取方共用同一个真相源——
**两处各写一份字面量就是两个真相源**，改一处忘一处会让判据静默失效。

### 修好的效果

```text
distilled = 2
  [感受] 「有点」这件事反复牵动我的情绪，前后经历了 2 次，每次感受都明显
  [感受] 「报错」这件事反复牵动我的情绪，前后经历了 2 次，每次感受都明显
```

（「有点」是停用词漏项，属于词表质量问题，不是机制缺陷。）

### 反向验证

```text
.tmp/reverse-29-30.mjs
  ✅ D1 themeTerms 退回按空格切整句    — 红 4 条
  ✅ D2 themeTerms 传原文而非归一化    — 红 2 条
  ✅ D3 判据退回 kind 标签             — 红 5 条
  3/3 被抓住
```

### 三条推论

1. **「能进来」和「能沉淀」是两件事。** 修好写入路径不等于下游会有产出，
   中间还隔着粒度、判据、顺序。三个缺陷的观测值一模一样，只能靠**逐层探针**
   区分，不能靠「重跑一次看看」。

2. **注释承诺的行为必须有一条测试真的去验它。**
   `if (card.kind === 'feeling')` 配着「感受卡本身」的注释，读注释会以为
   已经修好了，所以没人去看实现。这比没有注释更危险——
   本仓库在幂等键那里已经踩过同一个坑（注释说防三件事，实现只防一件半）。

3. **判据要读数据层的事实，不要读标签。** `kind` 是分类器的输出，
   会被上游改动影响；`source.sessionId` 是写入时确定的事实。
   用标签当判据，等于把两个模块耦合在一起，而上游一改下游就静默失效。

## 缺陷三十一：程度副词碎片成了主题词，感受卡在说假话

### 现象：感受卡写着「『有点』这件事反复牵动我的情绪」

修好前三个缺陷后，蒸馏终于产出非零。但产出的文本是：

```text
distilled = 2
  [感受] 「有点」这件事反复牵动我的情绪，前后经历了 2 次，每次感受都明显
  [感受] 「报错」这件事反复牵动我的情绪，前后经历了 2 次，每次感受都明显
```

第二条是对的。第一条在说假话——**「有点烦」和「有点慌」不是同一件事**，
它们只共享一个程度副词。

### 根因：二元组分词没有词典，程度副词会作为独立词项漏出来

`tokenize` 对中文产二元组，靠 `STOP_WORDS` 过滤噪声。原表收了「的 / 了 / 是 /
很 / 这个 / 那个」这类虚词，但**没有收「有点 / 有些 / 非常 / 特别 / 感觉 /
觉得」这类程度副词与感知动词**。

它们有两个共同特点：

1. **区分度为零**——几乎每句情绪表达都能带一个；
2. **恰好高频出现在情绪句里**——「有点烦」「有点慌」「感觉很累」「特别开心」。

于是它们成了最容易被聚成桶的「主题」，而桶的内容是假的。

### 为什么这不是「难看」而是「判据错误」

主题词不是展示用的标签，**它是聚桶的判据**：

```text
两张卡共享「有点」 → 聚成同一个桶 → 桶内张数 >= distillMinRecurrence
→ 判定「这件事反复牵动情绪」 → 产出感受卡
```

一旦判据选错，后面整条链路都在为一个假前提服务，而**每一步都执行成功**：
不报错、不崩溃、`distilled` 正常非零、感受卡格式完全正确。
唯一能发现它的是**读一遍产出的文本**。

### 修法：加进 `STOP_WORDS`，不在 `themeTerms` 里另加一层过滤

第一反应会是在 `themeTerms` 里再过滤一遍。**那是错的**，理由是同一个：

> 停用词表已经是「什么不算词项」的唯一真相源。另开一份就是两个真相源，
> 将来加词必然漏掉一处。

而且检索侧同样不该把「有点」当查询词——修在 `STOP_WORDS` 一处，两处同时受益。

### 效果

```text
修复前                              修复后
distilled = 2                       distilled = 1
  「有点」…（假主题）        →        （消失）
  「报错」…（真主题）                 「报错」…（保留）
```

注意 `distilled` **从 2 降到 1**。这不是退化，是去掉了一条假的。
**「产出变多」和「产出变对」是两件事**，只看数量会把这条修复当成回归。

### 反向验证

```text
.tmp/reverse-31.mjs
  ✅ S1 停用词表去掉程度副词 — 红 2 条
  1/1 被抓住
```

测试里配了反向对照 `配对对照：真实主题词仍然能被聚出来（不是把分桶关掉了）`——
只测「副词不聚桶」是半个测试，**把分桶整个关掉也能让它绿**。

### 一条推论

**修好一个「产出恒为零」的缺陷之后，必须读一遍产出的内容。**
「非零」只证明链路通了，不证明链路对了。这个仓库里已经有过同源教训：
感受文本曾替实现撒谎（模板不表态、引用却替它表态）——
**产出的文本本身是一个需要被测试断言的输出**，不能只断言它非空。

## 缺陷三十二：种子判据与加分护栏各用一把尺子，扩散在数学上恒为空

**症状**：`spread.mode` 设为 `off` / `shadow` / `on` 三种，召回的总分**逐位相同**，
影子观察值 0 条。也就是说：这个功能配了、算力花了、日志也写了，但**什么都没发生**。

**探针证据**（`.tmp/probe-spread-visible.mjs`，7 条同域语料 + 夜整理）：

```text
=== off ===     0.498 回滚就是 git revert…  （7 张卡，按 total 降序）
=== shadow ===  0.498 回滚就是 git revert…  （影子观察值 0 条）
=== on ===      0.498 回滚就是 git revert…  （逐位相同）
成员差异 off vs on： 无差异（扩散没改变成员）
排序差异 off vs on： 无差异
```

**根因**：两道闸用了两把尺子。

| 闸 | 判据 | 尺子 |
|---|---|---|
| 种子筛选 | `score.total >= maxTotal × seedRatio` | **`total`** |
| 加分护栏 | `selfScore >= absoluteThreshold × minSelfScoreRatio` | **`relevance`** |

`total` 里有 **0.48 的权重**（importance 0.18 + recency 0.20 + confidence 0.10）
与查询无关，它给每张卡垫了一层共同地板，把相对离散度压平了。实测：

| 语料 | `total` 最小/最大 | `relevance` 最小/最大 |
|---|---|---|
| 同质（全在讲部署） | **0.9059** | 0.7237 |
| 异质（部署 + 别的主题） | **0.9655** | 0.8158 |

`seedRatio = 0.85` 落在 `total` 的离散区间（0.91~0.97）**之下**，于是
「所有卡都是种子」，受益者集合恒为空——**而种子不因扩散加分**，所以 boost 恒为空集。

```text
total     判据：种子 7/7，受益者 0   ← 恒空
relevance 判据：种子 3/7，受益者 4   ← 生效
```

**为什么上一轮没发现**：缺陷二十六把**加分护栏**从 `total` 挪到了 `relevance`，
并在注释里写下了「护栏与被护栏的量必须在同一把尺子上」。但那句话只复查了
**护栏那一半**——种子筛选这一半仍然拿 `total` 算相对门槛。

**同一个教训，第二次犯**：

> 阈值换尺子之后，所有拿它做乘数的护栏都要逐个复查，而它们的失效方式一律是恒真。

这次漏掉的是「拿它当**分子**去算相对门槛」的那一处。它比护栏更隐蔽，因为
护栏失效是「多放行」，而种子失效是「全放行」——**全放行看起来更像正常工作**。

**修法**：种子判据也换成 `relevance`，`maxScore` 同步取 `relevance` 的最大值
（否则门槛与判据又不同尺）。

```ts
const maxScore = scored.reduce((m, item) => (item.score.relevance > m ? item.score.relevance : m), 0)
const seedFloor = maxScore * config.spread.seedRatio
const seeds = scored
  .filter((item) => item.score.relevance >= seedFloor)
  // 种子的**能量**仍用 total：那是「这张卡有多强」的完整度量。
  // 判据用 relevance（够不够格当种子），能量用 total（能撒多少）——
  // 两个用途不同，用不同的量是刻意的，不是又一处尺子错配。
  .map((item) => ({ id: item.card.id, score: item.score.total }))
```

**修复后**（同一份语料）：

```text
=== off ===     0.498 回滚就是 git revert…
=== shadow ===  0.498 回滚就是 git revert…  （影子观察值 2 条）
=== on ===      0.502 记得部署后看一遍 access.log…   ← 排序真的变了
```

人读渲染里终于能说出「因为想起了谁」：

```text
扩散加分 +0.120 × 权重 1.000 = +0.120，因为想起了：方案是用 Redis 做缓存，结论已定 / 约定 Redis 和 PostgreSQL 的…
```

**这才是「类似神经的突触效果」的可感知形态**：不是「分数莫名高了一点」，
而是**能说出「因为想起 A，所以想起 B」**。

### 反向验证逼出的第二个问题：第一版 fixture 是靠巧合绿的

修完代码后我加了 4 条测试，反向验证时把种子判据改回 `total`——**测试全绿**。

原因是第一版 fixture 用「新/旧混合 + 多词项查询」，那份语料里 `total` 恰好
也有足够离散度，两把尺子给出相同的种子集合。**它绿在巧合上，不在规则上。**

改成「全部卡同一时刻写入」之后，`recency` / `importance` / `confidence`
三个维度几乎相同，`total` 被压平到 `[0.4508, 0.4981]`，`seedRatio = 0.85`
的门槛 `0.4234` **落在值域之下** ⇒ `total` 判据下受益者恒为 0。
两把尺子的差别成了**结构性的**，不再依赖数值巧合。

反向验证结果：**3/3 被抓住**，其中 R1 精确红 4 条且名字全部对上。

> **教训**：一条测试能不能抓住它声称要抓的缺陷，必须在**反向验证**里证明，
> 不能靠「我写了断言」推断。**「测试绿」和「测试守住了东西」是两件事。**
> 而 fixture 的判别力是**构造出来的**，不是碰巧有的。

### 这条缺陷与缺陷二十六的关系

两者是同一个错误的**两半**，但表现完全不同：

| | 缺陷二十六 | 缺陷三十二 |
|---|---|---|
| 哪一半错 | 加分护栏用 `total` | 种子判据用 `total` |
| 失效方式 | 护栏**恒真**（多放行无关卡） | 种子**全命中**（受益者恒空） |
| 观测 | 无关卡也能拿到扩散加分 | 扩散完全不动，三种模式逐位相同 |
| 谁发现的 | 反事实重排探针 | 三模式逐位对比探针 |

**同一个参数（`absoluteThreshold` / `seedRatio` 的相对标定）有多个用途时，
只看一个会得出相反结论。** 修好一半不等于修好，而剩下那一半的失效方式
恰好是「什么都不发生」——它不会报错，也不会让任何断言变红。

## 缺陷三十三：可塑性开关是空操作，而它的注释承诺了一个不存在的能力

### 症状

`spread.plasticityEnabled` 打开与关闭，跑 10 夜整理后**边权逐位相同**。

```text
false 模式第 1 夜  = 0.110000,0.120000,0.500000,0.500000,1.000000
false 模式第 10 夜 = 0.110000,0.120000,0.500000,0.500000,1.000000
true  模式第 1 夜  = 0.110000,0.120000,0.500000,0.500000,1.000000
true  模式第 10 夜 = 0.110000,0.120000,0.500000,0.500000,1.000000
两种模式结果是否相同：完全相同（配置项是空操作）
```

`.tmp/probe-weight-static.mjs` 更进一步：连跑 8 夜，每夜打印边权快照，
**8 次完全相同**。真实运行中边权从建立那一刻起就不再变化。

### 根因：三处「有」，一处「没人读」

| 层 | 状态 | 实际情况 |
|---|---|---|
| 实现 | `reinforceEdges` / `decayEdges` / `prunableEdges` | 全部实现，逻辑正确 |
| 测试 | `tests/core/spread.test.ts` | **55 条全绿**，覆盖强化/衰减/剪枝 |
| 配置 | `spread.plasticityEnabled` 等 5 个字段 | 齐备，有默认值 |
| 校验 | `validateConfig` 里一整块子参数校验 | 齐备，能精确报错 |
| **生产调用** | `grep` 全 `src/` | **零调用方** |

三个纯函数各自的第一行都是 `if (!sp.plasticityEnabled) return []`，
而**除它们自己之外，没有任何代码读过这个字段**。

这是缺陷十七（`minCards` / `reindexEveryRecords` 零读取）的原样重演。
但这次更隐蔽，因为它多了一层「看起来接上了」的假象：

- 字段有注释（而且注释写得很具体）
- 校验里有一整块 `if (sp.plasticityEnabled) { ... }` 子参数检查
- 55 条单元测试全绿

**「代码里有」+「测试里有」+「配置里有」+「校验里有」≠「生产路径会走到」。**

### 注释是怎么替实现撒谎的

字段注释原文：

```ts
/**
 * 是否启用边权可塑性。
 *
 * 关掉时边权停在建立时的初始值，只有扩散生效。
 */
plasticityEnabled: boolean
```

「关掉时边权停在建立时的初始值」——这句话在**两个状态下都成立**。
它读起来像「打开时边权会变化」，但那件事从未发生。
**一个字段的注释和它唯一可能的语义互相矛盾，说明它从来没人真正想过要它干什么。**

### 修法选择：不接线，而是让「打开」响亮失败

四个候选的共激活信号全部被否决：

| 候选信号 | 为什么不行 |
|---|---|
| 被一起召回 | 召回是「看见」不是「使用」，会让焦点包自我固化，违反起源 L29（第 5 条·专注当前位置） |
| 夜整理同批 | 同批只是「同一天」，日摘要一晚处理几百张卡，一次拉满 |
| 上轮焦点包重叠 | recall 变成有状态的，「看见」间接影响「看见」，违反 L29 |
| **扩散传播过这条边** | 正反馈闭环：边权大 ⇒ 传得多 ⇒ 边权更大；且种子来自打分，等于让「排得前」加固「为什么排得前」 |

唯一合法入口 `Engine.confirmRecall` **零调用方**，且它被有意暂缓
（确认信号必须来自「这条记忆真的影响了输出」的可审计证据）。

所以修法不是接线，而是**让空操作变成加载期失败**：

```ts
if (sp.plasticityEnabled) {
  errors.push(
    'spread.plasticityEnabled 必须为 false：可塑性（边权随共激活变化）尚未接线，'
    + '打开它不会产生任何效果。已实现的只有扩散激活（spread.mode）。'
    + '接线前提是确认信号有可审计来源，见 docs/3-架构设计.md §7.2',
  )
}
```

**静默接受一个打开了也没用的开关，比拒绝它更坏**——它让人以为突触学习
已经生效，从而永远不去查它从未生效。

### 顺带修掉：一整块不可达的校验

原来四个可塑性参数（`reinforceDelta` / `maxEdgeWeight` / `decayFactor` /
`pruneThreshold` / `maxPrunePerRun`）的校验包在 `if (sp.plasticityEnabled)` 里，
注释写的是「关着的时候配错值不该拦住整个配置」。

那个理由本身没错。但开关一旦**必须**为 false，整块校验就变成了**不可达代码**——
`validateConfig` 永远不会检查这些值。**「校验写了」和「校验会执行」成了两件事**，
而它们看起来完全一样。

改为无条件校验。实测：

```text
plasticityEnabled=false, decayFactor=1.5（非法）→ 修复前：通过
plasticityEnabled=false, decayFactor=1.5（非法）→ 修复后：拒绝
```

### 第二层：即使接线，默认参数也分不出使用频率

这是探针在追「要不要接线」时**意外发现**的，比第一层更根本。

衰减是乘性的（每夜 `× 0.98`，−2%），强化是加性的（每次 `+0.05`，相当于 +5%，
这是修复前的默认值）。
每天 n 次共激活、每夜一次衰减，日末权重的不动点是：

```text
w* = n × delta × factor / (1 − factor)
```

代入修复前的默认值 `delta = 0.05, factor = 0.98`：

```text
w* = n × 0.05 × 0.98 / 0.02 = n × 2.45
```

**n = 1 就已经是 2.45，远超上限 1.0。** 实测（`.tmp/probe-calibration.mjs`）：

```text
每 1 夜 1 次 → 0.9800   每 5 夜 1 次 → 0.5000
每 2 夜 1 次 → 0.9800   每 10 夜 1 次 → 0.0400
每 3 夜 1 次 → 0.7400   从不 → 0.0000
```

参数空间扫描（`.tmp/probe-grid.mjs`）：

| delta | factor | n=1 | n=2 | n=5 | n=10 | 能分出的档数 |
|---|---|---|---|---|---|---|
| **0.05** | **0.98**（当前默认） | 0.98 | 0.98 | 0.98 | 0.98 | **1** |
| 0.02 | 0.98 | 0.74 | 0.98 | 0.98 | 0.98 | 2 |
| 0.01 | 0.98 | 0.50 | 0.74 | 0.98 | 0.98 | 3 |
| 0.01 | 0.95 | 0.28 | 0.48 | 0.86 | 0.95 | 4 |
| 0.01 | 0.90 | 0.14 | 0.23 | 0.50 | 0.86 | 4 |

**当前默认值恰好是全场最坏的一组：只能分出 1 档。**

这条发现改变了修法的性质：问题不只是「信号没有合法来源」，而是
**即使给了合法来源，默认参数也会把它变成「全部拉满」**。
一个携带不了「用得多还是少」的边权，接上去只是把图谱变成「全部等强」——
**它比不接线更糟，因为看起来在工作**。

### 为什么不是「把参数调一调」就完事：加性模型有分辨率上限

我一开始以为这只是「默认值选得不好」，调一调就行。**这个判断是错的**，
而且是被自己的探针推翻的。

要让 `n = 1..N` 全部不撞顶，需要 `N × delta × factor / (1 − factor) ≤ 1`，即

```text
delta ≤ (1 − factor) / (N × factor)
```

同时 `delta ≥ EDGE_WEIGHT_STEP = 0.01`（低于半格会被圆整掉，缺陷二十）。
两个约束求交：

| N | factor=0.90 | factor=0.95 | factor=0.98 |
|---|---|---|---|
| 3 | 可行 | 可行 | **无解** |
| 5 | 可行 | 可行 | **无解** |
| 10 | 可行 | **无解** | **无解** |
| 20 | **无解** | **无解** | **无解** |

`factor = 0.98` 时要覆盖 `n = 1..10`，需 `delta ≤ 0.00204`，**低于量化格 0.01**。

**结论：在「加性强化 + 0.01 量化格 + 每天若干次共激活」这个组合下，
无论 `delta` 取什么值，机制都分不出使用频率。** 这是模型分辨率的问题，
不是标定问题。

我原本在文档里写的是「标定需要真实数据，现在没有，所以只记录不调参」——
**那句话是错的**。它把一条可以解析推导的结构性约束，说成了一条需要等待数据的
经验问题。两者的区别很重要：前者说明「这个模型走不通」，后者只说明
「我还不知道该填什么数」。**把结构性问题误判成标定问题，会让下一个人
以为接上信号就能用。**

（一个可能的出路：把加性换成**饱和式** `w ← w + delta × (cap − w)`，
每次只补剩余空间的一部分。它的均衡上限是 `factor` 而不是 `1`，再常用也留余量。
离线实测默认参数下能分出 3 档、`factor = 0.90` 时 5 档。但它改变了边权语义，
且同样受量化格限制，属于接线时与信号一起裁决的设计决定。）

所以这一层只记录、不调参。调参属于接线时的工作，而接线的前置条件
（可审计的确认信号）还没满足——**现在又多了第二个前置条件：换强化模型。**

### 测试与反向验证

新增 4 条（`tests/core/config.test.ts`）：

1. `plasticityEnabled=true` 必须让校验失败，且报错指向该字段
2. 报错必须说清「没有效果」而不是只说「非法」（否则用户会去调参数）
3. 默认配置必须能通过校验（不能把出厂配置判成非法）
4. 可塑性参数**无条件**校验，不再挂在开关下面（5 个字段逐一破坏）

反向验证 3 个变异，**3/3 捕获**：

| 变异 | 结果 |
|---|---|
| R1 删掉「打开即报错」那条校验 | 红 3 条 |
| R2 可塑性参数重新挂回开关下面 | 红 2 条 |
| R3 报错文案退化成纯取值范围错误 | 红 2 条 |

R3 第一次写成了**无效变异**：只替换首行字符串，而「尚未接线」还在后面一句里，
断言依然通过、全绿。改成整条 `errors.push(...)` 一起替换后才真正变红。
**这本身就是一次「变异未命中看起来和验证通过一样」的复现。**

### 这一条教了什么

1. **「代码里有」+「测试里有」+「配置里有」+「校验里有」≠「生产路径会走到」。**
   判定一个能力是否存在，唯一的判据是 `grep` 生产代码的调用方。
2. **一个开关打开和关闭产生完全相同的结果，那它就不是开关，是注释。**
   更坏的是，这条「注释」还带 55 条测试和一块校验为它作证。
3. **注释的前半句承诺能力、后半句取消它，等于把缺陷写成了事实。**
4. **校验块挂在「永远不会为 true」的条件下面，就是不可达代码。**
   「校验写了」和「校验会执行」是两件事，而它们看起来完全一样。
5. **修「空操作」有两条路：接上去，或者让它报错。** 当接线的前置条件不具备时，
   报错是唯一诚实的选择——**静默空转比失败更坏**。
6. **追一个问题时挖出的第二层，可能推翻第一层的修法。**
   本轮如果直接接线，就会得到一个「全部拉满」的图谱，而且它看起来在工作。
7. **「需要真实数据才能定」是一句很容易说出口、也很容易错的挡箭牌。**
   本轮我先写下这句话，随后探针给出了解析判据：`delta` 的合法区间与 `N` 直接
   相关，而 `factor=0.98` 时区间为空。**结构性的无解和「参数没选好」是两件事**，
   把它们混为一谈会让下一个人白跑一趟。

## 附：可塑性的第五个候选共激活信号，为什么也不行

这一条不是缺陷，是**一次否决的裁决记录**。记在这里是因为它推翻了一个很容易
成立的直觉：**「数据拿得到、密度健康、代码干净」仍然可能在语义上是错的。**

### 候选内容

「同一轮对话里被抽取出来的多张卡」构成共激活。理由听起来很对：一次用户发言 +
助手回复构成「一次思考」，从这一轮抽出的卡（`maxCardsPerTurn = 4`）是同一次
思考里同时浮现的概念。赫布学习（Hebbian learning）的原话就是「一起激发的
神经元连在一起」。

### 它看起来为什么完全干净

喂给 `writeTurn` 的是 `readTurnText()` 的**对话原文**，不是 `renderFocusPack()`
的输出。所以「这轮说了 A 和 B」≠「这轮注入了 A 和 B」，**这个区分在代码里是真的**。
接线只需要一行：

```ts
const ids = new Set(summary.cards.map((c) => c.id))
const next = reinforceEdges(store.allEdges(), ids, config)
```

变量名是 `cards`，来源是 `writeTurn` 的返回值，文本是对话原文。
**这一行里没有任何「召回」的痕迹。**

### 但实测：命中的已连边对 100% 依赖助手通道

3 天 36 轮真实中文语料（52 卡 / 61 边），按来源拆解口径 B（真正会被
`reinforceEdges` 改动的已连边对）：

| 口径 | 合计 | 用户×用户 | 用户×助手 | 助手×助手 |
|---|---|---|---|---|
| A 本轮任意两卡 | 22 对（7.33/夜） | **0** | 20 | 2 |
| B 本轮且有边 | 5 对（1.67/夜） | **0** | **5** | 0 |

**助手侧参与占比 = 100.0%。**

决定性反事实：把 `includeAssistant` 设为 `false` 重跑同一份语料，口径 B 从
5 对**精确归零**。也就是说这个信号**在结构上完全依赖助手通道**。

而助手通道的输入文本是被焦点包条件化过的：

1. `CONTEXT_ORDER = 300` 的动态上下文在助手生成**之前**注入（`src/index.ts`），
   查询文本是本轮用户原话；
2. `config.extraction.includeAssistant = true` 让助手回复进抽取；
3. 于是「同轮配对」把**召回结果和召回结果自己**配成一对。

**它和已否决的「上轮焦点包与本轮重叠」是同一个东西，只是多洗了一层。**
那个是「把上次注入的包拿来比」，一眼可见；这个是「注入 → 模型自己说出来 →
再抽回来」，数据面上只剩两段看起来无关的原文。

### 它是复合的，不是一次性的

焦点包渲染每行带 `- [事实] ` 前缀，被复述后抽取成卡就带上前缀，下一轮再被
召回、复述、抽取，前缀层层叠加。实测：

- 出卡事件 46 → 90，夜整理后边数 **61 → 172**
- 最大嵌套深度 **5**，且**逐轮增长**（1→2→3→4→5）
- 41 条边（23.8%）挂在嵌套卡上，**全部是 `supersedes@1.00`**

最后一条最要命：**污染伪造出了最高权重的取代关系**，而它在数据层完全自洽——
权重满格、关系合法、日志正常。只有读文本才会发现那是一条深度 5 的前缀垃圾。

### 它唯一的优点必须如实记下：密度是健康的

| 口径 | 每夜 | 说明 |
|---|---|---|
| A 本轮任意两卡 | 7.33 对/夜 | 候选面 |
| B 本轮且有边 | **1.67 对/夜** | 实际效果面 |
| C 本轮且共享实体 | 0.67 对/夜 | 窄化面 |

对照已否决的「夜整理同批」：**61 条边/夜、覆盖 100% 的边**。倍数差 **36.6 倍**。
3 夜里被触及的不同边只有 5/61 = **8.2%**；跨轮重复出现的卡 = 0
（`buildCardId` 含 `source.turn`，轮内边界成立）。

**所以密度不是问题，问题全在合法性。** 这一点必须写清楚，否则后来者会以为
它是因为「信号太密」被否决的，而那个理由是错的。

### 两个窄化变体都不成立

| 变体 | L29 上是否干净 | 真实语料密度 | 结论 |
|---|---|---|---|
| 两侧都是用户侧 | **干净**（用户原话产生于注入之前） | **0.00 对/夜** | 接上去就是缺陷三十三的形态 |
| 只取 `distills` 边 | — | **结构上恒为空** | 死路 |

`distills` 那条不必测：`distillSource` 把感受卡的 `source.turn` 写死为 `0`、
`sessionId` 写死为 `'distill'`，而来源卡是真实轮次，两者**永远不可能同轮**
（实测 6 条 `distills` 边，两端 `source.turn` 相同且非 0 的 **0 / 6**）。

### 额外发现：它是「同一份证据数了两遍」

5 对命中里 2 对两端共享实体，而 `same-entity` 边权的定义本身就是
「共享实体数 / 实体并集」——强化它等于把同一个量再乘一遍。

而且同轮对边权均值 **0.192**，反而**低于**同天跨轮对的 **0.410**
（秩相关 rho = −0.058）。**它挑出的不是「更该强的边」，是「碰巧在同一轮
被说到的边」。**

### 这一条教了什么

1. **「数据拿得到」不等于「信号合法」。** 前四个候选的否决理由都是「拿不到」
   或「一眼可见的正反馈」，容易被记成「等有数据了再说」。这一个必须记成
   **「有数据也不能用，因为它测的不是使用，是复述」**。
2. **隐蔽性来自「违反点隔了两跳」。** 一跳是配置 `includeAssistant = true`，
   一跳是动态上下文的注入顺序。**两跳各自都完全合理，单独看都是正确设计，
   只有连起来才是闭环——而没有任何一个文件同时写着这两件事。**
3. **最坏的失败是「数据层完全自洽」。** `supersedes@1.00` 权重满格、关系合法、
   日志正常，看起来是「学习生效了」。**只有读文本才能发现它在说假话**——
   这与缺陷三十一（感受卡在说假话）是同一种失败形态。
4. **诚实边界：助手侧对焦点包的依赖是模拟的。** 探针把 `engine.peek()` 的输出
   直接拼进助手回复，这是**最坏情况**。真实模型会改写而非逐字引用，嵌套深度
   的增长会显著减弱。另外「动态上下文先于生成注入」依据的是宿主契约，
   **未在真实宿主上观测时序**——若时序相反，这条闭环不成立，但那样一来
   `spread.mode: 'on'` 的全部价值也不成立了。
