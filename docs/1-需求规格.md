## 1. 背景

通用 agent 的问题：

1. **每次会话从零开始**：跨会话只认得文件，不记得"我们聊过什么"。
2. **现有记忆方案是查表，不是记忆**：RAG（检索增强生成，Retrieval-Augmented Generation）、记忆插件、MCP（模型上下文协议，Model Context Protocol）记忆服务，本质都是"模型主动检索 → 候选塞上下文"，没有时间感、没有遗忘、没有一致性保证。
3. **记忆"长不稳"**：用久了会膨胀、会重复、会冲突、会污染上下文，最后不可信。

本阶段先把**稳定记忆**做扎实——它不炫，但它是后面一切（人格、分身、主动性）的地基。地基不稳，上层做多漂亮都是幻觉。

## 2. 目标与非目标

### 2.1 本阶段目标：稳定记忆

"稳定"定义为四个维度，每个维度都要可测：

| 维度 | 含义 | 可测指标 |
|---|---|---|
| 数据稳定 | 不丢、不坏、可重建、可迁移 | 崩溃后完整率 100%；导出重建成功率 100% |
| 内容稳定 | 同一事实多次召回一致；不编造；冲突显式；修正可追溯 | 同状态同查询 10 次结果一致；来源可追溯率 100% |
| 行为稳定 | 检索可解释、参数可调、可回滚；不会越用越膨胀 | 连续 50 轮动态层 token 波动 ≤ ±10% |
| 成本稳定 | token 与存储有明确上界 | 每轮记忆注入 ≤ 预算；库增长有上限 |

功能主线只有四条：**写得进、存得住、取得回、忘得掉**。

### 2.2 长期方向（不在本阶段验收）

- 人格连续性（单一主体的长期叙事）。
- 双人格、分身、交流卡、汇报卡、分叉——**暂缓，不进本阶段路线图**。
- 机械飞升等长期叙事——不进需求。

这些不是被否定，是"等稳定记忆跑通以后再谈"。

### 2.3 非目标（本阶段明确不做）

- 不做双人格/分身/多人格协作。
- 不改模型权重、不做微调（服务商 API 约束）。
- 不做通用记忆 SaaS、不做多用户。
- 不做多模态（语音、视频、语气）。
- 不做参数化记忆（把记忆写进权重/隐状态）。
- 不做"让模型自己管理记忆"——写入与召回由系统驱动。
- 不做复杂状态机与情绪系统（降为后续）。
- 不靠长上下文硬扛（百万上下文不是方案）。

## 3. 设计原则

| 编号 | 原则 | 含义 |
|---|---|---|
| P1 | 记忆系统是操作系统，不是提示词技巧 | 写入、去重、衰减、打分由确定性代码完成；LLM 只负责摘要抽取与表达 |
| P2 | 事件日志是唯一真相源 | 记忆卡是派生视图，任何时候都能从日志重建 |
| P3 | 写入幂等、读取可解释 | 重复处理不产生重复记忆；每条召回能说出为什么 |
| P4 | 记忆是带置信的线索，不是事实 | 每条记忆带来源、置信度、时效、冲突标记 |
| P5 | 遗忘是功能 | 不追求记住一切，追求"记得对、忘得合理、找得回" |
| P6 | 门控先于检索 | 系统在模型开口前预取，模型不发起检索 |
| P7 | 参数可版本化、可回滚 | 阈值/权重/策略带版本，改动可追溯 |
| P8 | 成本有上界 | 记忆注入、库大小、整理耗时都有硬上限 |

## 4. 使用场景

| 编号 | 场景 | 通过标准 |
|---|---|---|
| S1 | 跨会话回忆 | 次日新会话问"我们昨天聊了什么"，要点正确、不编造 |
| S2 | 工作任务记忆 | C++ 项目的任务、决策、踩坑能按需召回 |
| S3 | 长期使用稳定 | 连续用两周，召回质量不下降、上下文不膨胀 |
| S4 | 夜间整理 | 日终自动去重、合并、降权、归档，产出一份变更日志 |
| S5 | 到期提醒 | 重要事项到点主动提醒 |

## 6. 宿主与平台约束

| 编号 | 约束 | 影响 |
|---|---|---|
| C1 | 宿主为 DSH（DeepSeek Harness）预览版，插件为 TypeScript/ESM/Cordis 形态 | 主干语言 TS |
| C2 | 模型是服务商 API，无权重访问 | 只能做上下文级可塑性 |
| C3 | 存储走宿主 storage domain，后端 node:sqlite / JSON | 不引入原生数据库扩展 |
| C4 | 注入主通道是 `systemPrompt.context()`（每轮求值、尾部追加、压缩后自愈） | 记忆卡不重写系统提示词头部 |
| C5 | 不得写自定义 session 事件类型 | 记忆状态只存 storage domain |
| C6 | 压缩没有"压缩前"阻塞钩子 | 平时增量写 + 压缩摘要事件回填 |
| C7 | KV 前缀缓存要求稳定内容在前、动态内容在后 | 记忆卡只进动态层 |
| C8 | 宿主预览版会有破坏性变更 | 必须有适配层 |
| C9 | 单机本地、单用户 | 规模目标 10 万级记忆卡 |

## 7. 功能需求

优先级：P0 = M1 必须；P1 = M2；P2 = 后续。

### 7.1 写入与数据稳定

| 编号 | 优先级 | 需求 | 验收要点 |
|---|---|---|---|
| FR-A1 | P0 | 轮次边界异步写记忆卡，不阻塞回复 | 回复延迟与写入耗时无关 |
| FR-A2 | P0 | 幂等：同一事件重复处理不产生重复卡（按事件序号去重） | 重复导入同一会话，卡数不变 |
| FR-A3 | P0 | 原子性：单次写入要么全部生效要么不生效；崩溃后重启不受影响 | kill 进程后重启，无半条记录 |
| FR-A4 | P0 | 来源指针：每张卡记录 session/turn/step/原文序号 | 任意卡能定位回原文 |
| FR-A5 | P0 | 修正与版本：同一事实更新时保留旧版本，可查看历史 | 修正后可查"改过什么、为什么" |
| FR-A6 | P1 | 导出与重建：全量导出 JSONL，可从导出重建库 | 导出→重建→抽查 100 条一致 |
| FR-A7 | P1 | 索引可重建：向量/检索索引随时可丢弃重建，不影响真相源 | 删索引后自动重建 |

### 7.2 召回与内容稳定

| 编号 | 优先级 | 需求 | 验收要点 |
|---|---|---|---|
| FR-B1 | P0 | 打分公式：语义相关 + 重要性 + 时间衰减 + 目标匹配 + 置信度 − 冲突惩罚，权重可配 | 公式可单测，参数落在配置文件 |
| FR-B2 | P0 | 阈值截断：绝对阈值 + 相对 top 值阈值；硬上限 7 条 | 全低分时不硬塞 |
| FR-B3 | P0 | 确定性：固定模型版本与参数下，同状态同查询返回相同结果 | 10 次查询结果完全一致 |
| FR-B4 | P0 | 可解释：焦点包每条附分数构成（各分项与总分） | 能回答"为什么想起这条" |
| FR-B5 | P1 | 冲突显式：冲突记忆标 CONFLICT 并同时暴露双方 | 冲突不隐藏 |
| FR-B6 | P0 | 不编造：模型只能引用焦点包内容；召回为空时**不得编造**，且系统要能给出"没有相关记忆"的明确信号（`renderEmptyNote`），供命令输出与诊断使用；注入侧空包不写任何内容，避免诱导模型主动声明"我查过了" | 构造空库场景验证；空包时注入文本为空，`renderEmptyNote` 返回明确说明 |
| FR-B7 | P0 | 看到与使用分离：**召回本身不改变记忆状态**（不改强度、不改访问计数、不写日志），只有显式确认「这条被真正用上了」才加深记忆。理由见起源 L29（第 5 条·专注当前位置）：若召回即强化，则偶然召回 → 强度上升 → 更易被召回，形成马太效应，把历史噪音越推越前，与「专注当前位置」相反 | `recall`/`peek` 前后强度、访问计数、日志字节数**均不变**；`confirmRecall` 后访问计数 +1、强度上升；有对照测试证明写库确实会发生（防止只读测试假绿） |

### 7.3 遗忘与巩固

| 编号 | 优先级 | 需求 | 验收要点 |
|---|---|---|---|
| FR-C1 | P1 | 夜整理最小集：去重、合并、降权、归档、重建索引，产出变更日志；整理前先产出当日日摘要（与 FR-D4 衔接），整理进度 `lastRunAt` 必须落盘，重启后不重复执行 | 每次整理有一份可读报告；重启后再跑一次不会重复衰减 |
| FR-C2 | P0 | 遗忘可逆：归档不删除，可恢复 | 恢复后能正常召回 |
| FR-C3 | P1 | 阈值可配 + 永不归档类别（承诺、核心事实、长期偏好、**感受**） | 这些类别不会被归档；`feeling` 卡在任何归档策略下都保留 |
| FR-C5 | P1 | 感受必须**被产出**而不只是被保留：从事件卡蒸馏出 `feeling` 卡，并用 `distills` 边指向源事件。理由见起源 L11（无编号·细节会忘只留感受）与 L19（无编号·如何出现感受和经验的写入和回忆）——只做到「不删感受」而没有任何产出路径，等于假设感受是外部送进来的，而起源问的正是「如何出现」 | 从一批事件卡能蒸馏出 `feeling` 卡；该卡带 `distills` 边指向源事件；蒸馏出的卡在归档策略下不被吃掉 |
| FR-C4 | P0 | 库增长有界：无上限增长时自动触发合并与归档 | 连续两周使用，库大小趋于平稳 |

> **FR-C3 注（2026-11 对齐，缺陷同源于「机制在数学上恒为空」）：**
> 本行原文里的四类在数据模型中没有一一对应的 `MemoryKind`——`MemoryKind` 是
> `event / fact / promise / concept / feeling / experience / summary` 七值。
> 实现层面的映射与取舍是：**「承诺」→ `promise`、「核心事实」→ `fact`、
> 「感受」→ `feeling`**；「长期偏好」没有独立类别（偏好句在抽取时会落到
> `fact` 或 `feeling`），因此由前两者共同覆盖。
>
> **这一条曾经长期不一致**：实现里的 `forgetting.neverArchiveKinds` 只有
> `['feeling', 'promise', 'concept', 'experience']`，**`fact` 从来不在列**，
> 于是「我决定数据库以后就用 PostgreSQL」这类结论性内容一旦强度衰减到阈值
> 以下就会被夜整理自动归档——与「核心事实不被归档」直接矛盾。更糟的是
> `tests/consolidate/archive.test.ts` 里有一条用例名叫「事件、事实不受类别保护」，
> **把与规格相反的行为固化成了契约**（替实现打掩护的测试）。
>
> **取舍：选择改实现（把 `fact` 加进去），不选「改规格删掉核心事实」。**
> 判据是实测而不是印象——探针走真实链路（`gateTurn` → `extractCards` →
> `draftToCard`），42 句日常中文覆盖闲聊 / 决策 / 偏好 / 承诺 / 情绪 / 事件 /
> 技术陈述各 6 句，测得 `fact` 只占产出卡的 **21.1%（4/19）**，远低于
> 「类别保护覆盖绝大部分卡 ⇒ 归档路径恒为空」的 40% 经验线；且这 4 张按真实
> 意图全是决策 / 技术陈述，没有一张是临时事件。补进 `fact` 之后样本里仍有
> **6/19（31.6%）可归档**，归档机制不是空集。
>
> 若将来 `fact` 的占比真的涨到覆盖大部分产出（例如分类器变得更宽），
> 这里必须重新裁决——那时「全保护」与「永不遗忘」不可兼得，正确动作是
> 收紧 `classifySentence` 的 fact 判据，而不是把这个类别再移出去。

## 9. 已定决策（Decision Log）

| 编号 | 决策 | 理由 |
|---|---|---|
| D-01 | TypeScript / ESM / Cordis 插件主干 | 注入点必须在宿主进程内 |
| D-02 | 先在 CLI `dsh web` profile 验证，再进桌面 profile | 可热重载、可灰度 |
| D-03 | 主注入点 `systemPrompt.context()` | 追加式、KV 安全、压缩后自愈 |
| D-04 | 存储用 storage domain + node:sqlite 后端 | 避免原生模块 ABI 风险 |
| D-05 | 不写自定义 session 事件类型 | 读路径会拒绝未知事件 |
| D-06 | 压缩不做前置阻塞：增量写 + 摘要事件回填 | 宿主没有压缩前钩子 |
| D-07 | 时间读数复用 `dsh-time-context` | 不重复造时钟 |
| D-08 | 数据面在 host 平面单例，行为面按 agent 挂载 | 为将来多 agent 留接口，当前只有一个 |
| D-09 | **范围收敛为稳定记忆**：双人格/分身/机械飞升暂缓 | 地基优先 |
| D-10 | 本阶段不引入人格/身份机制 | 稳定记忆不需要 persona 层 |
| D-11 | 记忆卡写入由系统驱动，不开放"模型写记忆"工具 | 防止自说自话污染记忆库 |
| D-12 | 第一版不做多模态 | 独立感知层，后续接入 |

## 12. 验收

### 12.1 稳定性验收（本阶段硬指标）

| 编号 | 测试 | 通过标准 |
|---|---|---|
| ST-1 | 重启一致 | 相同状态+参数+查询，连续 10 次召回结果完全一致 |
| ST-2 | 幂等 | 重复导入同一会话两次，记忆卡数量不变 |
| ST-3 | 崩溃恢复 | 写入过程中强杀进程，重启后已确认写入完整、无半条记录 |
| ST-4 | 来源可追溯 | 随机抽 100 张卡，100% 能定位回原始事件 |
| ST-5 | 不编造 | 空库/无关话题时，明确回答"没有相关记忆"，不臆造 |
| ST-6 | 上下文稳定 | 连续 50 轮，动态层 token 波动 ≤ ±10%，不单调增长 |
| ST-7 | 遗忘可逆 | 归档的记忆可恢复并正常召回 |
| ST-8 | 导出重建 | 全量导出后重建，抽查 100 条一致，召回结果一致 |

### 12.2 功能场景验收

| 编号 | 场景 | 通过标准 |
|---|---|---|
