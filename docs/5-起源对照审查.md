## 第二部分：遗漏项清单

按「起源有 → 需求规格承接了 → 代码没做或做得很弱」三重过滤，共 12 项。前 7 项是点名的高风险点。

### 2.1 高风险点逐个核查

#### ① 起源第 1 条「激素是关键」→ `emotional` 到底参与打分/遗忘了吗？

**答：参与了，但参与得很浅，而且「感受」这一侧的保护是缺的。**

`emotional` 一共有三处消费：

1. **打分**：`src/core/scoring.ts:90`
   ```ts
   const raw = card.salience * 0.55 + card.emotional * 0.25 + accessBoost * 0.20
   ```
   再乘 `weights.importance = 0.18`（`src/core/config.ts:142`）→ 情绪对总分的**实际最大贡献 = 0.25 × 0.18 = 0.045**。而语义相关权重是 0.42。也就是说：**一条情绪强度拉满的记忆，比一条情绪为零的记忆，只多值 4.5% 的分**。这个量级在绝对阈值（`absoluteThreshold: 0.18`）面前几乎无效。

2. **遗忘（半衰期）**：`src/core/scoring.ts:220` 与 `src/consolidate/decay.ts:76`
   ```
   情绪因子 = 1 + emotional × (emotionalHalfLifeBoost − 1)   // 默认 2.0
   ```
   `emotional = 1` 时半衰期从 14 天变 28 天。这是**唯一真正有意义的一处**，做得对。

3. **合并**：`src/consolidate/dedupe.ts:263` 取最大值，注释写明「强烈的感受不能因为合并而稀释」。做得对。

**但这里有三个真问题：**

- **`feeling` 卡不受保护**。`src/core/config.ts:163`：
  ```ts
  neverArchiveKinds: ['promise', 'concept', 'experience'],
  ```
  **没有 `feeling`**。而 `src/core/types.ts:40` 明说 `feeling` 就是「起源『我们大多数细节都会忘记，只会留下感受』」的落地。现在的实际行为是：**一张「今天有点累」的感受卡，14 天后强度衰减到 0.08 以下就被归档了**，而一张「这个项目用 Qt5」的事实卡只要被召回几次就能活很久。
  → 这与起源**直接矛盾**。而且 FR-C3 列的「永不归档类别（承诺、核心事实、长期偏好）」里也没有感受——**这是需求规格的缺口**（`docs/1-需求规格.md:148`），代码照抄了这个缺口。

- **`emotional` 只在写入时算一次**。`src/core/extraction.ts:230` 之后，全库没有任何地方更新它。一次召回、一次修正、一次合并都不会让情绪变化。它是个静态标签。

- **`computeEmotional` 的正则有重复项**。`src/core/extraction.ts:155` 的强情绪词表里 `特别` 写了两遍。虽然 `match` 是计数不去重，影响极小，但说明这段没被认真过。

#### ③ 起源第 5 条「专注当前位置，不会代入其它记忆」→ 有专注/抑制机制吗？

**答：没有。只有 top-k 检索，而且召回反馈是正反馈，与「专注」的语义相反。**

召回全流程（`src/host/engine.ts:155-186`）：

```
倒排索引取候选（candidateLimit=400）
  + 已到期事项（永远为空，见 ①）
  + 钉住的卡
→ scoreCards 逐条打分
→ buildFocusPack（绝对阈值 + 相对阈值 + maxCards=7 + token 预算）
```

这是**标准的 RAG 检索**，只是多了阈值。起源要的「专注机制」比这多两件事：

**（a）没有任何抑制（inhibition）**

- 没有「上一轮刚注入的不再注入」——同一张卡可以在连续 10 轮里被注入 10 次。
- 没有「话题切换抑制」——用户从「线性代数」切到「昨天吃了什么」，前一个话题的高分卡照样参与竞争。
- 没有侧抑制（lateral inhibition）——分数相近的卡不做互相压制，只做绝对/相对阈值截断。
- `query.domains`（`src/core/scoring.ts:55`）是**死字段**，域级聚焦完全没生效。

**（b）召回反馈是正反馈，方向相反**

`src/host/engine.ts:180-186`：

```ts
for (const item of pack.cards) {
  this.store.append({
    op: 'touch',
    id: item.card.id,
    at,
    strength: Math.min(1, item.card.strength + this.config.forgetting.accessBoost),
  })
}
```

被召回的卡 `accessCount + 1`、`strength + 0.18`。而 `accessCount` 又同时进入：
- 重要性分（`src/core/scoring.ts:89`）
- 有效半衰期（`src/core/scoring.ts:223`）
- 衰减半衰期（`src/consolidate/decay.ts:83`）

三重放大。结果就是**马太效应**：前几轮被召回的卡越来越容易被召回，其余卡越来越难。「专注」是**当前**话题的抑制，不是**历史**召回的累积——现在的实现恰恰相反。

**（c）「目标匹配」项在默认路径下恒为 0**

`src/host/engine.ts:155`：`recall(queryText: string, goalText = '')`。而 `src/index.ts:177` 调用时只传了 `engine.recentQuery()`，**没传目标**。`goalTokens` 为空集 → `goalScore` 直接 `return 0`（`src/core/scoring.ts:105`）。FR-B1 明确要求的「目标匹配」分项，**在生产路径上是死的**。

**（d）查询文本的来源很可疑**

`src/index.ts:177` 用 `engine.recentQuery()` 作为召回查询。看 `src/host/engine.ts:265-271`：

```ts
recentQuery(): string {
  let latest: MemoryCard | null = null
  for (const card of this.store.listCards({ status: 'active' })) {
    if (latest === null || card.updatedAt > latest.updatedAt) latest = card
  }
  return latest?.text ?? ''
}
```

它返回的是**库里最近更新的那张卡的文本**，不是用户当前消息。注释（`src/index.ts:175-176`）辩称「此刻还没拿到本轮请求，但上一轮的意图通常就是当前话题」——但实现根本不是「上一轮意图」，是「上一张卡的正文」，那是被抽取并截断到 160 字的一句话。**用一个记忆碎片当检索查询，语义漂移不可控**。这是接线层最该改的一处。

#### ④ 起源第 6 条「上下文 = 某个瞬间大脑信号的瞬时状态」→ 焦点包体现「瞬时」了吗？

**答：体现了「瞬时重建」，没体现「状态」。**

`src/core/types.ts:247-262` 的 `FocusPack`：

```ts
export interface FocusPack {
  cards: ScoredCard[]
  tokens: number
  budgetTokens: number
  query: string
  builtAt: number
  empty: boolean
  note: string
}
```

这是一个**检索结果快照**，不是**状态**。判断依据：

| 起源要的「瞬时状态」成分 | FocusPack 里有吗 |
|---|---|
| 当前注意力焦点（在做什么） | ❌ 只有 `query` 字符串 |
| 当前目标 / 意图 | ❌ `goalTokens` 默认空（见 ③c） |
| 唤醒度 / 情绪 | ❌ 无（FR-G2 移出，合理） |
| 上一瞬到这一瞬的变化（焦点漂移） | ❌ 无跨轮状态 |
| 时间坐标 | ✅ 只有渲染时一行 `当前时间：`（`src/core/scoring.ts:395`） |

**关键点**：`buildFocusPack` 是**纯函数**——同样的 `(state, query, now)` 永远得到同样的包。这对 ST-1 确定性是好事，但也意味着**它不可能承载「瞬时状态」**，因为状态天然依赖历史。

这不是要否定现在的设计（FR-G2 明确把状态向量移出本阶段，`docs/1-需求规格.md:184`），而是要指出：**「瞬时状态」这个比喻在本阶段只能做到「瞬时」，做不到「状态」。** 若想向起源靠一点，成本最低的是给 `RecallQuery` 加一个**上一轮焦点包的卡 id 集合**，用于抑制重复注入（见 ③a）。这不需要状态向量，只需要一个 `Set<string>`。

#### ⑥ 起源第 7 条「利用有限上下文衍生真正智能」→ 记忆系统真的在节省上下文吗？

**答：方向对，但有三处会让上下文「膨胀」的实现问题。**

**做对的部分**：
- `maxCards: 7`（`src/core/config.ts:151`）硬上限，符合术语表「焦点包 3~7 条」
- `tokenBudget: 900`（`src/core/config.ts:153`），`buildFocusPack` 里逐条累加 `estimateTokens` 硬截断（`src/core/scoring.ts:318-335`）
- 只注入摘要，不注入分数、来源指针、候选池（`src/core/scoring.ts:359-362`）
- 候选池（400 条）完全在内存里，不进上下文

**会让上下文膨胀的三处**：

1. **`renderFocusPack` 的头尾固定开销不计入预算**。`src/core/scoring.ts:391-406`：
   ```ts
   lines.push('## 相关记忆（由记忆系统自动召回，非用户输入）')   // ~25 token
   lines.push(`当前时间：${formatTime(...)}`)                    // ~15 token
   ...卡片...
   lines.push('以上是系统召回的旧记忆，可能过时或不完整；与当前对话冲突时以当前对话为准。')  // ~40 token
   ```
   固定开销约 **80 token**，**完全不在 `pack.tokens` 里**。FR-E3 要求「每轮记忆注入有硬上限」，实际硬上限是 `900 + 80 + 时间块`。ST-6（连续 50 轮波动 ≤ ±10%）在这个基础上大概率过不了。

2. **`truncate(..., 200)` 硬编码**。`src/core/scoring.ts:398`：
   ```ts
   const text = truncate(item.card.text, 200)
   ```
   而 `buildFocusPack` 估算 token 时用的是 `config.recall.maxCardChars`（=160，`src/core/scoring.ts:319`）。**估算用 160，渲染用 200**——`pack.tokens` 系统性低估约 25%。这直接违反 AGENTS.md 硬性约定 5「所有阈值、权重、上限必须落在 `src/core/config.ts`，禁止散落字面量」。

3. **时间读数是预算外的额外注入**。`src/index.ts:179-181`：
   ```ts
   const time = engine.renderTime()
   if (time.length > 0) blocks.push(time)
   if (result.text.length > 0) blocks.push(result.text)
   ```
   时间块**独立于焦点包预算**，永远注入。所以真实注入量 = 时间块 + 焦点包 + 固定头尾，三者只有中间一项受 `tokenBudget` 约束。

4. **空包时的自相矛盾**。`src/core/scoring.ts:345` 精心构造了 `note: '没有相关记忆。'`（FR-B6 要求），然后 `src/core/scoring.ts:392`：
   ```ts
   if (pack.empty) return ''
   ```
   **空包时什么都不注入，`note` 永远到不了模型。** 模型看不到「没有相关记忆」这句话，反而更容易编造。FR-B6 与 ST-5 的核心验收项**在渲染层被自己废掉了**。`tests/core/scoring.test.ts:170` 只断言 `pack.note.length > 0`——测了 note 存在，没测 note 被用。这是本次审查最讽刺的一处：写了、测了、然后没用。

#### ⑦ 起源开篇「大多数细节都会忘记，只会留下感受」→ 实现是「记住细节」还是「留下感受」？

**答：是「记住细节」。差距最大的一条，也是最难补的一条。**

看写入路径（`src/core/extraction.ts:205-244`）：

```ts
for (const sentence of splitSentences(text)) {
  ...
  const kind = classifySentence(sentence)      // 正则分类
  const salience = computeSalience(...)
  if (salience < 0.25) continue
  const text = truncate(sentence.trim(), config.recall.maxCardChars)   // 160 字
  drafts.push({ kind, text, ... })
}
```

**每一句都变成一张卡，卡的正文就是原句截断 160 字。** 这就是「记住细节」的字面实现。

对比起源要的东西：

| 起源要的 | 代码做的 |
|---|---|
| 细节**忘掉** | 细节**逐句存卡**，`event` 是兜底类型（`src/core/extraction.ts:119`），占绝大多数 |
| 留下**感受** | `feeling` 只是一个 kind 标签 + 12 个词的正则（`src/core/extraction.ts:113`），且**不在永不归档列表**（`src/core/config.ts:163`） |
| 感受是**提炼**出来的 | 没有任何提炼：没有「从 N 张事件卡合成 1 张感受卡」，没有日终「今天感觉如何」，没有 `event → feeling` 的边 |
| 经验是**沉淀**的 | `experience` 同样只能靠单句正则命中（`src/core/extraction.ts:115`）；`distills` 边（`src/core/types.ts:179`）**定义了但从不生成** |

**具体缺口**：

1. **`feeling` 卡的来源是「用户说了感受词」，不是「系统提炼了感受」。** 用户不说「我感觉……」，系统就永远不会有感受卡。这跟「大多数细节会忘记、只留下感受」的机制**完全不同**——人的感受是从大量细节里自动沉淀的，不需要显式声明。

2. **`event` 卡没有任何「被感受吸收后降权」的路径。** 一张 `feeling` 卡和它对应的一堆 `event` 卡之间没有连接、没有替代关系、没有「感受留下、细节退场」的机制。`event` 卡只能靠时间衰减慢慢归档（半衰期 14 天）。

3. **合并方向是反的。** `src/consolidate/dedupe.ts:210` 合并时「取最长的那条文本」——**越详细越容易存活**。而起源要的是「细节压缩成感受」，应该是越抽象越存活。

**差距量化**：如果起源的「留下感受」是 100 分，现在大概在 **15 分**——类型定义到位了（`src/core/types.ts:40-46`），机制一步都没走。

**但要说清楚**：完整的「感受抽象」需要 LLM 提炼，而 FR-G3「夜整理的经验抽象（LLM 提炼经验卡）」明确排在「基础去重合并稳定之后」。所以**本阶段不该做 LLM 提炼**。本阶段该做的是三件低成本的事：
- `feeling` 进 `neverArchiveKinds`（1 行）
- 感受卡的 `emotional` 下限提高（几行）
- 事件卡被感受卡「覆盖」后加速衰减（几十行）

**一句话判断**：这是一个**优秀的记忆数据层** + **合格的行为层** + **刚接上的适配层**。它现在能跑起来了，但跑起来的方向和起源指的方向有一处**相反**——它在攒细节，起源要它留感受。
