## 第二部分：遗漏项清单

按「起源有 → 需求规格承接了 → 代码没做或做得很弱」三重过滤，共 **18 项**。前 7 项是点名的高风险点。

### 2.1 高风险点逐个核查

#### ① 起源 L3「激素是关键」→ `emotional` 到底参与打分/遗忘了吗？

**答：参与了，但参与得很浅。** 三处消费：

1. **打分** — `src/core/scoring.ts:90`
   ```ts
   const raw = card.salience * 0.55 + card.emotional * 0.25 + accessBoost * 0.20
   ```
   再乘 `weights.importance = 0.18`（`src/core/config.ts:186`）→ 情绪对总分**最大贡献 = 0.045**。而语义权重 0.42。**一条情绪拉满的记忆，只比零情绪的多值 4.5% 的分**——在 `absoluteThreshold: 0.18` 面前几乎无效。

2. **遗忘（半衰期）** — `src/core/scoring.ts:220`、`src/consolidate/decay.ts:76`
   ```
   情绪因子 = 1 + emotional × (emotionalHalfLifeBoost − 1)   // 默认 2.0
   ```
   `emotional = 1` 时半衰期 14 天 → 28 天。**这是唯一真正有意义的一处，做得对。**

3. **合并** — `src/consolidate/dedupe.ts` `mergeGroup` 取最大值，注释写明「强烈的感受不能因为合并而稀释」。**做得对。**

**真问题两个**：

- **`emotional` 只在写入时算一次**。`src/core/extraction.ts:242` 之后，全库无任何地方更新它。召回、修正、合并都不改变情绪。它是个**静态标签**。
- **「感受必须留下」的机制仍是零**。✅ 配置层已修（`src/core/config.ts:211` 含 `feeling`），但这只是「别把用户明说的感受删掉」。起源要的是**从大量细节里自动沉淀出感受**，那需要 `event → feeling` 的提炼，`src/` 里一行都没有。

**结论**：`emotional` **参与了打分和遗忘，但强度不足以支撑「激素是关键」这句话**。

#### ③ 起源 L29「专注当前位置，不会代入其它记忆」→ 有专注/抑制机制吗？

**答：没有。只有 top-k 检索，且召回反馈是正反馈，与「专注」语义相反。**

召回全流程（`src/host/engine.ts:214-247`）：

```
倒排索引取候选（candidateLimit=400）
  + 已到期事项（`pickDue`，见第 1 条：能用，但不会推进 `dueAt`）
  + 钉住的卡
→ scoreCards 逐条打分
→ buildFocusPack（绝对阈值 + 相对阈值 + maxCards=7 + token 预算）
```

这是**标准 RAG 检索**，只是多了阈值。起源要的「专注机制」比这多两件事：

**（a）没有任何抑制（inhibition）**

- 没有「上一轮刚注入的不再注入」——同一张卡可在连续 10 轮被注入 10 次。
- 没有「话题切换抑制」——用户从「线性代数」切到「昨天吃了什么」，前话题高分卡照样竞争。
- 没有侧抑制（lateral inhibition）——分数相近的卡不互相压制，只做绝对/相对阈值截断。

**（b）召回反馈是正反馈，方向相反**

`src/host/engine.ts:239-247`：

```ts
for (const item of pack.cards) {
  this.store.append({
    op: 'touch',
    id: item.card.id,
    at,
    strength: Math.min(1, item.card.strength + this.config.forgetting.accessBoost),
  })
}
```

被召回的卡 `accessCount + 1`、`strength + 0.18`。而 `accessCount` 同时进入：
- 重要性分（`src/core/scoring.ts:89`）
- 有效半衰期（`src/core/scoring.ts:223`）
- 衰减半衰期（`src/consolidate/decay.ts:83`）

三重放大 → **马太效应**：前几轮被召回的卡越来越容易被召回。「专注」是**当前**话题的抑制，不是**历史**召回的累积——现在的实现恰恰相反。

**（c）「目标匹配」在默认路径恒 0**

`src/host/engine.ts:214`：`recall(queryText: string, goalText = '')`。而 `src/index.ts:269` 调用时只传 `engine.recentQuery()`，**没传目标** → `goalTokens` 空 → `goalScore` 直接 `return 0`（`src/core/scoring.ts:105`）。FR-B1 要求的「目标匹配」分项，**在生产路径上是死的**。

**（d）查询文本的来源可疑**

`src/index.ts:269` 用 `engine.recentQuery()` 当召回查询。看 `src/host/engine.ts:383-388`：

```ts
recentQuery(): string {
  let latest: MemoryCard | null = null
  for (const card of this.store.listCards({ status: 'active' })) {
    if (latest === null || card.updatedAt > latest.updatedAt) latest = card
  }
  return latest?.text ?? ''
}
```

返回的是**库里最近更新的那张卡的正文**，不是用户当前消息。注释（`src/index.ts:267-268`）辩称「此刻还没拿到本轮请求，但上一轮的意图通常就是当前话题」——但实现根本不是「上一轮意图」，是「上一张卡被抽取并截断到 160 字的一句话」。**用一个记忆碎片当检索查询，语义漂移不可控。**

#### ④ 起源 L31「上下文 = 某个瞬间大脑信号的瞬时状态」→ 焦点包体现「瞬时」了吗？

**答：体现了「瞬时重建」，没体现「状态」。**

`src/core/types.ts:248-263` 的 `FocusPack`：

```ts
export interface FocusPack {
  cards: ScoredCard[]
  tokens: number
  budgetTokens: number
  maxCardChars: number
  query: string
  builtAt: number
  empty: boolean
  note: string
}
```

这是一个**检索结果快照**，不是**状态**。逐项对照：

| 起源要的「瞬时状态」成分 | FocusPack 里有吗 |
|---|---|
| 当前注意力焦点（在做什么） | ❌ 只有 `query` 字符串 |
| 当前目标 / 意图 | ❌ `goalTokens` 默认空（见 ③c） |
| 唤醒度 / 情绪 | ❌ 无（FR-G2 移出，合理） |
| 上一瞬到这一瞬的变化（焦点漂移） | ❌ 无跨轮状态 |
| 时间坐标 | ✅ 只有渲染时一行 `当前时间：`（`src/core/scoring.ts:424`） |

**关键点**：`buildFocusPack` 是**纯函数**——同样的 `(state, query, now)` 永远得到同样的包。这对 ST-1 确定性是好事，但也意味着**它不可能承载「瞬时状态」**，因为状态天然依赖历史。

这不是否定现在的设计（FR-G2 明确把状态向量移出本阶段，`docs/1-需求规格.md:184`），而是指出：**「瞬时状态」这个比喻在本阶段只能做到「瞬时」，做不到「状态」。** 若想向起源靠一点，成本最低的是给 `RecallQuery` 加一个**上一轮焦点包的卡 id 集合**，用于抑制重复注入。这不需要状态向量，只需要一个 `Set<string>`。

#### ⑦ 起源 L11「大多数细节都会忘记，只会留下感受」→ 在记细节还是留感受？

**答：在记细节。差距最大的一条，也是最难补的一条。**

写入路径（`src/core/extraction.ts:214-244`）：

```ts
for (const sentence of splitSentences(text)) {
  ...
  const kind = classifySentence(sentence)      // 正则分类
  const salience = computeSalience(...)
  if (salience < 0.25) continue
```

| 起源要的 | 代码做的 |
|---|---|
| 细节**忘掉** | 细节**逐句存卡**，`event` 是兜底类型（`src/core/extraction.ts:125`），占绝大多数 |

**三个具体缺口**：

1. **`feeling` 的来源是「用户说了感受词」，不是「系统提炼了感受」。** 用户不说「我感觉……」，系统就永远没有感受卡。这跟「大多数细节会忘记、只留下感受」的机制**完全不同**——人的感受从大量细节自动沉淀，不需要显式声明。

加权：`17×0.2 + 13×0.2 + 12×0.2 + 11×0.15 + 8×0.15 + 1.5×0.1 = 3.4 + 2.6 + 2.4 + 1.65 + 1.2 + 0.15 = 11.40`

按满分 20 归一化：`11.40 / 20 = 57.0%`——但这是「需求规格维度」的分数。**对起源的忠实度要再打折**，因为：

- 起源最核心的「只留感受」在机制层仍是**反向的**（在攒细节，不是在提炼感受）
- 图谱（L15）本阶段无需求承接却已写了 202 行，属**越界**
- 「专注当前位置」缺抑制，且有正反馈反向拉扯
- 「渐进累积」「很长时间迭代」完全没有

取 **37%**。审查初期是 32%，涨到 37% 是因为修了 12 项——**修了 12 项只涨 5 分，说明修的全是「别做错」，没有一项是「做对方向」**。

其中 `dueAt` 那一条线（`src/time/due.ts` 307 行 + `dueNow`/`markReminded` + 轮询器）是本审查期间唯一一次**新增能力**，因此贡献了 3 分；其余 11 项都是「把本来该对的地方改对」，合计贡献约 2 分。这个不对称本身就是结论：**仓库在补漏，还没在长本事。**

**一句话判断**：这是一个**优秀的记忆数据层** + **合格的行为层** + **刚接上的适配层**。它现在能跑起来了，但跑起来的方向和起源指的方向有一处**相反**——它在攒细节，起源要它留感受。修 `neverArchiveKinds` 只是「别把感受删掉」，不是「生成感受」。**真正的差距在后者，而后者本阶段不该做**（需要 LLM 提炼，FR-G3）。
