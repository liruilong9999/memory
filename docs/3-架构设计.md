# 稳定记忆系统 · 架构设计

> 上游依据：`docs/0-起源.md`（最终目标）、`docs/1-需求规格.md`（v0.2 需求）、`docs/2-DSH宿主约束.md`（宿主边界）。
> 本文回答三个问题：**分几层**、**数据怎么流**、**每个需求编号落在哪段代码**。

---

## 1. 一句话架构

**一条日志、两个视图、三个面。**

- **一条日志**：记忆库的真相源是一串只追加的事件日志（`src/store/journal.ts`）。卡片、索引、焦点包全部是它的派生视图。
- **两个视图**：当前状态（卡片 + 图谱边，`src/store/state.ts`）与检索索引（倒排表，`src/store/inverted.ts`）。两者都可丢弃、可从日志重建（FR-A7）。
- **三个面**：
  - **数据面** `src/store/`：写得进、存得住。
  - **行为面** `src/core/` + `src/consolidate/`：取得回、忘得掉。
  - **适配面** `src/host/`：把上面两者接到 DSH 宿主上（唯一允许 import 宿主包的地方）。

对应决策 D-08「数据面在 host 平面单例，行为面按 agent 挂载」与 NFR-7「数据面/行为面/适配面分离，宿主升级只改适配层」。

## 2. 分层与依赖方向

```text
┌──────────────────────────────────────────────┐
│  适配面 src/host/                             │
│  · 订阅 turn 事件 → 调抽取 → 调数据面          │
│  · 每轮求值 context() → 打分 → 注入焦点包       │
│  · 注册 /memory 命令、夜整理定时器              │
└───────────────┬──────────────────────────────┘
                │ 只能向下依赖
┌───────────────▼──────────────────────────────┐
│  行为面 src/core/ + src/consolidate/ + src/time/ │
│  · 纯函数：抽取、打分、衰减、去重、归档、时间读数  │
│  · 无 IO、无宿主依赖、可完整单测                  │
└───────────────┬──────────────────────────────┘
                │
┌───────────────▼──────────────────────────────┐
│  数据面 src/store/                            │
│  · 事件日志、重放、倒排索引、导出导入            │
│  · 只依赖 node: 内置模块                        │
└──────────────────────────────────────────────┘
```

**单向依赖是硬约束**：`core ← store ← consolidate ← host` 中任何反向 import 都视为设计错误。
好处是宿主升级（C8）只需要改最上面一层，下面全部可以原地不动。

## 3. 一轮对话的数据流

```text
用户消息进来
    │
    ▼
[宿主] turn/start → agent/pre-step
    │
    ├─►【读路径】取用户最新消息作为 query
    │       │
    │       ├─ 分词（text.tokenize）
    │       ├─ 倒排索引取候选（inverted.search，上限 candidateLimit）
    │       ├─ 逐条打分（scoring.scoreCard：语义/重要性/新鲜度/目标/置信/冲突）
    │       ├─ 阈值截断（scoring.applyThresholds：绝对 + 相对 + 硬上限 7 条）
    │       └─ 装包（scoring.buildFocusPack：token 硬预算内截断）
    │       │
    │       ▼
    │   systemPrompt.context() 注册的 text 函数返回焦点包文本
    │       │
    │       ▼
    │   [宿主] 追加为 user 快照，进模型上下文（KV 安全）
    │
    ▼
[宿主] LLM 流式回复 → assistant/message
    │
    ▼
[宿主] agent/turn-stopping（串行、await）
    │
    └─►【写路径】异步，不阻塞回复（FR-A1）
            │
            ├─ 门控（extraction.gateTurn：信号词 / 长度）
            ├─ 切句 + 分类 + 打分（extraction.extractCards）
            ├─ 转完整卡（extraction.draftToCard，id 由内容派生 → 幂等）
            ├─ 追加日志（store.append，带幂等键 → 重复事件直接丢弃）
            └─ 更新内存状态 + 倒排索引
```

**关键设计**：读路径与写路径在时间上完全解耦。
写慢不影响回复（FR-A1），读快因为只查内存索引（NFR-1）。

## 4. 为什么用「事件日志 + 派生视图」而不是「一张会变的表」

需求原则 P2 明确要求「事件日志是唯一真相源」。落地好处有四条：

| 需求 | 日志方案如何满足 |
|---|---|
| FR-A2 幂等 | 每条日志带幂等键，重放时按键去重 |
| FR-A3 原子性 | 单行 JSONL 追加 + fsync，一行要么完整要么不存在 |
| FR-A5 修正留痕 | `revise` 操作显式保留旧版本，不覆盖 |
| FR-A7 索引可重建 | 索引是纯函数派生物，删了重建即可 |
| ST-2 重复导入不增卡 | 幂等键 = 来源指针 + 类型 + 归一化文本 |
| ST-8 导出重建一致 | 导出日志即导出真相源 |

**代价**：读取要重放。缓解办法是启动时一次性重放，之后增量应用；10 万卡量级重放耗时可接受（C9）。

### 4.1 打分分母恒含全部维度（「缺陷伪装成改进」的防线）

`scoreCard` 的归一化分母**恒为全部维度权重之和**，即使某个维度的输入缺失
（例如宿主没传 `goalText` 导致 `goalTokens` 为空）。该维度贡献 0，但权重
仍留在分母里。

为什么不把缺失维度的权重从分母摘掉：**那会让上游缺陷反而提升召回质量**。
具体算一遍——宿主漏传目标时，摘掉 `w.goal` 使分母从 1.15 降到 0.9，每张卡
的归一化分整体上浮约 11%，更容易越过阈值进入焦点包。于是：

> 宿主漏传目标 → 分数变好看 → 召回看起来更准 → **没人会去修那个漏传**。

这是最难排查的一类失败：不是算错了，而是**算错了还看起来更对**。代价是
`weights.goal` 配得越大、缺目标时整体越难达标——但这个压力加在「宿主该给
而没给」上，方向是对的；加在「记忆内容好不好」上则是错的。

配套要求：`explain` 必须如实标注该维度未启用（「目标匹配 未启用（本次未
提供目标，权重 X 计入分母）」），让人一眼看出分数被什么拖低了，而不是只
看到一个偏低的总分。

### 4.2 投影层不得改写事实（ST-1 的硬边界）

这是本系统里最容易犯、犯了又最难发现的一类错误，单独立一条约定。

日志是唯一真相源（P2），重放出来的状态是**读模型**。读模型的职责是
**搬运，不是裁决**——它无权把日志里写的值「修正」成它认为合理的值。

具体到 `src/store/state.ts` 的 `coerceKind` / `coerceDomain`，三种情况必须分开：

| 情况 | 处理 | 理由 |
|---|---|---|
| 已知成员 | 原样保留 | 正常路径 |
| **未知但合法的字符串** | **原样透传** | 前向兼容：旧版本读到新版本写的 `kind`，必须忠实搬运 |
| 缺失 / 非字符串 | 兜底默认值 | 此时**确实没有信息可保留**，兜底才成立 |

为什么第二条不能改成「兜底成 `fact`」：那会让日志写的是 A、重放出来是 B。
同一条日志两种结果，重放确定性直接破裂，而且**事后无从发现**——日志看着
正常，视图也看着正常，只有把它们并排比才看得出不一致。这比抛错危险得多。

推论：既然未知 `kind` 能透传到渲染层，渲染层就不能靠 `switch` 的隐式
`undefined` 兜底（会渲染出 `- [undefined] xxx`，比降级更难查）。
`src/core/scoring.ts` 的 `kindLabel` 因此显式 `default: return String(kind)`：
不发明中文、不假装认识，把真相摆出来。

> **已知的类型谎言**：`coerceKind` 用 `as MemoryKind` 断言，意味着类型系统
> 认为 `kind` 必然是那六个值，而运行时可能是更新的值。这是**刻意**的前向
> 兼容，不是漏校验。若将来 `MemoryKind` 需要真正开放，应改成 `string` 联合
> 而不是删掉这个断言。

## 5. 记忆卡的生命周期

```text
   抽取
    │
    ▼
 [active] ──衰减到阈值以下──► [archived] ──恢复──► [active]
    │                            │
    │                            └──► [purged]（硬删除，不可逆）
    │
    └──被重复卡合并──► [mergedInto 指向新卡]
```

- **归档不等于删除**（FR-C2）：归档只是标记 + 降强度，随时可恢复（ST-7）。
- **永不归档的类别**（FR-C3）：承诺（promise）、核心事实、长期偏好，以及任何 `pinned` 卡。
- **合并保留溯源**：`mergeOf` 记录被合并的卡 id，审计时能追回去。

## 6. 注入通道的选择

需求 FR-E2 与决策 D-03 指定主通道是 `systemPrompt.context()`。理由展开：

| 通道 | 落点 | 变化影响 | 是否可用 |
|---|---|---|---|
| `systemPrompt.section()` | system 消息（前缀） | 改写头部 → KV 缓存全失效 | ❌ 违反 C7 |
| `systemPrompt.context()` | 历史之后的 user 快照 | 只追加 → cache-safe | ✅ 主通道 |
| `agent/pre-step` 改 messages | 本次 step 的消息 | 需要小心不破坏消息序 | ⚠️ 备用 |

**压缩后自愈**（FR-E4）：`context()` 的 `text` 是每轮重新求值的函数，压缩清空历史后它会自动重新物化，不需要手动重放（待验证项 V-1）。

**上下文里只放摘要**（FR-E1）：卡片文本、类型标签，不放分数、不放来源指针、不放候选池。

## 7. 记忆图谱：跨层次关联怎么落地

起源第 4 条要求「建立记忆图谱，且能跨层次关联」。本系统的落地方式：

- **节点** = 记忆卡。
- **层次轴有两个**：域（生活/学习/工作）与类型（事件/事实/感受/经验）。边可以跨任一轴。
- **连边规则**（契约级构造在 `src/core/graph.ts`，策略在 `src/consolidate/graph.ts`）：
  - 共享实体 → `same-entity`（同一个人、同一个项目、同一个文件）
  - 文本相似度落在 `graph.topicFloor..duplicateSimilarity` 之间 → `same-topic`，
    并按 k 近邻（`graph.topicNeighbors`）封顶每张卡的度数
  - 合并时被并入卡指向存活卡 → `supersedes`（`src/store/state.ts` 的 merge 分支自动产出）
  - **感受卡指向它的来源事件卡 → `distills`**（起源 L11「细节会忘，只留感受」、L15 跨层次关联）
- **`distills` 的方向是「感受 → 原始事件」**，与 `supersedes` 的「旧 → 新」相反，
  这是刻意的：`supersedes` 表达「后者取代前者」，`distills` 表达「前者从后者提炼」。
  两者若同向，图谱上就无法区分「被取代」与「被提炼」，溯源时会读反。
- **边参与打分，但默认影子模式**：见下节 7.2。此前这里写的是「边不参与打分」，
  理由是「边是巩固面的产物，接进打分会让召回结果依赖巩固历史的副作用」。
  这个顾虑在实现扩散时被正面处理了，而不是绕开——**召回仍然只读**，
  扩散只读边集、不写边集，且边权变化只有一个显式入口（可塑性，当前未接线）。
  默认 `shadow` 意味着**照常计算但不改变排序**，所以「边不参与打分」在当前
  默认配置下仍然成立，只是系统同时积累了「如果参与会怎样」的证据。
- **不把边折进归一化分子**：归一化问的是「这张卡自己匹配得如何」，扩散加分
  是外部证据（「它的邻居匹配上了」）。折进分子会让 `explain` 说谎。

## 7.1 层级压缩与感受蒸馏（起源 L27 / L11）

夜整理的完整步骤顺序是**有约束的，不能随意调换**：

```text
一 取工作集 → 二 衰减 → 三 感受蒸馏 → 四 去重合并 → 五 摘要压缩 → 六 归档 → 七 连边 → 八 报告
```

三处顺序约束，每一处都有实测依据：

| 约束 | 若违反会怎样 |
|---|---|
| **蒸馏在去重之前** | 「反复经历」的证据是「多张卡共享同一主题」。去重会把高度相似的卡合并成一张，三张「上线又出问题」去重后只剩一张，`distillMinRecurrence` 永远达不到，感受层一条都产不出来（实测 `distilled = 0`）。 |
| **摘要在归档之前** | 归档的语义是「这段记忆已经不重要了」，把它算进「今天发生了什么」是自相矛盾。 |
| **摘要在蒸馏之后** | 日摘要要能把刚蒸馏出的感受统计进去，否则「今天的感受」在日摘要里永远缺席。 |

### 摘要的层级表达（不新增字段）

用现有字段表达三级摘要，避免为「摘要」再造一套数据结构：

| 信息 | 承载字段 | 示例 |
|---|---|---|
| 是摘要 | `kind` | `'summary'` |
| 哪一级 | `tags[0]` 前缀 | `daily:2026-11-02` / `weekly:2026-10-27` / `monthly:2026-11` |
| 时间键 | `source.sessionId` | 同上（冗余一份，便于按 source 查） |
| 来源卡 | `mergeOf` | 被压缩卡的 id 列表 |

**为什么必须真的压缩**：日摘要若只是把当天卡片的文本拼起来，那是**日志**不是摘要；
月摘要的信息量若不显著小于 30 张日摘要之和，压缩就是假的。两道门禁：

1. **算术门**（`summarize.ts`）：预算 = `min(层级上限, floor(来源字符数 × summaryTargetRatio))`，
   实现只按预算渲染统计与关键词，**从不拼接来源原文**。
2. **配置门**（`config.ts`）：`summaryTargetRatio >= 1` 直接校验失败；周/月上限必须严格
   小于上一级；`summaryMinChildren < 2` 直接失败（只有一个下级时是复制不是压缩）。
   配置层拒绝比代码里自觉判断更硬——它让「假压缩」在**配置层面不可能存在**。

摘要卡**不参与去重**（`findDuplicateGroups` 排除 `kind === 'summary'`）：摘要文本是
模板化统计句，任意两天的日摘要字面相似度极高，参与去重会被判重复合并掉，
「每天一张日摘要」在去重后只剩一张，层级压缩被自己的去重逻辑毁掉（实测两天的
日摘要确实进了同一分组）。摘要的唯一性由 `buildCardId`（日期键进 id）保证。

### 情绪通道：为什么抽取链路上要单独留一条（缺陷二十八/二十九/三十）

起源 L3（无编号·激素）说「激素是关键！！！大脑皮层只是记忆，激素控制情绪！！！」，
L11（无编号·细节会忘）说「细节会忘、感受会留」。这两条要求**情绪必须影响什么能进记忆**。

在缺陷二十八之前，这个入口**不存在**，而且是以最隐蔽的方式不存在的：
抽取链路上有四道过滤，每一道都「合理」，但判据全是「长度 / 信号词 / 实体」，
而情绪表达在这三项上恰恰是弱项。

| 闸 | 位置 | 原判据 | 情绪句为什么过不去 |
|---|---|---|---|
| ① 门控 | `gateTurn` | 信号词 ∨ 到期词 ∨ 助手信号 ∨ 双方都长 | 四条通道无一是情绪 |
| ② 逐句过滤 | `consume` | 有信号 ∨ 有实体 ∨ 长度 ≥ 40 | 「我快崩溃了」6 字、无实体、无信号词 |
| ③ 长度闸 | `consume` | `chars >= minTextChars`(6) | 「有点烦」3 字 |
| ④ 显著性 | `computeSalience` | 长度×0.42 + 信号×0.36 + 实体×0.22 | 短情绪句三项全低 |

**四道闸串联，任意一项恒假则整条路径恒假。只修任何一道，最终出卡仍然是 0。**
实测修复前情绪句通过率 **1/10**，且**高情绪组 17% < 低情绪组 43%**——
情绪越强越留不下来，方向是反的。

#### 修法：四条通道各加一条情绪理由，且不改变原有分数

第 ④ 项**必须用 `max(信息项, 情绪项)` 而不是加权相加**。理由是：

- 四项权重之和必须为 1，加权就得从原有三项里各砍一刀；
- 实测那样会让真正的决策句显著性下降 **18%**——为了修一个通道而弄坏另一个；
- 「信息量大」和「情绪强」是**两个独立的、择一的**记忆理由，不是互补分量。

取 `max` 则原有分数一分不动，情绪只负责把「本来进不来的」抬进来。
这条性质有配对测试守着：`信息量足够的决策句，显著性不会被情绪项改动`
与 `情绪项只在信息项不足时才起作用`。

#### 情绪豁免长度闸，但不得降低长度闸

`minTextChars` 是挡「嗯」「好的」这类寒暄的。情绪句豁免它，但**不能把闸本身调低**——
调低会放进所有寒暄。所以配了一条反向对照测试：`短情绪句豁免长度闸，但真正的寒暄
仍然被挡`。**只测「该放行的放行」是半个测试，必须有配对的反向对照。**

#### 情绪词表必须进配置

原实现只有 18 个硬编码词，「失望 / 慌 / 焦虑 / 委屈 / 疲惫 / 孤独 / 感激」全不在表内。
「哪些词算情绪」取决于用户的语言习惯，属于**配置项而非常量**。
现在 `extraction.emotionalStrongKeywords` / `emotionalMediumKeywords` 都在
`src/core/config.ts`，并有非空校验（否则情绪强度恒为标点项）。

`emotionalGateThreshold` 刻意等于 `consolidation.distillMinEmotional`（0.28），
避免出现「能写进来但永远蒸馏不出」的空隙——**两个门槛相等在这里是刻意的一致，
不是缺陷二十六那种「相等 ⇒ 恒空」的陷阱**，因为它们的可达区间是包含关系而非互斥。

### 蒸馏恒为空的三个独立原因

修好情绪通道让卡能写进来之后，`distilled` 仍然是 0。原因还有两个，
而**三个缺陷的观测值完全一样**（都是 `distilled = 0`）：

| 缺陷 | 机制 | 探针表现 |
|---|---|---|
| 二十八 | 情绪句写不进来 ⇒ 没有原料 | 门控 1/10 |
| 二十九 | 主题词按空格切整句 ⇒ 桶数恒为 0 | 5 张达标卡，桶数 0 |
| 三十 | 判据用 `kind` 标签 ⇒ 原话卡被排除 | 候选 5 → 1 < 阈值 2 |

**「能进来」和「能沉淀」是两件事。** 三个零长得一模一样，只能靠逐层探针区分，
不能靠「重跑一次看看」。

缺陷二十九的根因值得单记：`normalizeText` 把**所有标点替换成空格**，于是
`normalized.split(' ')` 切出来的是**整段长句**而不是词项。两张不同的情绪卡
几乎不可能共享一个整段长句，桶数因此恒为 0。修法是改用 `tokenize(card.normalized)`
——注意**必须传 `normalized` 而不是 `text`**，否则二元组会跨标点边界生成
`"，这"`、`"了，"` 这类假主题，感受卡写成「『，这』这件事反复牵动我的情绪」。
**主题词是判据，一个假主题会让两张本来无关的卡聚成桶。**

修好这三条之后还有**第四条**，它只能靠读产出发现：`STOP_WORDS` 没收
「有点 / 有些 / 非常 / 感觉 / 觉得」这类程度副词与感知动词，二元组分词把它们
当独立词项漏出来。它们区分度为零却高频出现在情绪句里，于是「有点烦」和「有点慌」
被聚成同一件事，感受卡写成「『有点』这件事反复牵动我的情绪」。

**主题词不是展示标签，是聚桶判据。** 判据错则整条链路都在为一个假前提服务，
而每一步都执行成功：不报错、`distilled` 正常非零、感受卡格式完全正确。
修在 `STOP_WORDS` 一处（不在 `themeTerms` 另加一层过滤，否则两个真相源，
检索侧也不会受益）。注意 `distilled` 从 2 降到 1——**「产出变多」和「产出变对」
是两件事**，只看数量会把这条修复误判成回归。

缺陷三十是「注释承诺的」与「实现判断的」不一致的又一例：
`if (card.kind === 'feeling') return false` 配着「感受卡本身不参与再蒸馏」的注释。
旧数据上恰好等价（原话当时进不来），修好上游后立刻失效。
正确判据是数据层可见的事实：`source.sessionId === DISTILL_SESSION_ID`。

### 感受蒸馏的诚实边界

`src/core/distill.ts` 是**规则版，不是语义理解**。它做的是：

1. 筛出 `emotional >= distillMinEmotional` 的活跃事件卡（排除感受卡本身，防止自激）；
2. 按实体/关键词聚桶，桶内张数 ≥ `distillMinRecurrence` 才算「反复经历」；
3. 渲染成「「X」这件事反复牵动我的情绪，前后经历了 N 次」。

**关键局限**：`computeEmotional` 只度量**强度**，不度量**极性**（开心与难过同分）。
因此产出的文本只说「反复牵动情绪」，**绝不说「开心」或「难过」**——写一个它判断
不出的情绪名，就是让文本撒谎。早期版本在末尾拼了来源原文当例子，结果原文里的
「特别开心」被读者当成了系统的情绪判断，已删除该引用。

`tests/core/distill.test.ts` 有一条用例**故意断言这个局限存在**：极性相反但强度相同的
两件事会被蒸馏成同一条感受。将来若引入极性，它会变红，提醒修改者同步更新本节。

## 7.2 图谱扩散激活与突触可塑性（FR-G1，默认影子模式）

需求出处：`docs/1-需求规格.md` §7.7「后续扩展（不在本阶段验收）」的 FR-G1。

**先说清诚实边界**：起源原文**没有出现**「突触 / 神经 / 扩散 / 激活 / 强化 /
衰减」任何一词。本功能是从起源 L15（无编号·图谱与跨层次关联）与 L11
（无编号·细节会忘只留感受）向前推一步，**不是起源的直接要求**。它的需求侧
依据是 FR-G1 自己，而 FR-G1 的触发条件是「稳定记忆跑通、积累了 2 周真实数据」。

### 三态开关：为什么不是布尔

`spread.mode` 取 `'off' | 'shadow' | 'on'`，默认 **`'shadow'`**。

不用 `enabled: boolean` + `shadow: boolean` 两个布尔，是因为那能表达出
「关掉了但还在影子计算」这种自相矛盾的状态；互斥的字符串联合从类型上就不允许。

| 模式 | 算什么 | 改排序 | 产出观察值 | 用途 |
|---|---|---|---|---|
| `off` | 不算 | 否 | 无 | 完全退化成引入本功能之前（FR-F4 可回滚） |
| `shadow` | **照常算** | 否 | **有** | 攒「打开会怎样」的证据，但不影响召回 |
| `on` | 算 | 是 | 无（已折进 `total`） | 真实参与排序 |

**为什么默认不是 `off`**：`off` 永远无法积累「它到底会怎么改」的证据，而那份
证据正是判断该不该打开它的依据。**为什么不是 `on`**：让一个未经真实数据检验
的机制默认生效，会悄悄改变每一次召回的排序——它改得不多，所以是这类缺陷里
最难发现的一种。`shadow` 让两者同时成立：**可见，但不生效。**

观察值存在 `ScoredCard.shadowSpread`（`boost` / `sources` /
`hypotheticalTotal` / `hypotheticalRank` / `actualRank`），**不进 `explain`**：
`explain` 会被人读渲染打印，假设值出现在那里会让读者以为它已生效。
`off` 与 `on` 下该字段都是 `undefined`——`off` 没算，`on` 已折进 `total`
（再记一份就是两个真相源）。

**影子模式必须算真账，不能近似。** 若它用了不同的种子集合或护栏，它预测的
就不是「打开后会怎样」，用近似值攒出的证据不足以支撑决策。所以
`hypotheticalRank` 的 tie-break 必须与真实路径**逐字相同**（分数降序 + id 升序），
有专项测试守这一点（同分场景是唯一能暴露 tie-break 错误的场景，
而它恰好是真实数据里最常见的）。

#### 观察值必须有出口，否则等于没算

`shadowSpread` 加上之后曾经**一个出口都没有**：`explain` 里不许放，注入文本
里更不能放（起源 L17·无编号·上下文污染）。结果是扩散在默认配置下每轮都在算，
但没有任何人能看到它算出了什么——**一个只有测试知道的机制，等于没有**。
这与 `goalText` 漏传、`confirmRecall` 零调用方是同一类问题：代码写了，链路不通。

现在有两个出口：

**出口一：人读渲染 `renderFocusPackExplain`**（`/memory explain` 与 CLI `query`
共用同一份实现，改一处两边生效）：

```text
■ 被扩散提权的卡
  总分 0.450
  recency 0.5 × 0.25 = 0.125
  [影子] 若开启扩散：+0.099 → 0.549，排名 2 → 1（当前未生效）
  [影子] 激活来自 2 张种子卡
```

三条约束各有测试守：影子行不混进 `explain`（语义不同）；「总分」那一行仍显示
实际值（假设值只在 `[影子]` 行）；必须明说「当前未生效」（这一行长得像分数的
一部分，读者极易误读）。

**出口二：结构化日志 `engine.recall` 的 `detail.shadow`**（FR-F1 可观测）。
摘要行追加「，影子模式下 N 条会被扩散提权（未生效）」，明细给出每条的
`id` / `boost` / `actualRank` / `hypotheticalRank`。键名用 `shadow` 而不是
`boost`——命名必须让它不可能被误读成已生效。

**`off` 与 `on` 都不带这个字段**，这是最容易被写错的一处：

| 模式 | 日志里有 `shadow` 吗 | 为什么 |
|---|---|---|
| `shadow` | 有（有观察值时） | 这是它唯一的出口 |
| `off` | **没有** | 根本没算扩散 |
| `on` | **没有** | 加分已折进 `total`，再记一份就是两个真相来源 |

若 `off` / `on` 也带这个字段（哪怕空数组），运维看日志会以为当前跑的是
shadow 模式。所以 `detail` 用条件展开而不是恒给键。

### 两层机制，可分别启用

| 层 | 机制 | 状态 |
|---|---|---|
| A | **扩散激活**：种子卡的激活沿边传播，给邻居加分 | **已接线**，库默认 `shadow`，出厂 patch 写 `on` |
| B | **边权可塑**：共激活强化、闲置衰减、低于阈值剪枝 | **函数已实现，未接线** |

#### 库默认值 `shadow` 与出厂 patch `on`，是两件事

这两个值不同，是有意的，不是不一致：

| 位置 | 值 | 它在回答什么问题 |
|---|---|---|
| `DEFAULT_CONFIG.spread.mode` | `'shadow'` | **没人配置时**，该不该擅自改变每一次召回的排序 |
| `cordis.patch.yml` | `'on'` | 发布者/用户**明确声明**要这个效果 |

库默认必须是保守的：未经真实数据检验的机制不该在无人配置时静默生效——
这正是当初选 `shadow` 而不是 `on` 的理由，不能因为「用户想要效果」就推翻。
而 patch 是**显式意图**，写在那里等于「我要」，不是「悄悄默认」。
用户诉求原话是「我要类似神经的突触效果」，所以出厂 patch 里把它打开。

这两件事以前是脱节的：patch 里**没有 `spread` 段**，于是出厂状态下扩散
每轮都在算、却不改排序也不改注入内容，用户拿不到效果，也没有任何文档
告诉他写什么。按本仓库自己的原则「算出来没人看得见，等于没算」，
这等于功能不存在。现在 `tests/host/patch.test.ts` 5 条测试守着 patch：
`mode` 必须存在、必须是合法值、必须是 `on`、必须与默认值不同且注释说明了
原因、`DEFAULT_CONFIG` 必须仍是 `shadow`。

那个测试的解析器**模拟 YAML 语义**而不只是正则取字符串：无引号的
`on` / `off` / `yes` / `no` 在 YAML 1.1 里是布尔值，宿主拿到的会是 `true`，
`validateConfig` 会拒绝 ⇒ 加载期失败。第一版解析器把裸 `on` 当字符串放过去了，
反向验证的 M4 变异**没命中**才暴露出来——**测试不能替「用户照抄文档就崩」
的写法背书**。

#### `maxBoost` 的定标：效果不随它增大而提升

用**严格判据**测（诱饵 = 与查询不共享任何实体，如「约定下周三去看牙医」），
20 张技术卡 + 4 张严格诱饵、12 个查询：

| `maxBoost` | 内容变化 | 顺序变化 | 可感知合计 | 污染 |
|---|---|---|---|---|
| 0.06 | 7/12 | 3/12 | 10/12 | **0** |
| 0.12（默认） | 7/12 | 3/12 | 10/12 | **0** |
| 0.18 | 7/12 | 3/12 | 10/12 | **0** |
| 0.20 | 7/12 | 3/12 | 10/12 | **0** |
| 0.30 | 7/12 | 3/12 | 10/12 | **0** |

**效果不随 `maxBoost` 增大而提升，污染始终为 0** ⇒ 保持 `0.12`，
不要为了「效果更明显」去调大它。

这里记一次**标注错误**：第一版把「决定 Redis 那本旧书拿去卖废纸」记成诱饵
越线，据此得出「0.2 会引入 4 张诱饵」。但那句话**确实含 Redis 实体**，
它是「一条关于 Redis 的记忆」，被 Redis 查询联想出来是图谱按实体关联的
**合理结果**，不是污染。换成不共享任何实体的诱饵后，控制臂越线 0 次、
实验臂越线 1 次。**用错标注定参数，会把设计行为当成缺陷去修**——
与缺陷五那次「同一句话标成两个主题」是同一类错误，只是错在「什么算无关」。

#### 真缺陷七：`on` 模式下 explain 自相矛盾，突触效果也算而不可见

这一条比前面几条更直接地伤到用户体验，因为它**不报错、不崩、测试全绿**，
只是把一张自相矛盾的账单摊在用户面前。

`explain` 由 `scoreCard` 生成，那时扩散**还没发生**（`mergeSpread` 在打分
之后才跑）。`applySpread` 只改 `score.total`，不改 `explain`。于是 `on`
模式下同一张卡在人读渲染里报出**两个互相矛盾的总分**：

```text
■ 约定 Redis 的过期时间设成 300 秒，注意踩坑
  总分 0.449          ← 头行取 score.total（已含 +0.12）
  语义相关 0.500 × 权重 0.420 = 0.210
  ...
  冲突惩罚 -1.000 × 权重 0.250 = -0.250
  总分 0.329          ← 末行取 explain，是加分前的值
```

实测 14 卡语料、查询「Redis 缓存」，焦点包 5 张里 **3 张如此**，
差额恰好等于 boost（`0.1200`）。这比「少一行」更糟：少一行是漏了，
**两行矛盾是自相矛盾**，读者只会认为系统算错了。FR-B4「可解释」的判据是
能回答「为什么想起这条」，而这里给出的答案是错的。

修法：在 `mergeSpread` 的 `on` 分支给每张被加分的卡补一行
「扩散加分」，并把末行总分换成**加过分之后**的值（`patchExplainForSpread`）。
补一行而不是重算整个 `explain`，因为重算要把 `goalApplied` /
`conflictCapped` 这些上下文一起搬过来，等于复制一份打分逻辑；而扩散加分
本来就不是这张卡自身的属性（见 `applySpread`：它不参与归一化）。

顺带补上了用户真正要看的东西：**「因为想起了哪张卡」**。
原先即使补上「扩散加分 +0.120」，读者只知道「高了 0.12」却不知道为什么，
突触效果在观感上仍是莫名加分。现在这一行是：

```text
扩散加分 +0.120 × 权重 1.000 = +0.120，因为想起了：方案是用 Redis 做缓存，结论已定 / 2023-11-15：14 条记忆…
```

这才是「类似神经的突触效果」的可感知形态——**能说出「因为想起 A，所以想起 B」**，
而不只是排名悄悄变了。来源卡文本长度由 `spread.explainSourceChars` 控制
（默认 24 字，设为 0 退回只报数量），不写死字面量。

三条边界必须同时成立，缺一条这个功能就会从「有用」变成「有害」：

| 边界 | 为什么 | 守它的测试 |
|---|---|---|
| 末行总分 == `score.total` | 两行矛盾比缺一行更误导 | 「末行总分必须等于 score.total」 |
| `on` 模式必须**有**这一行 | 只改分不解释 = 莫名加分 | 「explain 必须有一行说明扩散加分」 |
| `shadow` 模式必须**没有**这一行 | 它没生效，写了就是撒谎 | 「影子模式不得出现「扩散加分」行」 |

还有第四条，是这次最容易漏的：**这段解释只能进人读渲染，绝不能进注入上下文**。
`explain` 的唯一消费方是 `renderFocusPackExplain`；注入路径 `renderFocusPack`
只读 `formatCardLine`，不读 `explain`。起源 L17（无编号·上下文污染）要求
注入文本里不能有这类解释——它是给人看的，对模型毫无用处，还会烧 token 预算。
实测 4 个查询、注入文本 452~1949 字，`扩散` / `因为想起了` / `关联卡` /
`权重 1.000` 全部无泄漏；同时人读渲染确实含「因为想起了」，证明两条路径
真的分开了（只测「注入没有」的话，把解释整个删掉也能让测试变绿）。

> 这次反向验证里我**先选错了变异层次**：把 `explain` 拼进 `buildFocusPack`
> 里的 `line` 变量，结果 `fail=0`。原因不是测试弱，而是那个 `line` 只用于
> **估算 token**，真正输出注入文本的是 `renderFocusPack` 里的
> `formatCardLine`。改到正确的层次后两个变异都精确命中。
> 与 AGENTS.md §五「断言选错层次时，反向验证不会变红」是同一条教训，
> 只是这次错在**变异**而不是断言上。

#### 真缺陷八：影子模式照搬 `spreadBoost`，同一张卡带两个真相源

补 `ScoredCard` 的类型声明时顺手加了一条测试，它**当场就红了**——
不是我写错了断言，是它抓到了一个一直存在、但没人看得见的问题。

`applySpread` 会给**每一张**卡都挂上 `spreadBoost` / `spreadSources`
（没加分的挂 `0` / `[]`）。`attachShadow` 直接展开 `...item` 来复原原总分，
于是这两个字段被原样带进了影子模式的结果里。后果：

| 消费方读到 | 会以为什么 | 实际是 |
|---|---|---|
| `item.spreadBoost` | 加分**已经生效** | 影子模式不改变任何排序与注入 |
| `item.spreadBoost` vs `shadowSpread.boost` | 两个值该信哪个 | 一个是原始值、一个是 clamp 后的假设值，**可能不同** |

这跟 `ShadowSpread` 自己的文档是直接冲突的——那里写着「让『实际生效』和
『假设生效』在类型层面就是两件事」。**光在注释里写不算，必须在数据里真的分开。**

为什么长期没被发现：`spreadBoost` 此前**没在 `ScoredCard` 上声明**，
类型层面谁都读不到它，也就没有消费方会读到错的值。也就是说，
「类型没声明」这个缺陷**顺手把下一个缺陷挡住了**——而挡的方式是让功能
不可用，不是让功能正确。补上声明后，第二个缺陷立刻暴露。

修法：`attachShadow` 里用解构把这两个字段**摘掉**再返回：

```ts
const { spreadBoost, spreadSources, ...rest } = item
const restored: ScoredCard = { ...rest, score: { ...rest.score, total: base } }
```

不用赋 `undefined`：`exactOptionalPropertyTypes` 下「有键但值为 undefined」和
「没有这个键」是两件事，赋 `undefined` 会留下真实存在的键
（`'spreadBoost' in item === true`），那是另一种泄漏。

三条推论：

1. **补类型声明会顺带暴露运行时缺陷。** 类型不是文档，是**接口**——
   没有接口的字段等于没有出口，而「没有出口」会掩盖「出口输出的是错东西」。
2. **`...item` 展开是双刃剑**：它让新字段自动流到下游（方便），也让不该流
   的字段一起流过去（危险）。跨语义边界（实际生效 → 假设生效）展开时，
   必须显式摘掉对面语义的字段。
3. **反向验证的期望值必须是「用例名」，不是「断言文案」。** 这条我这次
   又踩了一次：把 `expect` 填成 `'不得记 spreadBoost'`（那是 `assert` 的
   message），而脚本匹配的是 `✖ <用例名>`，于是两个都命中的变异被报成
   「未命中」。**期望值选错层次时，反向验证会给出与事实相反的报告。**

#### 真缺陷九：CLI 写死默认配置，终端与会话报出两套分数

**这是同一类「两个真相源」的第三次发作**，只是这次在配置层。

| | 配置来源 | `spread.mode` | 结果 |
|---|---|---|---|
| 宿主 | `resolveConfig` 读 `cordis.patch.yml` | `'on'` | 扩散参与排序 |
| CLI | `const CLI_CONFIG = DEFAULT_CONFIG`（写死） | `'shadow'` | 扩散只算不改 |

同一个库、同一个查询，实测 **3/3 查询分数全部不一致**：

```text
Redis 缓存        宿主 0.5328,0.5313,0.5155,0.4155
                  CLI  0.5313,0.5155,0.4128,0.2955
Cordis 版本       宿主 0.5155,0.4569,0.4376,0.4257,0.4257
                  CLI  0.5155,0.4569,0.3176,0.3057,0.3057
PostgreSQL 索引   宿主 0.5155,0.4724,0.4155
                  CLI  0.5155,0.4724,0.2955
```

而且 CLI 输出里**从来没有「扩散加分」**——运维在终端看到的不是模型看到的。

**为什么这比「CLI 坏了」更严重**：CLI 的全部意义是「让我看看记忆库现在是什么样」。
一个报错的观测点比没有观测点更危险，因为人会信它。`health` 曾经只报
「活跃 N 张 / 图谱边 M 条」，恰好让人以为一切正常。

修法（三层）：

1. **共享解析器** `src/host/patchConfig.ts`：零依赖手写 YAML 子集解析。
   放 host 层是因为「读宿主配置文件」属于适配面；`core/` 必须无 IO。
   CLI 已经 import `host/engine.ts`，依赖方向不变。
2. **CLI 改走同一份配置**：`resolveCliConfig(io)` 读 patch → `mergeConfig`
   → `validateConfig`，并**把配置来源作为可报告的事实**返回。
   `health` 增加 `配置来源` / `扩散模式` 两行，`--verbose` 在 stderr 报
   `配置来源：... （spread.mode = on）`。
3. **不静默降级**：读不到 patch 或配置非法时，退回 `DEFAULT_CONFIG` 但
   **必须在 stderr 报「配置提醒」**。静默退回正是这个缺陷本身。

**修的时候顺带查出第二个真缺陷：`migrateSpreadMode` 静默吞掉非法值。**

`src/core/config.ts` 的 `migrateSpreadMode` 原本在「用户写了 `mode` 但不合法」时
退回 `fallback`。而 YAML 1.1 里无引号的 `on` 是**布尔值**，用户在 patch 里写
`mode: on`（极自然的写法）时宿主拿到 `true`，于是：

```text
mergeConfig 后 spread.mode = "shadow"     ← 静默降级
validateConfig.ok = true                  ← 校验层也放过
```

**不报错、不崩溃、测试全绿**，用户以为打开了扩散，实际跑的是影子模式。
这比加载期崩溃更坏：崩溃会让人立刻改，降级会让人一直以为自己开了。

我在 `patchConfig.ts` 的注释里一开始写的是「宿主拿到 true 会加载期失败」——
**这句是没验过的猜测**，探测脚本 `.tmp/probe-bare-on.ts` 一跑就推翻了。
现在改为：非法 `mode` **原样透传**给校验层，由 `validateConfig` 报
「spread.mode 必须是 'off' / 'shadow' / 'on' 之一，实际为 true」。
透传时用 `as SpreadMode` 是**故意的**——这一层的职责是把用户输入送到校验层，
不是替校验层做决定。

四条推论：

1. **「读同一份状态」不等于「用同一份参数」。** 两个进程读同一个库，
   只要各自持有不同的配置副本，结果就会分叉。多入口系统必须问：
   「这几个入口的参数分别从哪来？」
2. **运维工具必须能自证它用的是哪份配置。** 只报结果不报来源，
   分歧就永远无法被发现。`health` 现在同时报 `配置来源` 和 `扩散模式`。
3. **静默降级比崩溃更坏。** 崩溃是显式的、会被修的；降级是隐式的、
   会被当成「功能就是这样」。任何 `catch`/fallback 分支都必须留下痕迹。
4. **注释里的事实性断言也要验。** 我把「裸 on 会让宿主加载失败」写进注释时
   并没有验过，实测结果恰好相反。**没验过的话写进注释，就是给下一个人
   留一个错误的锚点**——而注释比代码更容易被信任。

### A. 扩散激活（`src/core/spread.ts`）

- **按种子独立 BFS，不是逐跳迭代**。逐跳迭代（第 1 跳用上轮结果、第 2 跳再
  用第 1 跳结果）会让结果依赖遍历顺序；独立 BFS 让每个种子的贡献可以独立算出
  再线性相加，结果与种子/边的顺序无关（ST-1）。
- **种子与边都显式排序**。浮点加法不满足结合律，`(a+b)+c ≠ (a+b)+(c)`；
  要让「同一个库在两台机器上重放得到同样分数」成立，加法顺序必须固定。
- **种子门槛是「本轮最高分 × `seedRatio`」，不是绝对阈值**。见下节，
  这里曾经有一个让整个机制恒为空集的真缺陷。

护栏（全部在 `src/core/config.ts` 的 `spread` 段，不写死）：

| 参数 | 默认 | 为什么不能是别的值 |
|---|---|---|
| `seedRatio` | `0.85` | 必须落在开区间 `(0,1)`。`≥1` 没有卡够格当种子（无激活源），`≤0` 所有卡都是种子（无受益者），**两种情况扩散都恒为空集且看不出异常** |
| `minSelfScoreRatio` | `1` | `< 1` 会让不达标的卡靠邻居混进焦点包，`absoluteThreshold` 退化成「只约束没有邻居的卡」。**注意它乘的 `absoluteThreshold` 与护栏比的自身分必须同尺**：缺陷二十六之后两者都是 `relevance`；错配一次，这条护栏就恒真（它已经错过两次） |
| `hopDecay` | `0.5` | `= 1` 会让扩散退化成「点亮整个连通分量」，与起源 L29（第 5 条·专注当前位置）冲突 |
| `maxHops` | `2` | `hopDecay^3` 已经是噪声；再远就不是「关联」而是「全库」 |
| `maxBoost` | `0.12` | 上限必须存在，否则连接多的卡能压过内容真正匹配的卡 |
| `maxAffected` | `5` | 限制受影响面，防止一次召回把半个库的排序都动了 |
| `distillBidirectional` | `true` | 见下 |

**`distills` 允许反向遍历，其余关系一律单向。** 起源 L11 说细节会忘、只留感受，
那么想起细节就该能唤起感受；严格有向做不到这件事。`supersedes` **明确排除**——
沿它扩散会把被取代的内容推回前面，与 FR-A5 相反。`causes` / `part-of` /
`contrasts` 排除，因为它们当前无产出点（见 `src/core/types.ts` 的预留说明）。

### B. 可塑性：已实现但**未接线**，且打开会被拒绝

`reinforceEdges` / `decayEdges` / `prunableEdges` 已实现且通过测试，但
**没有任何生产代码调用它们**。真实运行中边权从不变化。

**现在的行为是「写 `true` 加载期失败」，不是「写 `true` 静默空转」。**
`validateConfig` 强制 `spread.plasticityEnabled === false`（缺陷三十三）。
理由：配置项的名字就是承诺，用户写 `true` 是想要「一起被用到的连接变强」，
实际却什么都不发生——**这比报错更坏，因为它让人以为突触学习已经生效，
从而永远不去查它从未生效**。

原因是驱动信号缺失：可塑性的依据是「共激活」（这两张卡被一起用上了），
而仓库里唯一能提供该信号的入口 `Engine.confirmRecall` **零调用方**
（原因见 `docs/7-缺陷复盘.md`：确认信号必须来自「这条记忆真的影响了输出」的可审计
证据，而非「被展示过」）。

已否决的五个替代信号（写在这里是因为它们看起来都很合理，会有人再提一次。
**按隐蔽程度排序，越靠后越危险**——前三个读代码就能看穿，第五个不能）：

1. **把「被一起召回」当共激活**——召回是「看见」不是「使用」。用它驱动强化，
   等于「一起被展示过的记忆互相加固」，焦点包会逐渐自我固化，正是 L29 要抑制的。
2. **把「夜整理时同批处理」当共激活**——同批只是「同一天」。日摘要会批量处理
   几百张卡，一晚上能把整个图谱拉满权重。
3. **把「上轮焦点包与本轮重叠」当共激活**——会让 recall 变成有状态的，
   「看见」间接影响「看见」，同一段对话里越看越强，同样违反 L29。
4. **把「扩散传播过这条边」当共激活**——这是最像的一个，但它是正反馈闭环：
   边权大 ⇒ 传得多 ⇒ 边权更大。而扩散的种子本身来自打分，等于让「排得前」
   反过来加固「为什么排得前」，同样违反 L29 的抑制语义。
5. **把「同一轮对话里抽出的多张卡」当共激活**——**最隐蔽的一个**，必须单独说，
   因为接线代码看起来完全干净，而且它是唯一一个「数据完全拿得到、密度也健康」
   却被否决的候选。详见下一节。

#### 第五个候选为什么也被否决：它看起来干净，但 100% 依赖助手通道

这是目前为止**唯一一个数据完全拿得到、密度也健康**的候选，所以必须把它
被否决的理由写清楚——否则下一个人会认为前面几个是因为「拿不到数据」才放弃的。

**候选内容**：一轮对话里被抽取出来的多张卡，是「同一次思考里同时浮现的概念」，
符合赫布学习（Hebbian learning）「一起激发的神经元连在一起」的原意。

**它表面上为什么干净**：写入用的是 `readTurnText()` 的对话原文，不是
`renderFocusPack()` 的输出。所以「这轮说了 A 和 B」≠「这轮注入了 A 和 B」，
这个区分在代码里是**真的**。接线只需要一行：

```ts
const ids = new Set(summary.cards.map((c) => c.id))
const next = reinforceEdges(store.allEdges(), ids, config)
```

变量名是 `cards`，来源是 `writeTurn` 的返回值（`src/host/engine.ts:202-207`），
文本是对话原文。**这一行里没有任何「召回」的痕迹。**

**但它违反起源 L29（第 5 条·专注当前位置），走的是间接闭环**，链路三段：

1. 焦点包在本轮助手生成**之前**注入：`CONTEXT_ORDER = 300` 的动态上下文
   （`src/index.ts:431`），查询文本是本轮用户原话。
2. 助手回复会被抽取成卡：`config.extraction.includeAssistant = true`
   （`src/core/config.ts`），`minAssistantChars = 40`。
3. 于是「同轮配对」把**召回结果和召回结果自己**配成一对。

**决定性实测**（`.tmp/probe-turn-variants.mjs`，3 天 36 轮真实中文语料，
52 卡 / 61 边）：真正会被 `reinforceEdges` 改动的已连边对（5 对）中，
**助手侧参与的占 100%**。把 `includeAssistant` 设为 `false` 重跑同一份语料，
该口径从 5 对**精确归零**。

也就是说：**这个信号在结构上完全依赖助手通道**，而助手通道的输入文本是被
焦点包条件化过的。它和候选 3「上轮焦点包与本轮重叠」是同一个东西，
只是多洗了一层——3 是「把上次注入的包拿来比」，一眼可见；5 是
「注入 → 模型自己说出来 → 再抽回来」，数据面上只剩两段看起来无关的原文。

**而且它是复合的，不是一次性的**（`.tmp/probe-turn-nesting.mjs`）：焦点包渲染
每行带 `- [事实] ` 前缀，被复述后抽取成卡就带上前缀，下一轮再被召回、复述、
抽取，前缀层层叠加。实测 46 → 90 次出卡，夜整理后边数 **61 → 172**，
最大嵌套深度 **5**，且 41 条边（23.8%）挂在嵌套卡上、**全部是
`supersedes@1.00`**——污染甚至伪造出了最高权重的取代关系。
而这条数据在数据层**完全自洽**：权重满格、关系合法、日志正常。

**它唯一的优点必须如实记下：密度是健康的。** 实际效果面 **1.67 对/夜**，
比「夜整理同批」（61 边/夜、覆盖 100% 的边）低 **36.6 倍**；3 夜只触及
8.2% 的边；轮内边界成立（`buildCardId` 含 `source.turn`，跨轮重复的卡为 0）。
**所以密度不是问题，问题全在合法性。**

**两个窄化变体都不成立**：

- **两侧都是用户侧**（`source.eventType === 'user/message'`）：L29 上干净
  （用户原话产生于注入之前），但真实混合语料实测 **0.00 对/夜**
  （`.tmp/probe-turn-clean-density.mjs`，30 轮 / 7 个多句轮 / 22 卡 / 32 边）。
  接线后 `reinforceEdges` 一年也动不了几条边——**这正是缺陷三十三的形态：
  开关打开、代码执行、什么也没发生，而且不报错。**
- **只取 `distills` 边**：**结构上恒为空**。`distillSource` 把感受卡的
  `source.turn` 写死为 `0`、`sessionId` 写死为 `'distill'`，而来源卡是真实轮次，
  两者永远不可能同轮（实测 6 条 `distills` 边，两端 `source.turn` 相同且非 0 的
  **0 / 6**）。

**额外发现：这个信号是「同一份证据数了两遍」。** 5 对命中里 2 对两端共享实体，
而 `same-entity` 边权的定义本身就是「共享实体数 / 实体并集」，强化它等于把
同一个量再乘一遍。且同轮对边权均值 **0.192**，反而**低于**同天跨轮对的
**0.410**（秩相关 rho = −0.058）——它挑出的不是「更该强的边」，是
「碰巧在同一轮被说到的边」。

**这条候选教的东西**：一个信号「数据拿得到、密度健康、代码干净」，
仍然可能在语义上是错的。前四个候选的否决理由都是「拿不到」或「一眼可见的
正反馈」，容易被记成「等有数据了再说」；这一个必须记成
**「有数据也不能用，因为它测的不是使用，是复述」**。

（诚实边界：助手侧对焦点包的依赖是**模拟**的——探针把
`engine.peek()` 的输出直接拼进助手回复，这是最坏情况。真实模型会改写而非
逐字引用，嵌套深度的增长会显著减弱。另外「动态上下文先于生成注入」依据的是
宿主契约，未在真实宿主上观测时序。）

#### 为什么「先接线再说」也不成立：默认参数在数学上分不出使用频率

即使忽略信号合法性、硬把扩散当共激活接上去，**默认参数也会让可塑性退化成
「全部拉满」**。这不是接线问题，是强化与衰减的**量纲失配**：

```text
衰减是乘性的：每夜 w ← w × 0.98        （−2%）
强化是加性的：每次 w ← w + 0.05        （相当于 +5%）
```

教科书的连续推导会给出不动点 `w* = n × delta × factor / (1 − factor)`，
但**这个式子与实测严重不符**——真实的量化映射产生的是一个「不动点带」，
不是一个点：

```text
带的中心 = n · delta · f / (1 − f)
带的宽度 = 1 / (100 · (1 − f))
```

（`delta=0.01, f=0.98, n=2`：理论 0.98，实测 0.74，差 24 个百分点；
且同一 `n` 在不同初值下有 25 个不同终值——**`w*(n)` 根本不是良定义的函数**。
更正记录见 `docs/7-缺陷复盘.md` 缺陷三十三第二层。）

代入**修复前**的默认值 `delta=0.05, factor=0.98`：带中心 `= n × 2.45`。
**n = 1 就已经超过上限 1.0** ——也就是说「每夜被一起用一次」和「每夜被一起用
一百次」最终都是同一个值。离线仿真实测（`.tmp/probe-grid.mjs` /
`.tmp/probe-calibration.mjs`）：

| delta | factor | n=1 | n=2 | n=5 | n=10 | 能分出的档数 |
|---|---|---|---|---|---|---|
| **0.05** | **0.98**（修复前的默认） | 0.98 | 0.98 | 0.98 | 0.98 | **1** |
| 0.02 | 0.98 | 0.74 | 0.98 | 0.98 | 0.98 | 2 |
| **0.01** | **0.98**（**当前默认**） | 0.50 | 0.74 | 0.98 | 0.98 | 3 |
| 0.01 | 0.95 | 0.28 | 0.48 | 0.86 | 0.95 | 4 |
| 0.01 | 0.90 | 0.14 | 0.23 | 0.50 | 0.86 | 4 |

**修复前的默认值恰好是全场最坏的一组。** 一个携带不了「用得多还是少」的边权，
接上去也只是把图谱变成「全部等强」——它比不接线更糟，因为看起来在工作。

当前默认已改为 `delta=0.01`（`configVersion 14`），并且 `validateConfig` 现在
**强制** `w*(n=1) < maxEdgeWeight`：写一个「一次共激活就撞顶」的值会加载期失败。
这让「机制分不出使用频率」从「只能靠人看出来」变成「不可能悄悄发生」。
但它只是**必要条件**——0.01 只能分出 3 档，要分辨 `n=1..10` 仍需换强化模型。

这不只是「默认值选得不好」，而是**加性强化模型本身的分辨率上限**。
相邻档的中心差是 `Δw* = delta · f / (1 − f)`，要跨过量化格需
`delta > 0.01 / f`；要不撞顶需 `delta < (1 − f) / (N · f)`。两式联立得

```text
N < (1 − f) / 0.01
```

**这个界经过全参数空间实测验证**（`.tmp/probe-max-tiers.mjs`，
扫遍 `f ∈ [0.850, 0.999]` 与所有合法 `delta` 格点）：

| f | 半衰期 | 实测最大档数 | 理论界 `(1−f)/0.01` |
|---|---|---|---|
| 0.99 | 69.0 夜 | **2** | 1.00 |
| 0.98 | 34.3 夜 | **3** | 2.00 |
| 0.97 | 22.8 夜 | 4 | 3.00 |
| 0.95 | 13.5 夜 | 6 | 5.00 |
| 0.93 | 9.6 夜 | 8 | 7.00 |
| **0.914** | **7.7 夜** | **10** | 8.60 |

**反查**：要 10 档 → `f ≤ 0.914`（半衰期 7.7 夜）；要 6 档 → `f ≤ 0.954`
（14.7 夜）；要 4 档 → `f ≤ 0.974`（26.3 夜）。

也就是说：**在「加性强化 + 0.01 量化格 + 每夜若干次共激活」这个组合下，
无论 delta 取什么值，机制都分不出使用频率。** 要分辨 10 档，边权必须在
**7.7 夜**内衰减一半——与「图谱是长期记忆」的定位直接冲突。
这是模型分辨率的问题，不是标定问题——所以不能靠「等真实数据再调参」绕过。

（**饱和式也不是出路**。把加性改成 `w ← w + delta × (cap − w)`，
实测 `f=0.95` 时 `delta` 从 0.02 扫到 0.30，**档数恒为 5**，
对 `delta` 完全不敏感——它被量化格与衰减步长的耦合卡住，
而不是被 `delta` 卡住。见 `docs/7-缺陷复盘.md` 缺陷三十三第二层。）

**还有一层比档数更根本的冲突**：`delta` 的默认值 `0.01` 与 `nextDecayedWeight`
的线性地板步长 `0.01` **精确相等**，于是「强化一次 + 衰减一次」的净变化为零：

```text
w=0.10 → 强化 0.11 → quantize(0.11×0.98)=0.11 不小于 0.11
       → 走地板 0.11−0.01=0.10   ← 回到原值
```

实测默认参数下 101 个格点里 **75 个净变化为零、0 个上升**，只有 `w ≥ 0.75`
的 26 个会下降。即**「每夜用一次」与「完全不用」在前 75 个格点上无法区分**。
`makeEdge` 的初始权重来自相似度（常见 0.1~0.3，正落在地板区间），所以
**新建边若每夜只共激活一次，权重永不增长**。

而 `delta=0.01` 恰好是档数最大化的唯一选择 ⇒ **「分辨率最高」与「一次使用有效」
互相排斥**：取 0.02 抵消消失，但档数界 `(1−f)/delta` 立刻从 3 降到 2。
真正要解耦的是 `delta` 与地板步长，不是「精度取多少」。见 `docs/7` 缺陷三十三
第四层与 `docs/8` 事实 6。）

**完整的数学题面与六个待裁决问题见
[`docs/8-可塑性数学不可行性题面.md`](8-可塑性数学不可行性题面.md)。**

因此本层的状态是：**扩散已生效；可塑性未接线，且打开会报错。**

**有一条端到端测试证明 `recall` 不改动任何边权**（`tests/host/engine.test.ts`
的「recall 不得改动图谱边权」）。这条测试在反向验证时先发现「改了实现也不红」，
追下去查出 `store.putEdge` 的幂等键缺陷（见下），修复后才真正变红。

#### 可塑性未接线，会不会让扩散变成「只重排不换人」？

会，而且**真的变成了那样两次**，两次的观测值一模一样。

**第一次（缺陷二十六的连带）**：绝对闸从 `total` 挪到 `relevance` 之后，
扩散只改 `total`，于是实测 12 张卡拿到扩散加分、**0 张因此进焦点包**——
扩散退化成纯重排序。这次靠「相对闸留在 `total`」解决了：扩散加分直接进
`total`，天然能改变成员。我一度加的「被扩散推动的卡豁免相对闸」补丁
**已删除**——少一个未测分支比多一个「看起来更安全」的分支好。

**第二次（缺陷三十二，更隐蔽）**：种子判据拿 `total` 算相对门槛，
而加分护栏拿 `relevance`。`total` 有 0.48 的权重与查询无关，相对离散度
被压平到 0.91~0.97，`seedRatio = 0.85` 落在其下 ⇒ **所有卡都是种子**
⇒ 受益者恒为空 ⇒ 扩散恒空。`off` / `shadow` / `on` 三种模式总分**逐位相同**。

| 闸 | 缺陷二十六之前 | 缺陷三十二之前 | 现在 |
|---|---|---|---|
| 种子筛选 | `total >= absoluteThreshold` | `total >= maxTotal × seedRatio` | `relevance >= maxRelevance × seedRatio` |
| 加分护栏 | `total >= absoluteThreshold × ratio` | `relevance >= absoluteThreshold × ratio` | 同左（未变） |
| 能量（撒多少） | `total` | `total` | `total`（刻意保留） |

判据统一到 `relevance`，能量仍用 `total`——**两个用途不同，用不同的量是刻意的**。
判据问「够不够格当种子」，能量问「能撒多少」，混用才会出错。

**这条边界要一直盯着**：只要可塑性仍未接线、边权不变，扩散对成员的影响
完全来自「`total` 上的加分能否越过相对闸」。相对闸一旦再换尺子，
这条路径会重新失效，而失效方式仍然是**静默的**（不报错、日志正常）。

**同一个参数有多个用途时，只看一个会得出相反结论。** 缺陷二十六只复查了
护栏那一半，种子这一半漏了；而漏掉的那一半失效方式是「全放行」，
它比「多放行」更难发现——**因为什么都不发生看起来最像正常工作。**

### 实现过程中查出的真缺陷一：扩散在数学上恒为空

种子判据原本是 `total >= absoluteThreshold`（0.18），而加分护栏是
`selfScore >= absoluteThreshold * minSelfScoreRatio`，且 `minSelfScoreRatio`
被校验强制 `≥ 1`。两个门槛恰好相等，于是：

```text
能加分的卡一定已经是种子 → 而种子不因扩散加分 → boost 恒为空集
```

更严重的是当时 31 条单测全绿。原因是它们全部直接测 `spreadActivation` 这个
纯函数、自己构造种子数组，**从来没有经过「谁当种子」这一步**；唯一那条声称
「扩散能把卡推进焦点包」的用例写的是 `assert.ok(bAfter >= bBefore)`——等式
成立也算通过，而当时 `bAfter === bBefore`，所以它一直绿着却从没守过任何东西。

根因不是编码错误，是**参数结构错了**：用同一个阈值既挑种子又当护栏，等于要求
「被扩散提权的卡必须本来就该被提权」，那扩散就没有存在意义。

**第一次修复也失败了**：改成 `seedRatio = 1.5`（门槛 `0.18 × 1.5 = 0.27`），
实测仍然恒空。原因是打分有**基础分下限**——完全不相关的两句话也有 0.33 左右
（importance / recency / confidence 各贡献一份），0.18 永远拦不住任何卡。
实测 12 个样本最低 0.3295，无一低于 0.18。所以任何
「`absoluteThreshold` × 倍数」的标定都会落在所有卡之下。

**正解是相对量**：门槛 = 本轮候选池最高分 × `seedRatio`。它无量纲，自动跟随
本轮分数分布；它衡量的不是「这张卡够不够格」，而是「这张卡在本轮里够不够强」
——那才是「值得把自己的激活撒出去」的判据。实测修复后：`b` 0.4807 → 0.6007、
`c` 0.3295 → 0.4495，种子 `a` 不变；影子模式产出 3 条观察值而总分逐位相同。

**这条缺陷的教训是**：两个门槛相等 ⇒ 机制恒为空，而全绿的测试可能一条都没守。
判据之间是否**互相抵消**，比单个判据对不对更重要。

> **缺陷二十六之后补记**：上面「`c` 0.3295 → 0.4495」这个数字**现在不再成立**，
> 而且它不再成立是**正确的**。`c` 那张卡是「无关的做饭记录」，`relevance = 0`；
> 护栏的尺子从 `total` 换成 `relevance` 之后，它就不该再拿到扩散加分了。
> 旧的护栏之所以放它过去，正是因为 `total` 有 0.48 权重与查询无关，
> 一张无关卡也能拿 0.3295——**那个「扩散有效」的证据里，有一半是噪声**。
> 现在那条测试同时断言「相关卡 `b` 严格上升」和「无关卡 `c` 完全不变」，
> 两个方向都守住了。

### 实现过程中查出的真缺陷二：`putEdge` 静默丢弃边权更新

`deriveIdempotencyKey` 的 `edge` 分支原来只取 `op.edge.id`，**不含权重**。
于是用同一个 id 改边权时，幂等键与上次完全相同，数据面判重复而**静默丢弃**，
读回来还是旧值。探针实测：写 `0.33`，同 id 再写 `0.38`，读回 `0.33`。

长期没被发现的原因是：`edge` 的产出点只有夜整理，而夜整理只**新建**边、
从不修改已存在的边（`knownEdgeIds` 过滤），所以「幂等键不含权重」在当时的
调用模式下永远正确。直到可塑性需要改边权，这个前提才失效。

**这条缺陷说明一件事**：一个幂等键正确与否，取决于「谁会写它」，
而不取决于键本身长什么样。改键之前必须先问「将来会不会有人用同一 id 写不同内容」。

### 实现过程中查出的真缺陷三：对称边被当成有向边，扩散效果一半靠运气

`same-entity` / `same-topic` 在语义上**对称**：A 与 B 共享实体 ⇔ B 与 A 共享实体。
但 `graph.ts` 建边时必须写一个具体方向，那个方向来自 `pool` 的排序
（「创建时间 + id」），**与「谁是本轮种子」毫无关系**。
而 `canTraverse` 原先只对 `distills` 开放反向，对称关系被当成严格单向。

后果：激活有一半概率传不出去，**取决于建边时谁排在前面**。

实测（20 轮真实感语料 / 21 张卡 / 10 条 `same-entity` 边）：

| 场景 | 结果 |
|---|---|
| 查询「PostgreSQL」 | 唯一种子是**日摘要卡**（它含全部关键词，分数最高） |
| 4 条相关边方向 | 全是「普通卡 → 摘要卡」 |
| 正向传播 | **0 条**（摘要卡没有出边，激活出不去） |
| 把同样这些边反向 | **4 条** |
| 21 个查询整体 | 修复前 4 个生效 → 修复后 6 个 |

这个缺陷的形态值得记住：**机制是对的，方向是随机的，于是效果一半靠运气。**
它不报错、不崩溃，日志里只写「本次无扩散」，看的人无从判断是「数据确实没有
关联」还是「方向恰好反了」。而「一半靠运气」的机制比「完全不工作」更难发现
——完全不工作时有人会去查，时灵时不灵时人会以为是自己查询写得不好。

修法是按**关系语义**决定方向，而不是按建边时恰好写下的方向：

| 关系 | 正向 | 反向 | 理由 |
|---|---|---|---|
| `same-entity` / `same-topic` | 走 | **走** | 对称关系，交换主宾语义不变 |
| `distills` | 走 | 由 `distillBidirectional` 决定 | 「想起细节唤起感受」是刻意的例外 |
| `supersedes` | 不走 | 不走 | `isDiffusible` 已挡掉，避免把废弃内容推上台面 |
| `causes` / `part-of` / `contrasts` | 不走 | 不走 | 预留，无产出点 |

「哪些关系对称」这条知识收在 `isSymmetricRelation` 一个函数里，并有测试
遍历 `EDGE_RELATIONS` 校验分类完整——新增关系时必须**显式**决定它算不算对称，
而不是让它默认落进「单向」里静默出错。

### 实现过程中查出的真缺陷四：实体抽取认不出裸专有名词，图谱边几乎产不出来

`extractEntities` 原先只认四类：文件路径、URL、驼峰/下划线标识符、引号内专名。
中文对话里最常出现的项目名与技术名恰恰是**裸词**——`Cordis`、`Redis`、
`Vue3`、`Qt5`、`Vite`，一个都抽不出来。

实测（20 轮语料）：

| 专名 | 出现句数 | 被抽出句数 |
|---|---|---|
| `Cordis` | 8 | **0** |
| `Redis` | 3 | **0** |
| `Vue3` | 4 | **0** |
| `Qt5` | 3 | **0** |
| `Vite` | 1 | **0** |
| `PostgreSQL` | 4 | 4（含大小写混合，被驼峰规则误打误撞抽中） |

后果不是「少抽几个词」，而是**整条链路失效**：`same-entity` 边完全依赖实体
抽取 ⇒ 中文场景下图谱边本就稀疏 ⇒ 扩散激活没有边可走 ⇒ 「突触效果」在真实
数据上近乎不可见。这与缺陷一（方向随机）叠加，使 21 个查询里只有 4 个能生效。

修法：补第 5 类——首字母大写的拉丁词，配一份英文常用词排除表挡住纯英文句首的
`The` / `This` / `When`。定标实测（19 句带簇标签语料，判据是「共享实体 ⇒ 同主题」）：

| 判据 | 连对 | 误连 | 漏连 | 精确率 | 召回率 |
|---|---|---|---|---|---|
| 原四类 | 3 | 0 | 35 | 100% | **8%** |
| + 首字母大写（≥2 小写） | 32 | 3 | 6 | 91% | 84% |
| **+ 首字母大写（≥1 小写）** | **35** | **3** | **3** | **92%** | **92%** |

**精确率从 100% 降到 92% 是有意的交易**：100% 精确但只召回 8% 的判据，
在真实数据上等于不存在。图谱宁可多几条边，也不要一条边都没有——后者会让
「突触」这个能力永远不生效，而且看不出是缺陷。

不抽全大写缩写（`API` / `HTTP`）：实测加进去精确率反而从 92% 降到 89%，
召回率不涨。通用缩写在任何话题里都出现，没有区分力，抽出来只会乱连边。

修复后同一份探测脚本：扩散生效的查询 **4/21 → 20/21**。

剩下那 1 个（查询 `Qt5`）经查是**正确行为**，不是缺陷：该查询的 3 个种子恰好
就是全部 3 张含 `Qt5` 的卡，它们互相之间已有 w=1.000 的 `same-entity` 边，
但**种子不因扩散加分**、且没有其他邻居，所以 boost=0。
查询已经精确命中全部相关卡时，扩散没有可补充的内容——这正是它该有的表现。

### 实现过程中查出的真缺陷五：`same-topic` 边的阈值在中文 bigram 下不可达

这条**没有修**，因为实测证明「调阈值」是徒劳的，而换判据属于另一个功能点。
记在这里是为了防止下一个人重复调参。

`same-topic` 边的产出条件是 Jaccard 相似度落在
`[relatedSimilarity 0.45, duplicateSimilarity 0.86)`。而中文按 bigram 切分后，
两两相似度实测最高只有 **0.3125**，阈值 0.45 **永远达不到** ⇒ `same-topic` 恒为 0 条。
这与缺陷一「两个门槛相等 ⇒ 机制恒为空」是同一类问题的另一个形态：
**门槛与数据的可达区间没有交集**。

进一步定标（19 句、5 个主题簇、剔除标注错误后）说明调参也救不了：

| 阈值 | 簇内连上 | 簇间误连 | 精确率 |
|---|---|---|---|
| 0.15 | 5/38 | 3/133 | 63% |
| 0.28 | 1/38 | 0/133 | 100% |
| 0.31 | 1/38 | 0/133 | 100% |
| 0.45（现状） | 0/38 | 1/133 | 0% |

精确率 100% 的那一档只连上 1/38——**要精度就没有召回**。根因是
「字面相似度」本来就不是「语义同主题」的好代理：同一主题换种说法，bigram
重合度会骤降；而不同主题的两句话恰好都用「约定…注意…」句式时，重合度反而高。

对照实验：用**共享实体**判同主题，簇内连上 3、簇间误连 **0**，精确率 100%。
所以正确顺序是**先把实体抽取修好**（缺陷四），`same-topic` 是否还需要存在、
以及该用什么判据，留待有真实数据后再定。当前 `same-topic` 保持原样，
不调阈值——调了只会让「一条都没有」变成「连上一条且是运气」。

> **后续（已修，见 [`docs/7`](7-缺陷复盘.md) 缺陷二十二）**：上面的结论
> 「不调阈值」是对的，但当时只否定了「调值」，没有指出「判据的形态」也错了。
> 真正的问题有两层：
>
> 1. **作用域错了**：`relatedSimilarity`（0.45）是为**去重**标定的，衡量
>    「是不是在说同一件事」；连边要的是「有没有关系」，弱得多。
>    在 300 张真实中文卡上实测，相似度 99.9 分位只有 **0.275**——
>    0.45 落在分布的极尾，门槛与可达区间**根本没有交集**。
> 2. **形态错了**：绝对阈值让边数变成 O(n²) 的函数，随语料规模漂移，
>    违反 P8「耗时可控」。
>
> 修法是**换形态而不是调值**：拆出独立分区 `GraphPolicy`，改成
> k 近邻（`topicNeighbors`）+ 绝对下限（`topicFloor`）双判据。
> 边数上界变成 `n × K`，按构造封顶；同量级边数下精确率 57.5% vs
> 绝对阈值 50.7%，孤立卡 62 vs 143。
>
> 这段历史保留在此，因为它记录了一条**正确的否定**：当年「调阈值是徒劳的」
> 判断成立，只是「因此就不该动」的推论不成立——**判据的形态可以换**。

> 附带记一次**定标数据本身出错**：第一版统计得出「簇间最高相似度 1.000」，
> 看起来是判据失效。查下去发现是同一句话被我标成了两个不同主题（标注错误）。
> **定标之前先检查「最高分那一对是不是标注错了」**，否则会顺着错结论去改代码。

### 实现过程中查出的真缺陷六：`maxAffected` 截断退化成按 id 哈希取卡

起源依据：L15（无编号·图谱）「我需要一种建立记忆图谱的方法，且跨层次关联。」
需求归属：FR-G1「突触学习与图谱扩散」（`docs/1-需求规格.md` §7.7）。

`spreadActivation` 用**截平后**的 `boost` 当排序键，决定 `maxAffected`
淘汰谁：

```ts
const boost = Math.min(sp.maxBoost, raw)   // raw 被丢掉
results.sort((a, b) => {
  if (b.boost !== a.boost) return b.boost - a.boost  // 全撞在 maxBoost，恒等
  return a.id < b.id ? -1 : a.id > b.id ? 1 : 0      // 退化成按 id 哈希
})
return results.slice(0, sp.maxAffected)
```

只要被加分的卡多于 `maxAffected`，它们几乎必然**全部撞在 `maxBoost` 上**，
比较恒等，排序退化成按 `id` 升序 —— 而 `id` 是内容哈希，与相关性无关。
**「只保留最强的 N 张」实际是「按哈希取 N 张」。**

实测（20 张技术卡 + 6 张诱饵卡，查询 `Cordis 版本`）：14 张卡获得加分，
其中 11 张的 `raw` 完全相同（`0.272258`，同一批 `weight = 1.0` 的边一跳传出），
截平后全是 `0.12`，谁被留下完全由 id 决定。

这与缺陷一（对称边靠方向运气）是同一类：**机制在跑，但选择是随机的。**
两次都是「一半靠运气比完全不工作更难发现」—— 日志正常、测试全绿、分数在变，
只是变的方向由哈希决定。

**修法**：排序键改为 `raw 降序 → 自身分降序 → id 升序`。

- `raw`：截平前的真实传播能量，原先被丢弃。
- 自身分：`raw` 相同时优先留本身更相关的卡。
- `id`：最后兜底，保证 ST-1 确定性。

实测效果（15 个查询的 `off` / `on` 焦点包集合对比）：扩散新增的**诱饵**卡
`2 → 0`，新增的**相关**卡 `3 → 4`。污染消除，价值反而上升。

#### 顺带纠正一个差点写错的结论：`absoluteThreshold` 曾经有两个用途，现在只剩一个

第二排序键（自身分）的选择，来自对 `minSelfScoreRatio` 护栏的追查。

该护栏的判据原本是 `selfScore >= absoluteThreshold × minSelfScoreRatio`，
而 `minSelfScoreRatio` 被校验强制 `≥ 1`。当时**这条判据对所有卡恒成立**，
因为 `capConflictPenalty` 把 `absoluteThreshold` 当成了**分数地板**：
低于它的卡会被抬到恰好等于它。实测（直接改字段、并断言字段真的变了）：

| `absoluteThreshold` | 同一张卡的 `total` |
|---|---|
| 0.05 / 0.10 | 0.126386（未触及） |
| 0.18 | **0.180000** |
| 0.25 | **0.250000** |
| 0.30 | **0.300000** |

**现在这个封顶函数已经被删除（缺陷二十六）**，`absoluteThreshold` 只保留
一个用途：作为**绝对闸**的判据。它也不再比对 `total`，而是比对
`ScoreBreakdown.relevance`（只含 `semantic` + `goal` 的无量纲分量）。

于是护栏的尺子必须跟着换：`selfScores` 里装的是 `relevance`，护栏判据
`selfScore >= absoluteThreshold × minSelfScoreRatio` 才重新有意义。
**同一个护栏坏过两次，两次都是单位/语义错**——第一次是封顶把阈值当成了
分数地板，第二次是闸门换尺子后护栏还在用旧尺子。两次的表现都是「恒真」，
都不报错、不崩溃、日志正常。

这里记一次差点写进文档的错结论：只看「`applyThresholds` 的过滤」这一个用途时，
实测 11 张卡无一低于 0.18，我一度认定该参数「形同虚设」；读到
`capConflictPenalty`（`src/core/scoring.ts:258`）才发现它是**地板**，
两个方向都实测确认后才推翻前一个结论。**同一个参数有多个用途时，
只看一个会得出相反结论。**

#### 两道闸用两把不同的尺子（缺陷二十六的最终结论）

| 闸门 | 尺子 | 回答的问题 | 扩散能否影响 |
|---|---|---|---|
| `absoluteThreshold`（0.06） | `relevance` | 「这张卡和查询**有没有关系**」 | **不能**（扩散只改 `total`） |
| `relativeThreshold`（0.55） | `total` | 「比本轮最好的差多少」 | **能**（扩散直接抬高 `total`） |

**这不是「同一个判据写了两遍」。** 把它们统一成一把尺子（都看 `relevance`）
实测会误杀真相关卡：SC-2 场景的目标卡 `relevance = 0.1113`，相对闸
`0.1121`，**差 0.0008 被挡出包**；而同一张卡 `total = 0.3925`、相对闸
`0.2522`，本该轻松通过。根因是 `relevance` 的相对离散度比 `total` 大
（同批候选 0.546 vs 0.856），同一个 `relativeThreshold` 在 `relevance`
尺度上苛刻得多。

统一尺子的变体对照（161 张真实卡，19 个查询，含 5 个完全无关的）：

| 变体 | 进包 | 噪声 | 无关组进包 | 空包 |
|---|---|---|---|---|
| A 旧（abs@total, rel@total） | 67 | 0 | **4** | 4 |
| **B 现行（abs@relevance, rel@total）** | **61** | **0** | **0** | 5 |
| C 全挪（abs@relevance, rel@relevance 0.55） | 47 | 0 | 0 | 5 |

C 比 B 多丢 16 张，包括「幂等键必须包含边权」从 7 张降到 1 张，以及
`semantic = 0.130` 的真相关卡。**⇒ 选 B。**

**这道绝对闸是 FR-B2「全低分时不硬塞」的结构性保证**：因为
`relevance` 完全不含 `importance` / `recency` / `confidence`，
一张「无关但新鲜」的卡不可能靠新鲜度越过它。实测（161 张卡 × 19 个查询）
无关卡 `total` 区间 0.3131~0.3767、相关卡 0.3452~，重叠 33.3%——
**在 `total` 尺度上不可分**；换到 `relevance` 尺度，0.06 这个值
噪声 0、真相关卡损失 0。

正确的落点不是改判据，而是**在真正会淘汰卡的地方按自身分排队**：
`maxAffected` 名额有限时先淘汰自身更弱的，这才是那条护栏想表达的事。

#### 测试为什么长期没守住

原来那条 `maxAffected 限制受影响面` 只断言 `boosts.length === 2`，
**不管留下的是哪两张**。它对「排序键是否正确」没有任何约束力 ——
这正是缺陷能长期存在的原因：断言证明了「截断发生了」，
但没证明「按强弱截断」。

新增的 3 条测试都做了反向验证（三个变异各红 2 条，恢复后全绿）。
其中两条刻意让 **id 顺序与强弱顺序相反**：第一版写成一顺，
「按 id 排序」恰好也得到正确答案，反向验证时变异不红 ——
**那条测试绿在巧合上**。

第三条的注释曾经撒过谎，值得单独记：第一版写「边传入顺序不同也要相同结果」，
但 `buildAdjacency` 内部**已按 `edge.id` 排序**，反转边数组建出的邻接表
逐键逐边完全相同，该断言**永远绿**。最小复现证明变异后正序、逆序结果
都是 `q,p,t`，抓住变异的是最后那句 `deepEqual`。已改成直接断言
「留下 id 字典序最小三个」，并在注释里写明这次误判。
**注释声称的行为，必须有一条测试真的去验它** —— 否则注释会持续替实现撒谎。

### 测试分层：为什么必须有端到端

`tests/core/spread.test.ts` 测纯函数的数学性质（BFS 衰减、排序、护栏），
`tests/host/engine.test.ts` 测**真实链路**（写入 → 夜整理产边 → 召回）。

这个分层不是风格，是上面缺陷一的直接产物：**只测纯函数不等于测了链路**。
缺陷一在纯函数层完全正确，只在「谁当种子」这一步错，而那一步只有链路能走到。

## 8. 参数与版本

所有可调参数集中在 `src/core/config.ts`，带 `configVersion`（FR-F4）。
插件入口做**深合并**：宿主 patch 行是整块替换 config，不合并就会把默认值清空。

### 8.0 配置项的存在本身就是一种承诺

`docs/5-起源对照审查.md` 的死字段表里有两条被判定为「**配置在撒谎**」：
`recall.minCards` 与 `storage.reindexEveryRecords`——声明了、注释里承诺了、
校验里写了、默认值给了，**生产代码零读取**。

这与真缺陷十五（健康检查只看库自洽、不看插件能否加载）**同形**：
文档描述的是一个不存在的能力，而配置项存在本身会让人以为它生效了。
差别只是载体不同——一个是 CLI 输出，一个是配置文件。

两者的处置都是**删除**（`495781e`），理由不是「实现起来麻烦」，而是**实现它们会变坏**：

- `recall.minCards` 唯一可能的语义是「不足 N 条时放宽阈值凑数」。
  而 FR-B2（`docs/1-需求规格.md:135`）的验收要点就是「全低分时不硬塞」，
  FR-B6（`:140`）要求召回为空时「不得编造」并给出明确空信号。
  **实现它等于违反这两条 P0。** 更值得记的是原注释：「焦点包最少条数，
  低于此值不强行凑数」——这句话描述的恰好是**相反**的行为。
  一个字段的注释和它唯一可能的语义互相矛盾，说明它从来没人真正想过要它干什么。
- `storage.reindexEveryRecords` 语义是「日志新增条数达阈值后自动重建倒排索引」。
  但增量 `syncIndex` 已在每次 `append` 时维护索引，`open()` 会整库重放重建，
  夜整理也会重建（见 §8.0.1）。再按条数触发一次重建，**检测能力增量为零**，
  只是多一个能配错的旋钮。

**删除同样要递增 `configVersion`（9 → 10）**：旧 patch 里可能写着它们，
回滚快照里也可能有，`configVersion` 是「schema 变过」的唯一凭据。
`tests/core/config-summary.test.ts` 的绊线写死版本号，故意让
「改了默认配置却忘递增」变红。

### 8.0.1 夜整理报告里的 `reindexed` 曾经在报一个没发生的动作

`docs/1-需求规格.md:147`（FR-C1）把「重建索引」明确列进夜整理最小集。
而 `src/consolidate/nightly.ts` 写的是 `reindexed: afterActive`——
把活跃卡数换个名字打印了一遍，注释还配了一句「重建索引 = 为每张活跃卡重新登记」。

它看起来完全合理：数字不为 0、量纲也对，只有去读实现才知道索引一次都没重建。
**一个说错的观测点比没有观测点更危险，因为人会信它。**

修法是**分层**而不是硬填：`runConsolidation` 是纯函数（ST-1），
输入只有 `(state, config, now, timeZone)`，而倒排索引是数据面的派生视图（FR-A7），
**根本不在它的输入里**——它没有任何依据说「我重建了多少条索引」，只能填 0。
`MemoryEngine.consolidate()` 有 store，真的调 `store.rebuildIndex()` 并把返回的
`cards` 数写回来。纯函数层报 0、调用方回填，是唯一能同时保住
「纯函数无 IO」和「报告不说谎」的写法。

配 3 条测试，其中一条的判据值得单独记：**「`reindexed` 不许是活跃卡数的别名」
不能在没有归档卡的场景里断言**——那时两者天然相等，断言会绿在巧合上。
必须先归档一张卡（归档卡也登记进索引），把它变成**必然不等**，
判据才由规则决定而不是由巧合决定。**让测试由规则决定，不由巧合决定。**

### 8.1 一键回滚：快照台账 + 最小覆盖层（FR-F4 验收「改坏能一键回滚」）

`docs/1-需求规格.md:178`（FR-F4）的验收口径是**「改坏能一键回滚」**，设计原则 P7
（`docs/1-需求规格.md:71`）要求「阈值/权重/策略带版本，改动可追溯」。

**先说清旧状态**：此前 FR-F4 只有一个 `configVersion` 数字，以及 CLI 头注释里
一句「`rebuild` 是那条回滚路径」。**那句话是错的**：`rebuild` 重放的是记忆数据
（事件日志 → 投影层），**从不碰配置**。也就是说「改坏配置」当时**没有任何回滚
手段**——只能靠人手改回 patch，而他往往不知道自己刚改坏了哪一行。错误文案是
承诺不是装饰，所以那句话已在 `src/cli/memoryctl.ts` 头注释里被显式更正。

三个文件，三层职责，依赖方向与仓库一致：

| 层 | 文件 | 职责 |
|---|---|---|
| `core/`（纯函数，无 IO） | `src/core/configSnapshot.ts` | 摊平 / 确定性序列化 / 差异 / 最小覆盖 / 反序列化 |
| `store/`（数据面） | `src/store/configLedger.ts` | 台账读写：`config/snapshots.jsonl` + `config/rollback.json` |
| `host/`（接线） | `src/host/configRollback.ts` | 决策：算出该写什么、报出哪些回滚不了 |

#### 两个文件，两种语义，必须分开

| 文件 | 语义 | 写时机 | 可清除 |
|---|---|---|---|
| `config/snapshots.jsonl` | **追加**的历史事实：每次生效过的配置 | 启动成功后 / 任一 CLI 子命令后 | 否（按上限环形截断） |
| `config/rollback.json` | **当前**的回滚意图：最小覆盖层 | 用户执行 `config rollback <id>` | 是（`--clear`） |

合并成一个文件会出问题：历史是不可变的（P2 精神），而意图是可撤销的。
放在一起就得在「历史」里表达「这条已被撤销」，于是历史不再是历史。

#### 顺序不变量：整个机制的重点

```text
默认值 + patch（不校验） → 叠加回滚覆盖层 → 校验
```

**覆盖层必须在 `validateConfig` 之前叠加。** 反过来（先校验再叠加）意味着：
patch 一坏，`resolveConfig` 直接抛错，覆盖层永远没机会被应用 ⇒ 用户执行了回滚、
`config rollback` 报了成功、宿主下次启动**照样崩**。

这条不变量在实现时被真正踩过一次，且探针 `.tmp/probe-f4-e2e.ts` 第 5 步抓到了：
第一版把「回滚基准」取成了校验失败后**退回的 `DEFAULT_CONFIG`**，于是
`-5` 被当成「当前值」而目标快照也是 0.18，**差异恒为空** ⇒ 回滚什么都不写
⇒ patch 里的 `-5` 原封不动。命令行报「已回滚」，宿主仍然抛
`recall.absoluteThreshold 必须是 0..1 之间的有限数，实际为 -5`。

正解是把 `ResolvedCliConfig.baseline` 定义为**「默认值 + patch、未校验、不含
覆盖层」**的合并结果——回滚就是把它修成目标快照，坏掉的叶子自然出现在差异里。
**「当前值」必须是「假如没有覆盖层，宿主会拿到什么」，不是「校验失败后我们退回
的那个兜底值」。** 后者是被降级过的，拿它当基准等于拿一个谎言去算差异。

#### 自指环：`storage` 与 `configVersion` 不可回滚

`ROLLBACK_EXCLUDED_TOP_KEYS = ['storage', 'configVersion']`。

`rollback.json` 就住在 `dataDir` 里，而 `dataDir` 由 `storage.dataDir` 决定。
若允许回滚改 `storage`，就得到：**要先知道数据目录才能读覆盖层，而覆盖层决定
数据目录**。这个环不会报错——它会安静地读错目录、找不到覆盖层、当成「没有
覆盖层」，于是回滚静默失效。

被排除的差异**必须报出来**（`RollbackPlan.excluded`，CLI 打一行
「还有 N 项差异落在不可回滚的段上」），否则用户会以为整份都回滚了。

#### 最小覆盖而不是整份写回

覆盖层只冻结「这次要回滚的那几个叶子」。整份写回会把**用户没碰过的字段**
一起冻在回滚时刻：他之后改 patch 里别的参数会发现「改了不生效」，
而回滚层用一份旧值把它盖住了。**那种失败是静默的**（配置看起来改了、
行为没变），本仓库吃过太多次。

`buildRollbackPlan` 用 `changedPartial` 递归求最小覆盖；数组与标量整体替换，
与 `mergeConfig` 语义一致（拆成下标会得到「`[0]` 从 a 改成 b」这种没人看得懂、
也没法回滚的差异）。

#### `canonical` 是唯一判据，指纹只是标签

`canonicalConfig` 产出 `path=JSON值` 的多行文本，**逐字节可比**；
`configFingerprint` 是 32 位 FNV-1a，8 位十六进制，**会碰撞**，只用作人读短标签
（`config list` 的第一列）。拿指纹当「配置有没有变」的判据，迟早会把两份不同
配置当成同一份而跳过记录。

快照去重只与**最后一条**比：A→B→A 是两次真实变化（用户改回去了），
不能因为「与历史某条相同」而丢弃。

#### 降级态不记快照

patch 读不到或校验失败时，CLI 退回 `DEFAULT_CONFIG`。**这个降级态不记台账**
（`ResolvedCliConfig.degraded`）。它不是用户意图，记下去会在最需要回滚的那一刻
成为「最新的回滚点」——而回滚到它等于回滚到一个错误。

#### 为什么 `config` 子命令在 `validateConfig` 与 `openStore` 之前分派

回滚必须**在配置已经坏掉时**可用。`runCli` 里 `config` 分支在
`validateConfig`、`openStore` 之前 `return`：它只需要 `dataDir` 和台账文件，
不需要一个能打开的库。把它放在 `openStore` 之后，就等于「库打得开时才允许修
打不开的库」——一个自相矛盾的门槛。

#### 有一个真缺陷是在写测试时才发现的

`parseCanonicalConfig('')` 曾经返回 `{}`（空串一行都不进循环）。而
`snapshotToConfig({})` 会走 `mergeConfig(DEFAULT_CONFIG, {})` 得到**完整的默认
配置**并校验通过 ⇒ 一条被截断成空行的快照，回滚时会**静默把整库配置重置为
默认值**。用户要的是「回到那一份」，拿到的是「全部重置」，而两者都报成功。

修法是让「一行都没解出来」返回 `null`。**这个承诺原本就写在
`snapshotToConfig` 的注释里（「绝不兜底成默认配置」），但注释挡不住代码**
——承诺写在注释里不算，得有代码挡住那条路。

（顺带记一次自我纠正：这里一度写成两层防护——先判 `canonical.trim()` 为空、
末尾再判 `parsed === 0`。两层**严格重叠**：只要有一行解析成功，trim 必非空；
trim 为空时必一行也解不出。反向验证把外层删掉后 `fail = 0`，说明它是
**等价变异**、是死代码而不是双保险。已只保留 `parsed === 0` 那一层。）

### 8.2 健康检查必须同时看「库自洽」与「插件能不能加载」（FR-F5）

`docs/1-需求规格.md:179`（FR-F5）的验收口径是**「一条命令报健康/异常」**。

#### 真缺陷十五：只查「库内部自洽」，不查「插件能不能加载」

原 `runHealth` 的判据只有 `health.indexOk`。于是最需要它生效的场景
——**配置坏到宿主根本加载不了插件**——它报的是健康：

```text
$ memoryctl health
健康：正常
索引：一致
配置来源：DEFAULT_CONFIG（patch 非法）
$ echo $?
0
```

而同一份 patch 在宿主侧直接抛错：

```text
dsh-memory 配置非法：
recall.absoluteThreshold 必须是 0..1 之间的有限数，实际为 -5
```

用户发现记忆不生效、跑 `health` 得到「一切正常」。**一个报错的观测点
比没有观测点更危险，因为人会信它。**

修法：`healthExitCode` 的入参从 `{ indexOk }` 改成 `{ indexOk, configOk }`，
**两个字段都必填**；人读首行与 `--json` 的 `healthy` 都从同一个
`code` 推出，并新增一行「配置：正常/异常」——否则读人只看到一个
孤零零的「异常」（索引那行会报「一致」），不知道哪里坏了。

#### 真缺陷十六：配置坏掉后，health 看的是另一个库

上一条修完、探针复跑时才暴露的第二层：配置校验失败后
`config` 已经退回 `DEFAULT_CONFIG`，而 `DEFAULT_CONFIG.storage.dataDir` 是
**库默认路径**。于是：

```text
用户库（patch 指定的 dataDir）里有 3 张卡
patch 写成 absoluteThreshold: -5
$ memoryctl health
数据目录：<repo>/.dsh-memory      ← 另一个目录
活跃：0 张                          ← 用户那 3 条好端端在另一个目录里
```

用户看到的不是「配置坏了」，而是「我那 3 条记忆丢了」。
**看错库比报错库更危险**：报错库会让人去查配置，看错库会让人去找
并不存在的丢失。两件事同时发生时，后者会把前者掩盖掉。

正解是数据目录**不能从降级后的 `config` 取**，而要从 `baseline`
（默认值 + patch、**未校验**）取——那才是「假如没有校验失败，宿主
会用哪个目录」。这与 §8.1 里回滚基准的道理是**同一条**：
**「当前值」必须是「假如没有降级，宿主会拿到什么」，不是「降级后我们退回的那个兜底值」。**
两处缺陷同根，只是一个在回滚上、一个在数据目录上。

实现上把它收在 `ResolvedCliConfig.dataDir` 一个字段里，三条返回路径（patch
读不到 / patch 非法 / 成功）都从同一个入口算，`config` 子命令与其余
子命令也取同一个值。**两处各算一遍就是两个真相源，一定会有一处错。**

#### 为什么 `configOk` 是必填而不是可选

若写成 `configOk?: boolean`，那么下一个调用方泡拉图省略它时，行为会
静默退回真缺陷十五：编译通过、测试全绿、只是配置坏了不再报异常。
**必填字段是防线：它把「你忘了这个判据」变成一个编译错误。**
它确实发挥了作用：改完实现后 `tsc` 在
`tests/cli/memoryctl.test.ts` 两个旧调用点报 `TS2345`，而那两个点正是需要
补上新判据的地方。

#### 一条旧测试把缺陷固化成了契约

旧用例「patch 缺失时退回默认值」里写着：

```ts
assert.equal(result.code, EXIT_OK, '配置读不到不该让健康检查失败')
```

这句话把「配置读不到时报正常」写成了预期行为。而它保护的那一半
（库本身没坏、索引一致、卡片读得出）仍然成立，所以修法是**拆开两件事**：
`索引：一致` 照旧断言，退出码改为 `EXIT_UNHEALTHY`，并新增 `配置：异常`。
这是「测试替实现打掩护」的反向形态：**测试替缺陷打掩护**。

#### 测试与反向验证

`tests/cli/memoryctl.test.ts` 新增/改写 5 条：四种 `{indexOk, configOk}` 组合全写出来
（只写「都正常」与「都异常」两条的话，一个 `&&` 写成 `||`
的实现也会全绿）、配置坏掉→报异常且 json 的 `healthy` 与退出码同一结论、
patch 读不到→也报异常、配置坏掉→仍看用户那个库（活跃 2 张 + 路径匹配）。

反向验证 6/6 命中（`.tmp/reverse-f5.mjs`）：M1 判据只看索引、M2 判据写成 `||`、
M3 首行仍由 `health.healthy` 推出、M4 json 的 `healthy` 不与退出码对齐、
M5 「配置」那行恒报正常、M6 数据目录从降级后的 `config` 取。

两个值得记的坑：

- **M5 的锚点第一版命中 0 次**：我把文案写成了「不是你的那份」，
  实际代码是「不是你配的那份」。脚本报「锚点命中 0 次」而不是
  「通过」，这正是那条防御写得对。
- **M4 第一版我写成了 `expectAnyRed: false`**，理由是「可能没用例守 json」。
  但它与真缺陷七（同一张卡报两个总分）是同一类双真相源缺陷，
  应当被守住。补上 json 断言后它精确命中 2 条。
  **把一条本该守的东西标成「预期不变红」，是用脚本给自己开了一个后门。**

### 改字段名时，旧配置必须被如实迁移

配置版本 5 把扩散开关从布尔 `spread.enabled` 换成了三态 `spread.mode`。
若只是把新字段加进去，旧配置 `{ spread: { enabled: true } }` 会**静默降级**
成默认的 `'shadow'`：用户明确要求「打开扩散」，系统回答「好的，我不改排序」。

实测确认过：迁移前合并结果里 `enabled: true` 原样留着（**无人读取**），
`mode` 是默认的 `shadow`，`validateConfig` 返回 `{ ok: true, errors: [] }`。
**不报错、不告警、行为与用户意图相反，而且事后无从发现。**

`mergeConfig` 里的 `migrateSpreadMode` 按 `enabled` 原本的语义映射：

| 旧配置 | 迁移后 | 理由 |
|---|---|---|
| `enabled: true` | `'on'` | 旧版行为就是真实参与排序，逐位一致 |
| `enabled: false` | `'off'` | 旧版行为就是完全不计算，逐位一致 |
| 未写 | 保持默认 `'shadow'` | 没有意图可迁移 |
| 非布尔值 | 保持默认 | 无法解释的值不猜 |

**显式写了 `mode` 时以 `mode` 为准**：两个都写是用户自己矛盾，不替他猜，
但新字段更具体，旧字段只用来补空缺。迁移后**不把 `enabled` 带进结果**——
留着一个已无读者的字段，下一个人会以为它还在起作用。**配置对象的形状必须与
代码实际读的字段一致。**

一般化：**给配置字段改名、改类型、改语义时，必须问「旧值会变成什么」**。
静默降级比报错危险得多，因为它不会让任何人去看一眼。
