### P0-1 · ST-6 连续 50 轮 token 稳定性（唯一完全无测试的验收项，且实测会失败）

**要测什么**

`docs/1-需求规格.md` §12.1 原文：「连续 50 轮，动态层 token 波动 ≤ ±10%，不单调增长」。

**实测数据**（60 轮探针，`maxCards = 7`、`tokenBudget = 900`、`overheadTokens = 100`）：

| 轮次 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8–60 |
|---|---|---|---|---|---|---|---|---|
| 卡数 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 7 |
| token | 127 | 154 | 181 | 208 | 235 | 262 | 289 | 289 |

> **数据修订记录**：本表原为 `27 / 54 / … / 189 / 189 / 190`，那是在
> 「头尾固定开销未计入 token 预算」的旧实现上测的（该缺陷已修，见 AGENTS.md
> 起源对照审查遗留项）。修正后每轮恰好增加 `overheadTokens = 100`
> （27+100=127、189+100=289），**差值精确等于固定开销**，可以反证这次修复
> 只动了开销计入、没有动卡片选择逻辑。饱和期波动也从 `189→190` 收敛为**恒
> 289**，说明原先那 1 token 的漂移同样来自开销漏算。

**结论：ST-6 在预热期必然不成立。** 第 1 轮到第 7 轮 token 从 127 涨到 289，是 **2.3 倍**，远超 ±10%。这不是 bug，是焦点包「从空到满」的正常爬坡。所以：

- 如果照字面从第 1 轮开始量 ±10%，**这个测试永远红**，会被当成「写错的测试」删掉；
- 正确写法是**分开断言**：预热期断言单调上升，饱和期（第 7 轮起）断言 ±10%。

这个区分不写进测试，ST-6 要么无法通过、要么被写成永远绿的假测试。

## 第三部分补充：本轮测试查出的两个真缺陷

这两条都不是「测试没写」，而是**写了测试才发现实现是错的**。
记在这里是因为它们的发现方式比缺陷本身更值得复用。

### 缺陷一 · 边权更新被幂等键静默丢弃（`44cabd2`）

`deriveIdempotencyKey` 的 `edge` 分支原来只取 `op.edge.id`，**不含权重**。
同 id 改边权时派生的幂等键与上次完全相同，数据面判重复、**静默丢弃**，
读回还是旧值。

**发现方式**：给 FR-G1 写「召回不得改动图谱边权」这条端到端测试时，
我往 `buildRecall` 里注入 `reinforceEdges` 想让它变红——结果**不红**，
但注入日志明明打印了「强化了 1 条边」5 次。

追下去才发现：写入被幂等键吞了。**测试不红不是断言弱，是缺陷在更底层。**

**为什么长期没被发现**：`edge` 的产出点只有夜整理，而夜整理只**新建**边、
从不修改已存在的边（`knownEdgeIds` 过滤）。「幂等键不含权重」在当时的
调用模式下**永远正确**。直到可塑性需要改边权，前提才失效。

**原有测试为什么没守住**：`putEdge 应自动补齐边 id 并幂等` 只用**同一权重**
写两次，测的是「该丢弃的丢弃」，而缺陷在「不同权重也被当重复」——
**只测一个方向，缺陷从中间溜过去。**

### 缺陷二 · 夜整理时刻只活在内存里（`0e058b1`）

`lastConsolidationAt` 是进程内字段，`src/index.ts` 的 `lastRunAt` 也从 `null` 起。
后果：每次进程重启都认为「从未整理过」，立刻整理一次。幂等、不丢数据、
不报错——**只是白烧全库去重的 CPU**。

**发现方式**：写「重启后不应重复整理同一天」这条测试时，必须先造出
「引擎 A 整理 → 关闭 → 引擎 B 打开」的序列，才发现引擎 B 根本不知道
A 整理过。

**为什么值得单独记**：这类缺陷**没有症状**。它不报错、不丢数据、
不影响任何可见输出，唯一的代价是 CPU。**如果没人专门写「重启后」的测试，
它永远不会被发现，也永远不需要被修**——因为它不影响正确性。

这正是「判据一（可恢复性）」允许丢的状态，但**允许丢 ≠ 允许每次重算**。
两件事必须分开：丢了要能重建（判据一），但正常路径上不该丢。

### 缺陷三 · 扩散在数学上恒为空，而 31 条单测全绿（`af356bc`）

这条比前两条更值得记，因为**它不是某个函数写错了，而是参数结构自相矛盾**。

种子判据是 `total >= absoluteThreshold`（0.18），加分护栏是
`selfScore >= absoluteThreshold * minSelfScoreRatio`，而 `minSelfScoreRatio`
被校验强制 `≥ 1`。两个门槛恰好相等：

```text
能加分的卡一定已经是种子 → 而种子不因扩散加分 → boost 恒为空集
```

实测：`off` / `shadow` / `on` 三种模式的总分**逐位相同**，观察值 0 条。
整个 FR-G1 的接线等于一行都没执行。

**为什么 31 条单测全绿**：它们全部直接调 `spreadActivation` 这个纯函数、
**自己构造种子数组**，从来没有经过「谁当种子」这一步。而唯一那条声称
「扩散能把卡推进焦点包」的用例写的是 `assert.ok(bAfter >= bBefore)`——
等式成立也算通过，而当时 `bAfter === bBefore`。

**反向验证时它也不红**：把种子判据改成恒 `false`，只有 2 条**新写的**测试变红，
那条老用例纹丝不动。

**第一次修复也失败了**：改成 `seedRatio = 1.5`（门槛 `0.18 × 1.5 = 0.27`），
实测仍然恒空。因为打分有**基础分下限**——完全无关的两句话也有 0.33 左右
（importance / recency / confidence 各贡献一份）。实测 12 个样本最低 0.3295，
无一低于 0.18。所以任何「`absoluteThreshold` × 倍数」的标定都落在所有卡之下。

**正解是相对量**：门槛 = 本轮最高分 × `seedRatio`（默认 0.85）。
它无量纲、自动跟随本轮分数分布，衡量的是「这张卡在本轮里够不够强」，
而不是「这张卡够不够格」——后者在这个打分公式下没有意义。

**发现方式**：给扩散写「真的把排名靠后的卡提了分」这条测试时，要求断言
**严格上升**。原来的 `>=` 断言在 `bAfter === bBefore` 时也是绿的，
所以第一次写严格断言就直接红了，这才发现机制是空转。

**三条推论**：

1. **两个门槛相等 ⇒ 机制恒为空。** 判据之间是否互相抵消，比单个判据对不对
   更重要。写多阈值逻辑时必须问「这两个阈值的可达区间有没有交集」。
2. **断言 `>=` 等于没断言。** 要求「变好」就必须写 `>`；`>=` 在「什么都没发生」
   时也成立。同理，余量大到永远成立的 `<` 也是装饰。
3. **只测纯函数不等于测了链路。** 纯函数层的测试自己构造输入，
   跳过了「输入是怎么产生的」这一步——而缺陷经常恰好在那一层。

### 缺陷四 · `put` 的幂等键漏掉强度与状态，注释替实现撒了谎（`7a126ce`）

这是**缺陷一（`edge` 分支）的同源兄弟**，结构完全一样：

| | `edge`（缺陷一） | `put`（缺陷四） |
|---|---|---|
| 幂等键漏了什么 | 边权 `weight` | `strength` / `status` / `accessCount` |
| 后果 | 改边权被静默丢弃 | 改强度、改状态被静默丢弃 |

实测（修复前）：

| 只改这个字段 | `written` | 读回 |
|---|---|---|
| `strength` 0.6 → 0.2 | **false** | 0.6 |
| `status` active → archived | **false** | active |
| `accessCount` 0 → 7 | **false** | 0 |

三条全部静默丢弃，重放后仍是旧值。**不报错、不告警、`validateConfig` 也不管。**

**为什么比缺陷一更值得记**：`put` 分支的注释**明确写着**它防的是

> 只按 id 拼键会把「同一张卡的后续更新」误判为重复提交而静默丢弃
> ——冲突标记回写、强度调整、状态变更全部失效。

注释说它防三件事，实现只取了 `id + updatedAt + text + conflictOf`，防了一件半。
**读注释会以为已经修好了，所以没人去看实现**——这比没有注释更危险。

**为什么长期没暴露：靠巧合安全，不是靠规则安全。** 每个真实改动路径都**恰好**
顺带更新了 `updatedAt`：

- `decayCard`（`src/consolidate/decay.ts:127`）改 `strength` 时一并置 `updatedAt = now`；
- `revise` / `archive` / `restore` 走各自独立的 op 分支，不经过 `put`。

于是键碰巧变了、写入碰巧成功。判据不是「现在有没有出问题」，而是「**有没有一条
路径能只改这个字段**」——有，缺陷就还在，只是还没被走到。

**发现方式**：给 ST-1 写反向验证时，第一个变异（`recall` 里悄悄调 `strength`）
**没有变红**。按 AGENTS.md 的规矩先查「变异是否真的命中」，结果发现命中且能编译，
只是 `store.append({ op: 'put', ... })` 返回 `written: false`——幂等键判了重复。
顺着查下去才找到这条缺陷。**反向验证不红时，别急着加断言，先查变异为什么不生效。**

**两条推论**：

1. **修一个幂等键缺陷时，把同一文件里所有分支都看一遍。** 同一个人用同一种
   思路写下的多个 `case`，错法往往一样。
2. **注释声称的行为，必须有一条测试真的去验它。** 否则注释会持续替实现撒谎，
   而且比沉默更能阻止别人发现问题。

### 这四条的共同点

**都不是「漏写测试」，而是「测试写了但选错了方向或层次」。**

- 缺陷一：测了「该丢弃的丢弃」，没测「该更新的更新」
- 缺陷二：没有任何测试跨过「进程重启」这条边界
- 缺陷三：测了纯函数的数学性质，没测「谁当种子」这一步，且断言用了 `>=`
- 缺陷四：缺陷一修好后没回头把**同类分支**看一遍，注释成了「已修复」的假证据

推论：**测试覆盖率看不出这四类缺陷。** 它们藏在「已覆盖的代码里」，
只有问「这条测试在哪个方向上是空的」才能发现。

### 4.3 `tests/host/engine-token.test.ts`（P0-1，需真实 store + 临时目录）

```typescript
/**
 * 连续多轮的注入预算稳定性单测（ST-6 / FR-E3）。
 *
 * 覆盖目标：
 * - ST-6：连续 50 轮动态层 token 波动 ≤ ±10%，且不单调增长。
 * - FR-E3：每轮注入都不超 `recall.tokenBudget` 硬上限。
 * - 预热期（焦点包未装满）与饱和期（装满 7 条）要分开断言——
 *   混在一起断言会得到一个必然失败的测试，见报告第三部分 P0-1。
 *
 * 需要真实 `MemoryStore`（临时目录），不需要宿主。
 *
 * @module tests/host/engine-token.test
 */

import { after, describe, it } from 'node:test'
import assert from 'node:assert/strict'

import type { MemoryConfig } from '../../src/core/config.ts'
import type { TurnInput } from '../../src/core/extraction.ts'
import { MemoryEngine } from '../../src/host/engine.ts'
import { openStore } from '../../src/store/store.ts'
import type { MemoryStore } from '../../src/store/store.ts'
import { makeConfig } from '../consolidate/fixtures.ts'
import { makeTempDir, removeDirContents } from '../store/helpers.ts'

const TZ = 'Asia/Shanghai'
const T0 = 1_700_000_000_000
const MINUTE_MS = 60 * 1000

/** ST-6 要求连续观察的轮数。 */
const ROUNDS = 50

/** 焦点包装满所需轮数（maxCards = 7，每轮稳定贡献一张新卡）。 */
const WARMUP_ROUNDS = 7

const tempDirs: string[] = []

/** 建临时目录并登记。 */
function tempDir(): string {
  const dir = makeTempDir('dsh-memory-token-')
  tempDirs.push(dir)
  return dir
}

after(() => {
  for (const dir of tempDirs) removeDirContents(dir)
})

/** 一轮对话的输入；每轮换一个可区分的话题词，保证卡不被去重合并。 */
function turnInput(round: number, at: number): TurnInput {
  return {
    sessionId: 's-token',
    turn: round,
    step: 1,
    seq: round,
    userText: `第 ${round} 轮：我们决定把服务部署到集群 ${round}，方案已经确定`,
    assistantText: '',
    domain: 'work',
    at,
  }
}

/** 逐轮写入并召回，返回每轮的注入 token 数。 */
function runRounds(rounds: number): {
  tokens: number[]
  cards: number[]
  config: MemoryConfig
  store: MemoryStore
} {
  const dir = tempDir()
  const config = makeConfig({ storage: { dataDir: dir } })
  const store = openStore({ config, dataDir: dir })
  let now = T0
  const engine = new MemoryEngine({ store, config, timeZone: TZ, clock: () => now })

  const tokens: number[] = []
  const cards: number[] = []
  for (let round = 1; round <= rounds; round += 1) {
    now = T0 + round * MINUTE_MS
    engine.writeTurn(turnInput(round, now))
    const result = engine.recall(`第 ${round} 轮部署方案`)
    tokens.push(result.pack.tokens)
    cards.push(result.pack.cards.length)
  }
  return { tokens, cards, config, store }
}

/** 求均值。 */
function mean(values: readonly number[]): number {
  return values.reduce((sum, value) => sum + value, 0) / values.length
}

describe('FR-E3 每轮注入不超硬预算', () => {
  it('连续 50 轮每轮 token 都不超过 tokenBudget', () => {
    const { tokens, config, store } = runRounds(ROUNDS)
    for (const [index, value] of tokens.entries()) {
      assert.ok(
        value <= config.recall.tokenBudget,
        `第 ${index + 1} 轮 token ${value} 超出预算 ${config.recall.tokenBudget}`,
      )
    }
    store.close()
  })

  it('每轮 token 都不小于头尾固定开销（固定开销真的被算进去了）', () => {
    const { tokens, config, store } = runRounds(WARMUP_ROUNDS)
    for (const value of tokens) {
      assert.ok(value >= config.recall.overheadTokens)
    }
    store.close()
  })

  it('卡数不超过 maxCards（硬上限，不因库变大而膨胀）', () => {
    const { cards, config, store } = runRounds(ROUNDS)
    for (const [index, value] of cards.entries()) {
      assert.ok(
        value <= config.recall.maxCards,
        `第 ${index + 1} 轮 ${value} 张卡，超过 maxCards ${config.recall.maxCards}`,
      )
    }
    store.close()
  })
})

describe('ST-6 预热期行为（焦点包未装满）', () => {
  it('前若干轮 token 随卡数单调上升——这是正常的，不是抖动', () => {
    const { tokens, store } = runRounds(WARMUP_ROUNDS)
    for (let i = 1; i < tokens.length; i += 1) {
      assert.ok(
        tokens[i]! > tokens[i - 1]!,
        `第 ${i + 1} 轮 ${tokens[i]} 应大于第 ${i} 轮 ${tokens[i - 1]}`,
      )
    }
    store.close()
  })

  it('预热期 token 跨度必然远超 ±10%（所以 ST-6 不能从第 1 轮开始量）', () => {
    const { tokens, store } = runRounds(WARMUP_ROUNDS)
    const span = Math.max(...tokens) - Math.min(...tokens)
    const average = mean(tokens)
    assert.ok(
      span > average * 0.1,
      `预热期跨度 ${span} 若不大于均值 10%（${(average * 0.1).toFixed(1)}），说明前提变了`,
    )
    store.close()
  })
})

describe('ST-6 饱和期波动 ≤ ±10%', () => {
  it('焦点包装满后，连续 50 轮 token 波动不超过均值的 ±10%', () => {
    const { tokens, store } = runRounds(ROUNDS)
    const steady = tokens.slice(WARMUP_ROUNDS - 1)
    assert.ok(steady.length >= 40, `饱和期样本应 ≥ 40，实际 ${steady.length}`)

    const average = mean(steady)
    const low = Math.min(...steady)
    const high = Math.max(...steady)
    assert.ok(
      high - low <= average * 0.1,
      `波动 ${high - low} 超过均值 ${average.toFixed(1)} 的 10%（low=${low} high=${high}）`,
    )
    store.close()
  })

  it('第 50 轮 token 不高于第 7 轮的 110%（不单调增长）', () => {
    const { tokens, store } = runRounds(ROUNDS)
    const baseline = tokens[WARMUP_ROUNDS - 1]!
    const last = tokens[ROUNDS - 1]!
    assert.ok(
      last <= baseline * 1.1,
      `第 50 轮 ${last} 相对第 7 轮 ${baseline} 增长超过 10%`,
    )
    store.close()
  })

  it('饱和期卡数恒等于 maxCards（不再随轮数变化）', () => {
    const { cards, config, store } = runRounds(ROUNDS)
    const steady = cards.slice(WARMUP_ROUNDS - 1)
    for (const value of steady) assert.equal(value, config.recall.maxCards)
    store.close()
  })
})

describe('ST-1 相同查询在库增长后仍确定', () => {
  it('同一轮内重复召回同一查询结果完全一致', () => {
    const { store, config } = runRounds(WARMUP_ROUNDS)
    const engine = new MemoryEngine({
      store, config, timeZone: TZ, clock: () => T0 + WARMUP_ROUNDS * MINUTE_MS,
    })
    const first = engine.recall('部署方案')
    const second = engine.recall('部署方案')
    assert.deepEqual(
      first.pack.cards.map((item) => item.card.id),
      second.pack.cards.map((item) => item.card.id),
    )
    assert.equal(first.pack.tokens, second.pack.tokens)
    assert.equal(first.text, second.text)
    store.close()
  })
})
```
