## 〇、术语表（先读这个，否则后面看不懂）

| 术语 | 定义 |
|---|---|
| **记忆卡**（card） | 从对话里抽出的一条记忆。字段见 §2.3。它是这个系统唯一的记忆单位。 |
| **焦点包**（Focus Pack） | 每轮对话注入模型上下文的那一小段文本，装 **3~7 张卡**。这是「记忆」唯一被模型看见的形式。 |
| **夜整理**（consolidation） | 每晚跑一次的后台批处理：衰减、蒸馏、去重、归档、摘要、建图。 |
| **词项**（term） | 文本的最小可比较单位。中文按**二元组**切（「线性代数」→ 线性/性代/代数），英文按**整词**切。 |
| **total** | 一张卡的**总分**，5 个分量加权，∈[0,1]。见 §3.3。 |
| **relevance** | 一张卡的**相关分量**，只看语义与目标两项，∈[0,1]。见 §3.3。 |
| **两道尺子** | `total` 与 `relevance` 是两个不同尺度的量。**这是本项目最重要的一个区分**，见 §3.3。 |
| **种子**（seed） | 扩散激活的起点卡。 |
| **边权**（edge weight） | 图谱边的强度，∈[0,1]，**量化到 0.01 格点**（101 个可能值）。 |
| **扩散激活**（spread activation） | 「因为想起了 A，所以想起 B」——沿图把分数传出去。 |
| **可塑性**（plasticity） | 边权随使用而**变强**、随时间而**变弱**。**目前未启用**，见 §3.10。 |
| **token** | 模型计费单位。本文用 `CJK 字数 + ceil(非CJK 字符数/4)` 估算，不用真 tokenizer。 |
| **ST-1** | 本项目一条硬性验收：**同样输入连续 10 次必须给出逐位相同的结果**。 |

**关键背景**：这是一个「给 AI 加长期记忆」的插件。它每轮把最相关的几张记忆
塞进模型上下文，让模型「记得」之前发生过什么。所以本文档里所有数学，
最终都在回答同一个问题：**下一轮该让模型看见哪 3~7 张卡？**

### 1.3 硬约束（不能违反的边界）

| # | 约束 | 为什么 |
|---|---|---|
| C1 | **确定性**（ST-1） | 同样输入连续 10 次，结果必须**逐位相同**。所以任何数学都不能依赖随机、时间戳精度、哈希顺序、浮点累加顺序。 |
| C2 | **不编造** | 抽不出就说抽不出，不许猜。空包要显式输出「没有相关记忆」，不能输出空串。 |
| C3 | **可解释** | 每张卡为什么进包、为什么加分，都要能说出来。所以打分明细必须保留。 |
| C4 | **参数可版本化** | 所有阈值必须在配置里，不许散落字面量。 |
| C5 | **耗时可控** | 召回在每轮对话的主路径上，必须有上界。 |

**C1 是本文档里最容易被忽略、但杀伤力最大的一条**：它排除了「按相似度排序后
取前 k 个」之外的几乎所有图算法（因为图遍历顺序会影响浮点累加），
也排除了任何用 `Set` 迭代顺序的地方。后面 Q3/Q4 的很多取舍都是被 C1 逼出来的。

## 二、系统架构（不依赖代码）

### 2.1 三个时间尺度

```text
每轮对话（毫秒~秒）
  └─ 写入：从这一轮抽出 0~4 张卡，追加到日志
  └─ 召回：算分 → 过闸 → 装包 → 注入

每晚（一次）
  └─ 夜整理：衰减 → 蒸馏 → 去重合并 → 归档 → 摘要 → 建图 → 重建索引

永远（跨会话）
  └─ 日志是唯一真相源，卡是从日志重放出来的「视图」
```

**「日志是唯一真相源」的含义**：所有写入都是 append-only 的事件记录，
重启时重放日志得到当前状态。所以任何「卡」的字段都是**可重放的确定性函数**。
这条设计直接服务 C1（确定性）。

### 2.2 一轮对话的完整数据流

```text
用户输入 + 助手输出
  │
  ├─① 门控（gateTurn）：五条通道任一放行才继续，否则这一轮什么都不记
  │
  ├─② 切句 → 逐句打分（显著性 / 情绪 / 置信度）→ 排序取前 N（≤4）
  │
  └─③ 写入日志

（下一轮开始时）

  ├─④ 倒排索引取候选：按查询词项召回候选卡，再与「活跃卡」取交集
  │
  ├─⑤ 逐卡打分：5 个分量 → total + relevance
  │
  ├─⑥ 扩散激活：从种子卡沿图谱传播能量，给部分卡加分
  │
  ├─⑦ 三道闸截断：绝对闸 → 相对闸 → 硬上限 7 张
  │
  └─⑧ token 预算装包：超出就丢，装不下就截断
```

**注意 ⑥ 在 ⑦ 之前**：扩散只改 `total`，不改 `relevance`。这是刻意的，
原因见 §3.3——如果扩散能改 `relevance`，绝对闸就会被扩散绕过去。

### 2.3 数据结构（文字定义，不需要代码）

**记忆卡**（card）：

```text
id           内容哈希，同时是排序的最后 tiebreaker
text         原文
normalized   归一化文本（全角转半角、转小写、标点转空格）
kind         类别：event / concept / feeling / promise / experience / summary
domain       生活 / 学习 / 工作（对应起源 L13 的三模块）
entities[]   实体词（项目名、路径、需求编号、专名）
tags[]       标签
salience     显著性 [0,1]    ← 写入时算
emotional    情绪强度 [0,1]  ← 写入时算
confidence   置信度 [0,1]    ← 写入时算
strength     当前强度 [0,1]  ← 每夜衰减
accessCount  被访问次数      ← 只增
createdAt    创建时刻
updatedAt    最后更新时刻
conflictOf[] 与之冲突的卡 id
status       active / archived
mergedInto   若被合并，指向目标卡 id
```

**边**（edge）：

```text
from, to   两张卡的 id
relation   same-topic / same-entity / supersedes / distills
weight     [0,1]，量化到 0.01
at         创建时刻
```

## 三、公式全集（目前实际在算的）

> 本章每个算子给三件事：**公式**、**常量**、**为什么这么定**。
> 你可以把这章当成一份可以直接实现的规格说明书。

### 3.1 文本如何变成可计算的量

所有相似度都建立在「词项集合」上。

```text
normalize(text):
    全角字符 → 半角（码点 − 0xFEE0）
    全角空格 U+3000 → 半角空格
    转小写
    所有标点与符号 → 空格
    多个空格合并

tokenize(normalized):
    中文：取连续汉字的**二元组**（bigram）
          「线性代数」→ {线性, 性代, 代数}
          单字也保留为单元组
    英文：取**整个小写单词**（不切词干）
    过滤停用词

tokenSet(card) = tokenize(card.normalized)
```

**为什么中文用二元组而不是分词**：没有词典。二元组是无词典分词的标准做法，
代价是会产生一些无意义的组合（比如跨标点的「，这」），所以 `tokenize`
的入参约定必须是**已归一化文本**——标点已经被换成空格，二元组就不会跨标点。

**两个相似度函数**：

```text
jaccard(A, B) = |A ∩ B| / |A ∪ B|

coverage(A, B) = |A ∩ B| / |A|          ← 注意分母是 A，不是并集
```

`coverage` 用在「查询词有多少被这张卡覆盖了」，`jaccard` 用在「两张卡有多像」。
**两者不可互换**：`coverage` 对「卡比查询长得多」是宽容的，`jaccard` 不是。

### 3.2 一张卡怎么打分（5 个分量）

#### ① 语义分 semanticScore

```text
semanticScore = clamp01(
    文本覆盖 × 0.72
  + 标签命中 × 0.14
  + 实体命中 × 0.14
)
```

其中三项都是 `coverage`：`coverage(tokenSet(card), query.tokens)` 等。

三项系数和 = 1.00，所以不需要再夹。

**为什么 0.72**：正文是主要语义载体。让「正文完全不重合、只有标签重合」的卡
最高拿 0.14——不足以单独过闸（见 §3.4 的标定换算），所以**标签无法把无关卡拉进包**。

#### ② 重要性分 importanceScore

```text
importanceScore = clamp01(
    显著性 salience  × 0.55
  + 情绪   emotional × 0.25
  + 访问加成         × 0.20
)

访问加成 = min(1, log1p(accessCount) / log1p(12))
```

**为什么用 `log1p`**：访问次数是重尾分布（少数卡被反复访问）。
线性会把「访问过 100 次」压成绝对优势，`log1p` 让第 1 次访问贡献最大
（`log1p(1)/log1p(12) = 0.279`），第 12 次才饱和到 1。

**为什么分母是 12**：`log1p(12) ≈ 2.565`，配 0.20 权重意味着访问 12 次后
这一项封顶。12 对应「两周内每天看一次」——超过这个频次，边际价值应该让位于内容本身。
**【判断】这个 12 没有分布级标定，是经验值。**

#### ③ 新鲜度分 recencyScore

```text
recencyScore(ageMs, halfLifeMs) =
    halfLifeMs <= 0 ? 0
  : ageMs <= 0     ? 1
  : 2^(−ageMs / halfLifeMs)
```

标准指数衰减。`ageMs <= 0`（未来时刻或同刻）返回 1 而不是外推——
避免时钟回拨时出现 `> 1`。

**有效半衰期**（情绪与访问频次延长寿命，服务 R4）：

```text
effectiveHalfLife = base
                  × (1 + clamp01(emotional) × (boost − 1))
                  × (1 + min(1, log1p(accessCount) / log1p(20)))

base  = 14 天 = 1_209_600_000 ms
boost = 2.0
```

**为什么做成半衰期的乘数而不是额外加分**：起源 L11 说「细节会忘，感受会留」。
「忘得慢」和「分得高」是两件事——前者影响它在多久之后仍然可见，
后者影响它排第几。做成乘数才能实现「感受留得久」。

注意两处 `log1p` 分母不同（重要性用 12、半衰期用 20），这是**刻意的**：
重要性回答「这张卡有多重要」，半衰期回答「这张卡能活多久」，饱和点不必相同。
两处都用 12 会诱使读者以为它们是同一个量。

#### ④ 目标分 goalScore

```text
goalScore = coverage(tokenSet(card), query.goalTokens)
```

**关键约定：目标缺席时贡献 0，但权重仍留在分母里。**

这里有一个真实教训。我最初的做法是「没目标就把 goal 权重从分母里摘掉」，
理由是「不知道不该算 0 分」。归一化分因此整体上浮 `1/0.9 ≈ 11%`，
一张 100 个半衰期、语义相关为 0 的死卡从 0.168 抬到 0.187，越过了当时的阈值 0.18。

取「缺失即中性」的真正理由不是数学，是**防御性**：`goalText` 为空曾经是一个
上游 bug。按摘分母的写法，这个 bug 会让每张卡都涨 11%、更容易进焦点包
——**缺陷反而让召回看起来更好，没人会去修它**。

#### ⑤ 冲突惩罚 conflictPenalty

```text
conflictPenalty = clamp01(min(1, |card.conflictOf| / 3))
```

冲突数越多惩罚越重，但封顶，避免一条卡因多处冲突被彻底埋掉。

**⚠️ 注意两件事**：
1. 饱和点 `3` 是**未经标定的经验值**。
2. **产生 `conflictOf` 的判据方向是错的**（见 §5 Q6）。所以这个惩罚项
   目前是在惩罚一个不可信的量。

### 3.3 两个分量：total 与 relevance

**这是本项目最重要的一节。** 如果只读一节，读这节。

```text
权重：
    semantic   = 0.42
    importance = 0.18
    recency    = 0.20
    goal       = 0.10
    confidence = 0.10
    conflict   = 0.25        ← 只做惩罚，不进正权重和

正权重和 positiveWeight = 0.42+0.18+0.20+0.10+0.10 = 1.00

normalized = (semantic×0.42 + importance×0.18 + recency×0.20
            + goal×0.10 + confidence×0.10) / 1.00

total = clamp01(normalized − conflictPenalty × 0.25)
```

**相关分量**：

```text
relevantWeight = semantic权重 + goal权重 = 0.42 + 0.10 = 0.52

relevance = clamp01((semantic×0.42 + goal×0.10) / 0.52)
```

#### 为什么必须有两个分量

`total` 里有 **0.48 的权重与查询无关**（`importance 0.18 + recency 0.20 +
confidence 0.10`）。这意味着：

```text
一张语义完全为 0（与查询毫无关系）的卡，
total 仍然可以达到 (0.18×imp + 0.20×rec + 0.10×conf) / 1.00

各分项取 0.5 → 0.2400
各分项取 1.0 → 0.4800
```

**【实测】** 无关卡 `total` 落在 0.313~0.377，相关卡 0.345 起，**重叠 33.3%**。

⇒ **在 `total` 这把尺子上，不存在能分开「相关」与「无关」的阈值。**

这个结论我用血换的：项目里曾两次把绝对阈值架在 `total` 上，两次都变成**恒真**
（判据永远通过，机制永远不生效），而两次都不报错、不崩溃、日志正常、测试全绿。
详见 §4.1。

#### relevance 的一个已知收缩（代价）

```text
goal = 0 时（无目标查询）：
relevance = semantic × 0.42/0.52 = semantic × 0.8077
```

即**无目标时 `relevance` 系统性打 80.8 折**。而绝对阈值 0.06 是对 `relevance`
标定的，所以：

```text
无目标时需 semantic ≥ 0.06 / 0.8077 = 0.0743 才过闸
有目标时需 semantic 更低
```

**这不是 bug**（恒定分母的代价），但它意味着**同一个查询加上目标与不加，
过闸难度相差 23.8%**。见 §5 Q1。

### 3.4 三道闸（决定哪几张卡进包）

```text
relativeFloor = scored[0].score.total × relativeThreshold   (0.55)

for item in scored（已按 total 降序）:
    if picked.length >= maxCards (7):                break      ← 闸③ 硬上限
    if item.score.relevance < absoluteThreshold (0.06): continue  ← 闸① 绝对闸
    if item.score.total < relativeFloor:             continue     ← 闸② 相对闸
    picked.push(item)
```

**三道闸取最严**，且**用两把不同的尺子**：

| 闸 | 尺子 | 回答的问题 | 常量 |
|---|---|---|---|
| ① 绝对闸 | `relevance` | 「有没有关系」 | 0.06 |
| ② 相对闸 | `total` | 「比本轮最好的差多少」 | 0.55 |
| ③ 硬上限 | 张数 | 「最多给几张」 | 7 |

#### 为什么相对闸不能也挪到 relevance

**【实测】** 某个验收场景里目标卡 `relevance` 0.1113、相对闸 0.1121，
**差 0.0008 被挡出包**，而它在 `total` 尺度上（0.3925 vs 闸 0.2522）本该轻松通过。

根因：`relevance` 的相对离散度比 `total` 大（同批候选 0.546 vs 0.856），
同一个 `relativeThreshold` 在 `relevance` 尺度上苛刻得多。

⇒ **两把尺子不是不一致，是两道闸问的问题不同。**

但留在 `total` 尺度上有代价：会系统性淘汰「旧而相关」的卡。这是 §5 Q2。

### 3.5 扩散激活（「类似神经的突触效果」）

#### 算法

```text
输入：种子卡（含能量）、邻接表、各卡自身 relevance、配置

if mode == 'off':      return []          # shadow 模式必须照常算，只是不生效
if seeds.length == 0:  return []

selfFloor = absoluteThreshold × minSelfScoreRatio      # 0.06 × 1.0 = 0.06

对每个种子（按 id 升序，保证浮点累加顺序固定 ← 服务 C1 确定性）：
    visited  = {seed.id}
    frontier = [{ id: seed.id, energy: seed.score }]
    for hop in 0 .. maxHops−1:                        # maxHops = 2
        for node in frontier:
            for edge in adjacency[node.id]:
                target = 边的另一端点
                if target in visited: continue
                visited.add(target)
                energy = node.energy × edge.weight × hopDecay
                if energy <= 0: continue
                accumulated[target] += energy         # ← 多路径直接相加
                sourcesOf[target].add(seed.id)

对每个 target:
    if target 是种子:            continue             # 种子不给自己加分
    if selfScores[target] < selfFloor: continue       # 护栏
    boost = min(maxBoost, accumulated[target])        # 截平
    results.push({ id, boost, sources, raw: accumulated, selfScore })

results.sort(按 raw 降序 → selfScore 降序 → id 升序)
return results.slice(0, maxAffected)
```

#### 常量

| 参数 | 值 | 含义 |
|---|---|---|
| `hopDecay` | 0.5 | 每跳能量乘数 |
| `maxHops` | 2 | 最大跳数 |
| `maxBoost` | 0.12 | 单卡加分上限 |
| `minSelfScoreRatio` | 1.0 | 护栏倍数（校验强制 ≥ 1） |
| `seedRatio` | 0.85 | 种子门槛 = 本轮最高 `relevance` × 0.85 |
| `maxAffected` | 5 | 最多影响几张卡 |
| `mode` | `shadow`（默认）/ `on`（出厂） | 三态：关 / 只观察 / 生效 |

#### 种子选择

```text
maxScore  = max(item.score.relevance for item in scored)
seedFloor = maxScore × seedRatio            # 0.85

seeds = [ { id, score: item.score.total } for item
          if item.score.relevance >= seedFloor ]
```

**判据用 `relevance`（够不够格当种子），能量用 `total`（能撒多少）。**

两个用途不同，用不同的量是刻意的——但这是修了一个真缺陷的结果：
原来判据也用 `total`，而 `total` 有 0.48 权重与查询无关，把相对离散度压平到
**【实测】0.9059（同质语料）/ 0.9655（异质语料）**，而 `seedRatio = 0.85`
落在其下 ⇒ **所有卡都是种子 ⇒ 受益者恒为 0 ⇒ 扩散在数学上恒为空**。
详见 §4.1。

#### 加分怎么进包

```text
新 total = clamp01(旧 total + boost)
relevance 不变                              ← 关键：扩散不能改 relevance
```

**为什么扩散不能改 relevance**：绝对闸架在 `relevance` 上。若扩散能改它，
一张本来不该进包的卡就能靠「被邻居带出来」绕过绝对闸，
而绝对闸正是 R2（专注当前位置）的唯一实现。**护栏不能和它要守的判据用同一个通道。**

### 3.6 token 预算与装包

#### token 估算

```text
estimateTokens(text) = CJK字符数 + ceil(非CJK字符数 / 4)

CJK 范围：U+4E00–U+9FFF, U+3400–U+4DBF, U+3000–U+303F, U+FF00–U+FFEF
```

#### 装包

```text
cardBudget = max(0, tokenBudget − overheadTokens) = 900 − 100 = 800

for item in picked:
    text = truncate(card.text, maxCardChars (160))
    cost = estimateTokens(formatCardLine(card, text))
    if kept.length > 0 && used + cost > cardBudget: continue
    kept.push(item); used += cost

若单卡就超预算（kept 为空时）：
    text 再截到 max(8, floor(maxCardChars / 2)) = 80 字
    这是**两级截断**，所以降 maxCardChars 会同时影响两级

最终 tokens = 空包 ? 0 : used + overheadTokens
```

#### 【实测】哪个闸门真的生效

| 卡文本长度 | 实际装入 | 包 tokens | 单卡成本 | 受限于 |
|---|---|---|---|---|
| 20 字 | 7 | 268 | 24 | **maxCards** |
| 50 字 | 7 | 478 | 54 | **maxCards** |
| 80 字 | 7 | 688 | 84 | **maxCards** |
| 100 字 | 7 | 828 | 104 | **maxCards** |
| 120 字 | **6** | 844 | 124 | tokenBudget |
| **160 字** | **4** | 756 | 164 | tokenBudget |
| 200 字 | 4 | 752 | 163 | tokenBudget |

⇒ **哪个是真闸门取决于卡文本长度，不是一个固定答案。**
典型卡文本在 40~100 字，所以**多数情况下 `maxCards = 7` 才是生效的闸门**。

`maxCardChars = 160` 是**截断上限，不是典型长度**。

#### 【实测】overheadTokens 的准确性

```text
一张 60 字卡: tokens = 164
两张 60 字卡: tokens = 228
差值 64 ⇒ 单卡增量成本
overhead ≈ 164 − 64 = 100   ← 与配置值 overheadTokens = 100 精确相等
```

⇒ **`overheadTokens = 100` 是准确的，不是拍脑袋的常量。**
但它只在**非空包**时生效（空包 tokens = 0），所以不能从空包反推。

### 3.7 遗忘

#### 强度衰减

```text
decayStrength(card, now) = clamp01(card.strength × 0.5^(elapsed / effectiveHalfLife))

elapsed = max(0, now − card.updatedAt)
```

**关键实现细节**：强度未变时返回**同一个对象引用**（不是拷贝），
这样调用方可以用 `===` 判断「这一夜到底有没有发生衰减」。

#### 归档（不是删除）

```text
cap = floor( floor(totalActive) × clamp01(maxArchiveRatio) )     # maxArchiveRatio = 0.05

candidates.sort(按 strength 升序 → createdAt 升序 → id 升序)
return candidates.slice(0, cap)
```

**`floor` 是这里的关键**：`maxArchiveRatio = 0.05`，活跃卡少于 20 张时
`cap = 0` ⇒ **一张都不归档**。这是有意的：小库上按比例归档会让库被清空。

永不归档的类别：`feeling`、`promise`、`concept`、`experience`。
这是 R3（细节会忘、感受会留）的直接实现——**感受必须留**。

### 3.8 建图（夜整理的一部分）

#### 话题边（k-NN）

```text
pool = 活跃且未合并的卡，按 (createdAt 升序, id 升序) 排序
候选对 (i, j) 满足：
    similarity = jaccard(tokenSet(i), tokenSet(j))
    topicFloor (0.08) <= similarity < duplicateSimilarity (0.86)

按 (similarity 降序, from 升序, to 升序) 排序
贪心取边，同时维护**双向**度数计数：
    if degree[from] >= topicNeighbors (3): skip
    if degree[to]   >= topicNeighbors (3): skip
    else: 建边，degree[from] += 1, degree[to] += 1
```

**【实测】`topicFloor = 0.08` 的标定**：

| `topicFloor` | 平均度数 | 说明 |
|---|---|---|
| 0.05 | 10.09 | 图近似完全连通，扩散失去意义 |
| **0.08** | **3.75** | 选定值 |
| 更高 | < 3 | 图稀疏，孤立卡增多 |

**为什么用 k-NN 而不是绝对阈值**：k-NN 按构造**封顶度数**（服务 C5 耗时可控）。
绝对阈值在相似度分布随语料漂移时会失效——这里踩过一次真坑：
项目早期 `same-topic` 借用了去重阈值 0.45，而真实语料相似度 99.9 分位只有 0.275
⇒ **图谱恒空**。k-NN 不会犯这个错，因为它只问「谁最像」，不问「够不够像」。

#### 实体边（same-entity）

```text
对每对共享实体的卡：
    weight = |shared| / |union|
    无度数上限                                    ← 见 §5 Q8
```

**两类边处理不对称**：话题边有双向度数上限 3，实体边**没有**。
这导致实体边是 O(n²)。见 §5 Q8。

### 3.9 巩固（夜整理的其余部分）

#### 去重合并

```text
pool = 活跃、未合并、非 summary 的卡，按年龄排序
用并查集分组：
    若 jaccard(card_i, card_j) >= duplicateSimilarity (0.86): union(i, j)
每组内记录组内最小相似度
```

#### 摘要预算

```text
charBudgetOf(sourceChars, levelMaxChars, ratio) =
    max(1, min(levelMaxChars, floor(sourceChars × ratio)))

daily:   levelMaxChars = 180, ratio = 0.5
weekly:  levelMaxChars = 140, ratio = 0.5
monthly: levelMaxChars = 110, ratio = 0.5
```

`min(levelMaxChars, ...)` 保证**层越高越短**（校验强制 `daily ≥ weekly ≥ monthly`）。

#### 感受蒸馏

```text
候选：emotional >= distillMinEmotional (0.28)
  且 不是蒸馏自己产出的（source.sessionId != 'distill'）

按主题词分桶
桶的 recurrence = 桶内卡数
保留 recurrence >= distillMinRecurrence (2) 的桶
每轮最多产出 distillMaxPerRun (3) 张
```

**这是 R3（只留感受）的实现**：把反复出现的情绪聚成一个「感受」。

#### 夜整理的七步顺序（顺序是约束，不是风格）

```text
① 衰减（先释放过期的、降强度）
② 蒸馏感受（必须早于去重，否则感受卡会被去重吃掉）
③ 去重合并
④ 归档
⑤ 摘要（日 → 周 → 月）
⑥ 建图
⑦ 重建索引
```

**② 必须早于 ③ 是踩出来的**：最初蒸馏排在去重之后，实测一条感受都产不出来。

### 3.10 可塑性（目前未启用）

这是「突触效果」的完整形态：边被用一次就变强，不用就变弱。

```text
强化  R(w) = quantize(min(1, w + δ))

衰减  D(w) = if (w <= 0) return 0
             scaled = quantize(w × f)
             return scaled < w ? scaled : stepDownWeight(w)
             # stepDownWeight(w) = quantize(max(0, w − 0.01))

quantize(x) = round(100x) / 100          # 只有 101 个格点
δ 默认 = 0.01
f 默认 = 0.98                            # 每晚衰减 2%
EDGE_WEIGHT_STEP = 0.01                  # 地板步长
```

**⚠️ 这个机制目前没有接线，写 `true` 会在加载期直接失败。**

原因不是没实现，是**数学上不可行**。核心事实：

```text
δ = 0.01 与地板步长 EDGE_WEIGHT_STEP = 0.01 精确相等。
⇒ 「强化一次」被「地板衰减一次」完全抵消。
```

**【实测】** `δ=0.01, f=0.98`，对 101 个格点逐一迭代一夜：

```text
上升 0 格 / 不变 75 格 / 下降 26 格
「不变」区间 = [0, 0.74]，连续 75 个格点
```

⇒ **默认参数下，「这张边被用过一次」是零变化，且没有任何格点会上升。**

完整分析见 §5 Q7。

## 四、我的解法与取舍（含改错的）

这一章记录**已经解决**的问题。每一条的结构是：
**问题 → 我的第一反应（常常是错的）→ 实测发现什么 → 最终解法 → 代价**。

写这一章的目的是：**让你看到我在哪些形状上会犯错**，从而知道该重点怀疑哪里。

### 4.1 判据必须用相对量，不能用绝对阈值（踩了两次）

#### 问题

扩散激活需要选「种子」——哪几张卡强到足以向外传播？

#### 我的第一反应（错）

```text
seeds = [ card for card in scored if card.score.total >= absoluteThreshold ]
```

看起来天经地义：总分过阈值的就是好卡。

#### 实测发现

**总分的下限是 0.33 左右**。完全不相关的两句话也有这个分，因为
`importance / recency / confidence` 各贡献一份，而这三项与查询无关。
实测 12 个样本最低 0.3295，**无一低于 0.18**。

⇒ 这个判据**恒真**。所有卡都是种子。

#### 第二次尝试（也错）

把门槛改成 `absoluteThreshold × seedRatio`，`seedRatio = 1.5`（门槛 0.27）。
仍然恒真——因为下限 0.33 > 0.27。

**教训**：任何「绝对阈值 × 倍数」的标定都落在所有卡之下。**倍数不能救绝对阈值。**

#### 最终解法

用**相对量**：

```text
seedFloor = max(本轮所有卡的 relevance) × seedRatio (0.85)
seeds = [ card if card.relevance >= seedFloor ]
```

`relevance` 无量纲、自动跟随本轮分数分布，衡量的是「这张卡在本轮里够不够强」，
而不是「够不够格」——**后者在这个打分公式下没有意义**。

#### 代价

`relevance` 的相对离散度比 `total` 大，所以 `seedRatio = 0.85` 在不同语料上
选出的种子数会波动。这是可以接受的：种子少一点只是扩散弱一点，不会错。

#### 这个形状的第二次复发

改完种子判据后，**护栏那一半还是错的**：护栏写的是
`selfScore >= absoluteThreshold × minSelfScoreRatio`，而 `minSelfScoreRatio`
被校验强制 `≥ 1`，于是门槛恰好等于 `absoluteThreshold`。

而种子判据现在是 `relevance >= max × 0.85`。两个判据在两把不同的尺子上，
可达区间没有交集 ⇒ **能加分的卡一定已经是种子 ⇒ 受益者恒为空**。

**【实测】** `off` / `shadow` / `on` 三种模式的总分**逐位相同**，观察值 0 条。

⇒ **一个机制有「输入筛选」和「输出护栏」两道阈值时，必须检查两个阈值的
可达区间有没有交集。相等或互相包含时，机制在数学上恒为空集，
而且看不出任何异常：不报错、不崩溃、日志正常、测试全绿。**

### 4.2 一个参数不能承担两个相反职责

#### 问题

建图和冲突判定都需要一个「相似度阈值」。

#### 我的第一反应（错）

共用 `relatedSimilarity = 0.45`。

#### 实测发现

这个参数在两个地方的作用**方向相反**：

```text
在连边里：  阈值越低 → 边越多
在冲突判定里：阈值越低 → 冲突越多（因为判据是 similarity < 阈值）
```

⇒ 调它会让一个机制变好、另一个变坏。**任何取值都是错的。**

#### 最终解法

拆成两个参数：

```text
建图：     topicFloor = 0.08     （越低边越多）
冲突判定： relatedThreshold = 0.45（越低冲突越多）
```

**教训**：一个参数承担两个方向相反的职责时，**必须拆开而不是调值**。
调值只会在两条曲线之间找一个折中，而两条曲线的目标是相反的。

### 4.3 舍入粒度比步长还粗时，机制在数学上停摆

#### 问题

边权要衰减。公式是 `w ← w × 0.98`。

#### 实测发现

边权被量化到 0.01 格点。当 `w` 很小时：

```text
w = 0.02
w × 0.98 = 0.0196
quantize(0.0196) = round(1.96)/100 = 0.02     ← 圆整回原值
```

⇒ **0.01~0.25 共 25 个权重全部是不动点**，永远衰减不下去。

而它不报错、不崩溃、日志正常。

#### 最终解法

加一个「地板」：

```text
scaled = quantize(w × f)
return scaled < w ? scaled : stepDownWeight(w)     # 强制至少降一格
```

#### 代价（这个代价后来变成了 Q7）

地板步长 `EDGE_WEIGHT_STEP = 0.01`，而强化步长 `δ` 默认也是 `0.01`。
两者精确相等 ⇒ 强化被地板完全抵消。

**这个补丁修好了「衰减停摆」，但把缺陷推到了「强化无效」上。**
我当时没意识到：修完测了衰减（确实衰减了），没测「衰减 + 强化」的组合。

### 4.4 判据要读数据层的事实，不要读标签

#### 问题

感受蒸馏需要排除「蒸馏自己产出的卡」，否则会无限自我复制。

#### 我的第一反应（错）

```text
if (card.kind === 'feeling') return false      // 感受卡本身不参与再蒸馏
```

#### 为什么当时看起来对

在旧数据上恰好等价——因为真实情绪句当时进不来（另一个缺陷挡住了它们），
所以「kind 是 feeling 的卡」和「蒸馏产出的卡」是同一个集合。

#### 实测发现

修好上游的情绪通道后，真实情绪句都被判成 `feeling`，
于是**用户的原话卡被一并排除**，候选集又空了。`distilled = 0`。

#### 最终解法

改判**写入时就确定的事实**，而不是分类器的输出：

```text
if (card.source.sessionId === 'distill') return false
```

**教训**：判据要读数据层的事实，不要读标签。标签是分类器的输出，
而分类器会被上游改动影响。

**这条还有一层**：修好上游之后，下游那些「靠上游坏着才成立」的不变量会立刻失效。
所以**改上游时必须把所有依赖它的下游判据都复查一遍**。

### 4.5 主题词的粒度决定整条链路（三级错误）

#### 第一级：切词方式错，桶数恒为 0

感受蒸馏要按「主题词」把卡分桶。我最初写：

```text
themeTerms = card.normalized.split(' ')       // 按空格切
```

而 `normalizeText` 把**所有标点换成空格**，所以 `split(' ')` 切出来的是
**整段长句**，不是词项。两张卡几乎不可能共享整句 ⇒ **桶数恒为 0**。

**【实测】** 5 张情绪全部达标的真实语料，`distilled = 0`。

修法：改用 `tokenize(card.normalized)`。

**注意不能传 `card.text`**：未归一化的文本里标点还在，二元组会跨标点生成
`"，这"` 这类假主题词。

#### 第二级：停用词表漏了程度副词

改完切词后，产出变成了「**『有点』这件事反复牵动我的情绪**」。

根因：停用词表没收「有点 / 有些 / 非常 / 感觉 / 觉得」这类程度副词与感知动词。
它们区分度为零、却高频出现在情绪句里，于是「有点烦」和「有点慌」被聚成同一件事。

修法：**修在停用词表一处**，不在主题词函数里另加一层过滤
（否则就有两个真相源）。

**教训**：`distilled` 从 2 降到 1 不是退化——**「产出变多」和「产出变对」是两件事**。
而且 `distilled` 非零、格式完全正确，**只有读文本才能发现它在说假话**。

### 4.6 门控的通道集合决定了什么能进来

#### 问题

每轮对话都要判断「这一轮值不值得记」。原来的门控有四条通道：

```text
1. 用户侧命中信号词
2. 用户侧命中到期词
3. 助手侧命中信号词（且助手文本够长）
4. 双方文本都够长
```

#### 实测发现

**「我快崩溃了」这五个字，四条通道一条都不放行。**

```text
通道 1/2：没有信号词、没有时间词
通道 3：没有助手输出
通道 4：太短
```

实测情绪句通过率 **1/10**。更糟的是：

```text
高情绪组通过率 17%  <  低情绪组通过率 43%
```

⇒ **反相关**。情绪越强越留不下来。这与 R4（激素是关键）直接冲突。

#### 最终解法

加第五条通道：

```text
5. 用户侧 emotional >= emotionalGateThreshold (0.28)
```

并把显著性公式从「加权和」改成 **`max`**：

```text
infoRaw = 长度分×0.42 + 信号分×0.36 + 实体分×0.22
emoRaw  = clamp01(emotional)
salience = min(1, max(infoRaw, emoRaw))
```

**为什么是 `max` 而不是加权**：情绪项与信息项是两条**独立**的「值得记」理由。
加权会让决策句降 18%（【实测】），`max` 则保证加新通道时不动原有分数。

修复后：情绪句出卡 8/10、高情绪组 100%、反相关消除。

**教训**：**四道串联闸，每道单独看都合理，合起来让整条路径产出恒为零。**
判断一条路径是否有效，不能逐闸看，必须看串联后的整体。

### 4.7 一个间接闭环比直接闭环更难发现

#### 问题

插件每轮把焦点包注入模型上下文。宿主的 `user/message` 事件同时承载：

```text
① 用户真实输入
② 运行时上下文快照（本插件注入的焦点包就在里面）
③ 压缩摘要（合成消息）
```

#### 我的第一反应（错）

只按 `event.type` 分派，不看 `source.kind`。

#### 实测发现

用户每轮说**完全相同**的一句话，跑 6 轮：

```text
A 组（宿主回送上下文快照）：20 张卡，注入长度 171 → 845
B 组（不回送）：            6 张卡
```

产出里出现：

```text
- [事件] - [事件] - [事件] Current runtime context…
```

⇒ **插件把自己的注入内容当成用户原话吃了回去，逐轮自我复制。**
嵌套深度 1→5，还污染伪造出 `supersedes@1.00` 这种假关系。

#### 最终解法

**白名单**，不是黑名单：

```text
只接受 source.kind === 'user'（人类真实输入）
```

**为什么必须是白名单**：合成来源是**开放集合**（宿主侧至少有 21 种 kind），
黑名单挡不完。今天挡住 `runtime-context`，明天多一个 `compact-checkpoint` 就漏了。

#### 为什么假宿主测试全绿

测试用的假宿主构造 `userEvent()` 时**根本不带 `source` 字段**，
而生产代码**不读** `source`。两边互相掩护，缺陷从中间溜过去。

**教训**：假宿主的测试永远绿，因为普通对象不会像真实 Proxy 那样抛错。
**声明一个没有消费者的依赖，等于凭空拉高激活门槛而没人发现。**

### 4.8 权重不可观测的测试是装饰

#### 问题

怎么测「这条路径真的执行了」？

#### 踩过的坑

我写过一条断言：

```text
assert.ok(after >= before)          // 「扩散能让分数变好」
```

它一直是绿的。而真相是 `after === before`——**等式成立也算通过**。

**修法**：要求「变好」必须写 `>`。

同源问题还有一个更隐蔽的：

```text
assert.ok(result.cards.length <= maxCards)      // 实测余量为 0
```

把 `maxCards` 改成 100 或让硬上限整个失效，它照样绿。

⇒ **「余量为 0」和「断言有牙」是两件事。**

#### 我的规则

1. 要求「变好」写 `>`，不写 `>=`。
2. 断言「空」必须配一条**配对的反向对照**（证明非空的情况真的能非空）。
3. 反向验证：把实现改坏，确认测试**精确地**变红（只红相关的一两条，
   红一片说明测的是别的东西，一条不红说明这条测试是装饰）。
4. **变异未命中必须显式报错**——文本替换没命中时，代码一行没变，测试当然全绿，
   这看起来和「验证通过」完全一样。

### Q3：`maxHops = 2` 在默认参数下不可观测

#### 现状

**【实测】** 链 `a − b − c`，边权全 1.0，种子 `a`（能量 0.5）：

```text
默认 (hopDecay=0.5, maxBoost=0.12):
  b: raw = 0.5 × 1.0 × 0.5 = 0.25   → boost = min(0.12, 0.25) = 0.12
  c: raw = 0.25 × 1.0 × 0.5 = 0.125 → boost = min(0.12, 0.125) = 0.12

maxBoost = 1 时:
  b: boost = 0.25
  c: boost = 0.125                    ← 跳数信息可见
```

⇒ **一跳与两跳加分完全相同（都撞顶 0.12）。`maxHops` 这个参数在默认下是死的。**

#### 卡在哪

这是 R5（图谱）+ 用户「突触效果」要求的核心机制，但它不产生任何可观测差异。

约束：

```text
raw₁ = E × w × hopDecay
raw₂ = E × w² × hopDecay²

要让两跳不被截平，需 raw₂ < maxBoost
```

代入 `E = 0.5`（种子总分典型值）、`w` 常见 0.1~0.3、`hopDecay = 0.5`：

```text
raw₂ = 0.5 × w² × 0.25 = 0.125 w²
w = 0.3 → raw₂ = 0.01125
w = 0.1 → raw₂ = 0.00125
```

所以 `maxBoost` 需要降到 0.01 量级才能让两跳可见——但那时单跳加分也小到
无法影响排序。

#### 请裁决

1. **`maxBoost` 与 `hopDecay × 边权` 之间应满足什么不等式，才能让 `maxHops` 可观测？**
   请给出在真实边权分布（0.1~0.3）下的可行参数组合，或证明不存在。
2. **`maxBoost` 的本意是什么？**
   - 「防止单卡被扩散过度推高」→ 要它小；
   - 「防止图密度影响分数尺度」→ 要它随图密度自适应。

   这两个目的对 `maxBoost` 的要求相反。请判断哪一个才是应该保的。
3. **是否应改成按 `raw` 归一化后再乘 `maxBoost`？**
   ```text
   boost = maxBoost × raw / maxRaw
   ```
   这样跳数信息保留、加分上限也保留。代价是**加分变成相对的**——
   同一张卡在不同候选池里拿到不同加分。**ST-1（确定性）还成立吗？**
   （注意：确定性要求的是「同样输入 → 同样输出」，而候选池是输入的一部分，
   所以严格说仍然确定。但它破坏了「同一张卡在不同查询下加分可比」这个直觉。）

### Q7：衰减与强化的步长必须解耦（可塑性不可行性的根）

#### 两个算子

```text
强化  R(w) = quantize(min(1, w + δ))

衰减  D(w) = if (w <= 0) return 0
             scaled = quantize(w × f)
             return scaled < w ? scaled : stepDownWeight(w)
             # stepDownWeight(w) = quantize(max(0, w − 0.01))

quantize(x) = round(100x) / 100        # 101 个格点
δ 默认 = 0.01
f 默认 = 0.98
EDGE_WEIGHT_STEP = 0.01                # 地板步长
```

#### 核心事实（【实测】）

**`δ = 0.01` 与地板步长 `0.01` 精确相等。**

于是「一次共激活」的净变化：

```text
w ← R(w) = quantize(w + 0.01)
w ← D(w) = quantize(w × 0.98)，若没变小则 w − 0.01
```

对 101 个格点逐一迭代一夜：

| `δ` | `f` | 上升 | 不变 | 下降 |
|---|---|---|---|---|
| 0.01 | 0.98 | **0** | 75 | 26 |
| 0.02 | 0.98 | 74 | 25 | 2 |
| 0.01 | 0.95 | **0** | 29 | 72 |
| 0.01 | 0.914 | **0** | 17 | 84 |

⇒ **默认参数下，「用过一次」是零变化，且 101 个格点里 0 个上升。**
「不变」区间是 `[0, 0.74]`，连续 75 个格点。

而新建边的初始权重来自相似度（常见 0.1~0.3，**正落在这个区间内**），
所以**新建边若每夜只共激活一次，权重永不增长**。

#### 第二层：档数（分辨率）

即使不管抵消问题，还有一个更根本的限制。

**「档数」这个词有歧义，下面这张表用的是定义 A，不是定义 B。**
两个定义都自然，但结果差 25 倍，所以必须先说清：

```text
定义 A（本表用这个）：固定初值 w0 = 0.5，
        扫「一夜里共激活 n 次」，n = 1..30，
        各自迭代 2000 夜到稳态，数能到达多少个不同终值。
        → 问的是「用 1 次 / 2 次 / … / 30 次，最终强度分不分得开」

定义 B（另一种自然读法）：固定 n = 1，
        扫初值 w0 = 0.01..1.00，各自迭代到稳态，数终值个数。
        → 问的是「起点不同，最终强度分不分得开」
```

| 定义 | `f=0.98` 档数 | `f=0.95` | `f=0.914` |
|---|---|---|---|
| **A**（本表） | **3** | **6** | **10** |
| B | 74 | 28 | 16 |

**本文其余各节说「3 档 / 6 档 / 10 档」，一律指定义 A。**
定义 A 才是与「可塑性有没有用」相关的那个量：可塑性要区分的是
「这条边被用过几次」，不是「这条边从哪个权重起步」。
定义 B 数字更大，但它衡量的是另一件事——**拿它来反驳「分辨率不足」
会得出相反结论**，所以两个数不能混用。

| `f` | 实测档数（定义 A） |
|---|---|
| 0.995 | 2 |
| 0.99 | 2 |
| 0.98 | 3 |
| 0.95 | 6 |
| 0.93 | 8 |
| 0.914 | 10 |
| ≤ 0.914 | 10（饱和） |

**⚠️ 我在这里犯过两次推导错误，必须记录：**

1. 我先写了一个上界 `N < (1−f)/δ`。**被实测证伪**：
   `f=0.98` 实测 3 档而上界算得 2.00；`f=0.93` 实测 8 档而上界 7.53。
2. 我改成 `N ≈ (1−f)/(δ·f)`，**仍被证伪**（`f=0.93` 算得 7.53，实测 8）。
   而且**没有任何候选公式能覆盖全部 f**。

还有两个额外发现：

- **档数依赖初值 `w0`**：`f=0.98` 时 `w0 ∈ {0.1, 0.3, 0.5, 0.8}` 都是 3 档，
  **`w0 = 1.0` 只有 2 档**。
- **同一 `n` 有多个吸引子**：`δ=0.01, f=0.98` 时，`n=1` 迭代后落到
  **75 个不同的终值**，其中 74 个是自身不动点；`n=2` 落到 25 个终值；`n=3` 才收敛到 1 个。
  （注意这条数的是**定义 B**：固定 `n=1`、扫 `w0`。所以它和上表的「3 档」
  不矛盾——上表固定 `w0=0.5`、扫 `n`。**同一个系统，换一个维度扫，数字差 25 倍。**
  这正是「档数」这个词必须带定义的原因。）

⇒ **`w*(n)` 不是良定义函数。** 教科书式的「不动点」推导在这里无效，
因为系统是**离散状态机**（101 个状态），不是连续微分方程。

**根本原因**：连续域推导被当成了离散系统的结论。
`quantize(x) = round(100x)/100` 只有 101 个状态，必须用**状态机分析**。

#### 第三层：饱和式也不是出路

我试过换成 `w += δ(cap − w)`（指数逼近）。**【实测】**：

| `f` | δ 从 0.02 扫到 0.30 的档数 |
|---|---|
| 0.95 | 恒为 5（0.30 时 4） |
| 0.98 | 恒为 2~3 |

⇒ **对 δ 完全不敏感，不是修复。**

#### 卡在哪

```text
「分辨率最高」  ⇒ 需要 δ 小（δ=0.01 是档数最大化的唯一选择）
「一次使用有效」⇒ 需要 δ > 地板步长
```

**两者互相排斥。** 而地板步长不是可随便调的——它是修 §4.3（衰减停摆）的补丁。

#### 请裁决

1. **`δ` 与地板步长必须解耦——但解耦到多少？**
   请给出一个同时满足「档数够多」和「一次使用有效」的方案，**或证明不存在**。
2. **地板步长为什么必须是 `EDGE_WEIGHT_STEP`？**
   它现在是「至少降一格」。若改成 `quantize(w × f)` 且**不**兜底
   （允许 `scaled === w`，即真的不动），会发生什么？§4.3 的 25 个不动点会回来吗？
   请判断「地板」这个补丁的必要性——它是正解，还是把缺陷推到了另一处？
3. **量化精度从 0.01 提高到 0.001 是否可行？**
   101 格点 → 1001 格点。档数会怎么变？**请重新推导，不要套用本文档里
   已被证伪的公式。** 代价：边权存储从 2 位小数变 3 位小数，
   日志体积与幂等键都会变——这算不算「为一个未启用的机制改变持久格式」？
4. **有没有完全不同的强化模型？** 例如：
   - 把边权改成**整数计数**（用了几次），衰减时用「最后一次使用距今多久」计算
     当前权重（即把权重变成派生量而非存储量）。
   - 这样「用了 1 次」和「用了 100 次」天然可分，而量化格问题消失。
   请评估这个方向，以及它对「边权必须是持久状态」的影响。

### Q8：实体边没有度数上界，是 O(n²)（新发现）

#### 现状

建图对两类边处理不对称：

| 边类型 | 度数约束 | 【实测】 |
|---|---|---|
| `same-topic` | k-NN 双向约束，每端点 ≤ 3 | ✅ 严格 ≤ 3 |
| `same-entity` | **无任何约束** | ❌ 见下表 |

#### 【实测】边数随规模的增长

场景：每卡 3 个实体，实体池 40（真实语料里实体高度重复）：

⇒ **边数 ≈ 4 倍增长 ⇒ O(n²)。**

| **5000** | 500 | **122500** | **130000** | **3621 ms** |

`maxCardsPerRun = 5000`。⇒ 单次夜整理**光建图就 3.6 秒**，产出 **13 万条边**。

#### 极端场景

实体池 = 5（所有人共享同一批实体）：`n = 400` 时最大总度数 **242**，接近完全图。

#### 卡在哪

话题边用 k-NN 天然封顶度数。实体边的问题是：**「共享实体」是一个二值判据，
天然不封顶**——一个常见实体（比如项目名）会把所有卡连起来。

但直接加度数上限也有代价：`same-entity` 的语义是「它们说的是同一个东西」，
按相似度排序截断可能截掉真正重要的关系。

#### 请裁决

1. **实体边应该怎么封顶？**
   候选：
   - 双向度数上限（同话题边，`K = 3`）
   - 按「共享实体数」降序取前 K
   - 按实体**稀有度**加权（IDF 思路：常见实体权重低，罕见实体权重高）
   - 只对「罕见实体」建边（如出现在 < 5% 卡里的实体）

   请给出判据形式，并说明它如何避免「常见实体把全图连通」。
2. **O(n²) 的候选对枚举本身是否可接受？**
   即使封顶了建边数，**枚举所有对**仍然是 O(n²)。
   在 `n = 5000` 时是 1250 万对。是否需要改用倒排（按实体分组，组内两两）？
   注意组内两两在「常见实体」上仍是 O(n²)。
3. **实体边是否应该和话题边用同一个度数预算？**
   当前最大总度数会到 102（话题 ≤ 3 + 实体无上限）。这个量级下
   扩散的「能量分散」会让所有卡加分趋同（见 Q4）。请判断是否有必要
   对**总度数**（而非分类型度数）设上限。

| **P0** | **Q6**（冲突判据） | 当前一个坏判据的产出被当成事实消费。要么修，要么删。 |

| **不紧急** | **Q9**（共激活信号） | 这是产品决策，不是数学问题。但它是 Q7 的前置条件。 |

### 6.4 我需要你特别小心的三件事

1. **不要假设「代码里实现了」等于「生效了」。** 本项目有 4 个缺陷是
   「机制完整实现、单元测试全绿、配置齐备、生产代码零调用方」。
   我给出的每条公式，都可能没有接在真实路径上——我会注明，但请你也怀疑。

2. **不要只看公式，要看两个阈值的可达区间有没有交集。** 本项目最严重的一类
   缺陷是「两个阈值相等 ⇒ 机制恒为空」，它不报错、不崩溃、日志正常、测试全绿。

3. **「档数」「不动点」「收敛」这些词在离散系统里有歧义。**
   `quantize(x) = round(100x)/100` 只有 101 个状态，必须用状态机分析，
   不能用微分方程。我在这上面错了两次。
