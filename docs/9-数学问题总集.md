## 二、已实现的数学

> 本章每个算子给三件事：**公式**、**常量**、**标定依据**。
> 常量全部落在 `src/core/config/defaults.ts`，不散落字面量（AGENTS.md 硬性约定 6）。

### 2.1 语义分 `semanticScore`

```text
semanticScore = clamp01(
    文本覆盖 × 0.72
  + 标签命中 × 0.14
  + 实体命中 × 0.14
)
```

- **文本覆盖** = `coverage(tokenSet(card.normalized), query.tokens)` = `|命中词项| / |查询词项|`
- **标签命中** = 标签词集与查询词集的 `coverage`
- **实体命中** = 实体词集与查询词集的 `coverage`

三项系数 `0.72 / 0.14 / 0.14` 之和为 1，所以 `semanticScore ∈ [0,1]` 不需要再夹。

**标定依据**：正文是主要语义载体，标签与实体是辅助线索。0.72 让「正文完全不重合、
只有标签重合」的卡最高拿 0.14——不足以单独过 `absoluteThreshold`（0.06 在
`relevance` 尺度上，对应 `semantic ≈ 0.0743`，见 §2.6），所以**标签无法把无关卡拉进包**。

### 2.2 重要性分 `importanceScore`

```text
importanceScore = clamp01(
    salience     × 0.55
  + emotional    × 0.25
  + accessBoost  × 0.20
)

accessBoost = min(1, log1p(accessCount) / log1p(12))
```

**为什么用 `log1p` 而不是线性**：访问次数是重尾分布（少数卡被反复访问），
线性会把「访问过 100 次」压成绝对优势。`log1p` 让第 1 次访问贡献最大
（`log1p(1)/log1p(12) = 0.279`），第 12 次才饱和到 1。

**为什么分母是 12 而不是别的**：`log1p(12) ≈ 2.565`，配 0.20 权重意味着
**访问 12 次后这一项对总分的影响封顶在 0.20/0.90 × 0.20 ≈ 0.044**。
选 12 是因为它对应「两周内每天看一次」——超过这个频次，边际价值应该让位于内容本身。

### 2.3 新鲜度分 `recencyScore`

```text
recencyScore(ageMs, halfLifeMs) =
    halfLifeMs <= 0 ? 0
  : ageMs <= 0     ? 1
  : 2^(−ageMs / halfLifeMs)
```

标准指数衰减。`ageMs <= 0`（未来时间或同刻）返回 1 而不是外推——避免时钟回拨时出现 `> 1`。

**有效半衰期**（情绪与访问频次延长寿命）：

```text
effectiveHalfLife = base
                  × (1 + clamp01(emotional) × (emotionalHalfLifeBoost − 1))
                  × (1 + min(1, log1p(accessCount) / log1p(20)))

base = 14 天（1_209_600_000 ms）
emotionalHalfLifeBoost = 2.0
```

起源 L3（无编号·激素是关键）与 L11（无编号·细节会忘）的交点：
**强烈情绪的事件记得更久**。做成半衰期的**乘数**而不是额外加分，
因为「忘得慢」和「分得高」是两件事——前者影响它在多久之后仍然可见，后者影响它排第几。

两处 `log1p` 分母不同（重要性用 12、半衰期用 20），这是**刻意的**：
重要性回答「这张卡有多重要」，半衰期回答「这张卡能活多久」，两者的饱和点不必相同。
两处都用 12 会诱使读者以为它们是同一个量。

### 2.4 目标分 `goalScore`

```text
goalScore = coverage(tokenSet(card.normalized), query.goalTokens)
```

**关键约定：目标缺席时贡献 0，但权重仍留在分母里。**

`score.ts` 的注释记着这个坑：

> 我最初的做法是「没目标就把 `w.goal` 从分母里摘掉」，理由是「不知道不该算 0 分」。
> 归一化分因此整体上浮 1/0.9 ≈ 11%，一张 100 个半衰期、语义相关为 0 的死卡
> 从 0.168 抬到 0.187，越过了 `absoluteThreshold: 0.18`——测试当场抓到。

取「缺失即中性」的理由：`goalText` 为空曾经是一个**宿主侧 bug**，
按摘分母的写法，这个 bug 会让每张卡的分数都涨 11%、更容易进焦点包
——**缺陷反而让召回看起来更好，没人会去修它**。

### 2.5 冲突惩罚 `conflictPenalty`

```text
conflictPenalty = clamp01(min(1, |card.conflictOf| / 3))
```

冲突数越多惩罚越重，但封顶，避免一条卡因多处冲突被彻底埋掉。

**注意**：`|conflictOf| = 3` 就饱和到 1。这个 3 是**未经标定的经验值**，
见 Q6 的附带问题。

### 2.6 总分合成 `scoreCard`

```text
weights = { semantic: 0.42, importance: 0.18, recency: 0.20,
            goal: 0.10, confidence: 0.10, conflict: 0.25 }

正权重和 positiveWeight = 0.42 + 0.18 + 0.20 + 0.10 + 0.10 = 1.00

normalized = (semantic×0.42 + importance×0.18 + recency×0.20
            + goal×0.10 + confidence×0.10) / positiveWeight

total = clamp01(normalized − conflictPenalty × 0.25)
```

**相关分量 `relevance`（缺陷二十六引入）**：

```text
relevantWeight = semantic权重 + goal权重 = 0.42 + 0.10 = 0.52

relevance = clamp01((semantic×0.42 + goal×0.10) / relevantWeight)
```

#### 为什么必须有两个分量

`total` 有 **0.48 的权重与查询无关**（`importance 0.18 + recency 0.20 + confidence 0.10`）。
这意味着：

- **一张语义为 0 的卡，`total` 仍可达到 `(0.18×imp + 0.20×rec + 0.10×conf) / 1.00`。**
  各分项取 0.5 → **0.2400**；各分项取 1.0 → **0.4800**。
- 实测无关卡 `total` 落在 0.313~0.377，相关卡 0.345~，**重叠 33.3%**。

⇒ **在 `total` 这把尺子上，不存在能分开「相关」与「无关」的阈值。**
任何拿 `total` 去比 `absoluteThreshold` 的护栏都会变成恒真
（缺陷二十六、三十二都是这个形状，坏过两次）。

#### `relevance` 的一个已知收缩

```text
goal = 0 时（无目标查询）：
relevance = semantic × 0.42/0.52 = semantic × 0.8077
```

即**无目标时 `relevance` 系统性打 80.8 折**。而 `absoluteThreshold = 0.06`
是对 `relevance` 标定的，所以：

```text
semantic ≥ 0.06 / 0.8077 = 0.0743 才过闸
```

**这不是 bug**（分母恒定的代价），但它意味着**同一个查询加上 `goalText` 与不加，
过闸难度相差 23.8%**。见 Q1。

### 2.7 三道闸 `applyThresholds`（FR-B2）

```text
relativeFloor = scored[0].score.total × relativeThreshold   (0.55)

for item in scored（已按 total 降序）:
    if picked.length >= maxCards (7):            break      ← 硬上限
    if item.score.relevance < absoluteThreshold (0.06): continue   ← 绝对闸
    if item.score.total < relativeFloor:         continue   ← 相对闸
    picked.push(item)
```

**两道闸用两把不同的尺子，这是修缺陷二十六时定下来的**：

| 闸 | 尺子 | 回答的问题 |
|---|---|---|
| 绝对闸 | `relevance` | 「有没有关系」 |
| 相对闸 | `total` | 「比本轮最好的差多少」 |

**为什么相对闸不能也挪到 `relevance`**（`pack.ts` 注释里的实测）：

> SC-2 场景里目标卡 `relevance` 0.1113、相对闸 0.1121，**差 0.0008 被挡出包**，
> 而它在 `total` 尺度上（0.3925 vs 闸 0.2522）本该轻松通过。
> 根因是 `relevance` 的相对离散度比 `total` 大（同批候选 0.546 vs 0.856），
> 同一个 `relativeThreshold` 在 `relevance` 尺度上苛刻得多。

⇒ **两把尺子不是不一致，是两道闸问的问题不同。**

### 2.8 扩散激活 `spreadActivation`（FR-G1）

#### 算法

```text
输入：seeds（种子卡 + 能量）、adjacency（邻接表）、selfScores（relevance）、config

if mode == 'off':  return []            # shadow 必须照常算
if seeds.length == 0: return []

selfFloor = absoluteThreshold × minSelfScoreRatio      # 0.06 × 1.0 = 0.06

对每个种子（按 id 升序，保证浮点累加顺序固定）：
    visited = {seed.id}
    frontier = [{ id: seed.id, energy: seed.score }]
    for hop in 0..maxHops−1:
        for node in frontier:
            for edge in adjacency[node.id]:
                target = 另一端点（反向时需 canTraverse）
                if target in visited: continue
                visited.add(target)
                energy = node.energy × edge.weight × hopDecay
                if energy <= 0: continue
                accumulated[target] += energy              # ← 多路径直接相加
                sourcesOf[target].add(seed.id)

对每个 target:
    if target 是种子: continue                              # 种子不给自己加分
    if selfScores[target] < selfFloor: continue             # 护栏
    boost = min(maxBoost, accumulated[target])              # 截平
    results.push({ id, boost, sources, raw: accumulated, selfScore })

results.sort(按 raw 降序 → selfScore 降序 → id 升序)
return results.slice(0, maxAffected)
```

#### 常量

| 参数 | 值 | 含义 |
|---|---|---|
| `hopDecay` | 0.5 | 每跳能量乘数 |
| `maxHops` | 2 | 最大跳数 |
| `maxBoost` | 0.12 | 单卡加分上限 |
| `minSelfScoreRatio` | 1.0 | 护栏倍数（校验强制 ≥ 1） |
| `seedRatio` | 0.85 | 种子门槛 = 本轮最高 `relevance` × 0.85 |
| `maxAffected` | 5 | 最多影响几张卡 |
| `mode` | `'shadow'`（默认）/ `'on'`（出厂 patch） | 三态 |

#### 种子选择（`mergeSpread`）

```text
maxScore  = max(item.score.relevance for item in scored)
seedFloor = maxScore × seedRatio            # 0.85

seeds = [ { id, score: item.score.total } for item
          if item.score.relevance >= seedFloor ]
```

**判据用 `relevance`（够不够格当种子），能量用 `total`（能撒多少）。**

两个用途不同，用不同的量是刻意的——但这是缺陷三十二的修复结果：
原来判据也用 `total`，而 `total` 有 0.48 权重与查询无关，把相对离散度压平到
**0.9059（同质）/ 0.9655（异质）**，`seedRatio = 0.85` 落在其下
⇒ **所有卡都是种子 ⇒ 受益者恒为 0**。

#### 已知的数学性质（实测，见 §4 Q3/Q4）

**① `maxHops = 2` 在默认参数下不可观测。**

链 `a − b − c`，边权全 1.0，种子 `a`（能量 0.5）：

```text
默认 (hopDecay=0.5, maxBoost=0.12):
  b: raw = 0.5 × 1.0 × 0.5 = 0.25  → boost = min(0.12, 0.25) = 0.12
  c: raw = 0.25 × 1.0 × 0.5 = 0.125 → boost = min(0.12, 0.125) = 0.12

maxBoost=1 时:
  b: boost = 0.25
  c: boost = 0.125
```

⇒ **一跳与两跳在默认参数下加分完全相同（都撞顶 0.12）。**
`maxHops` 这个参数只在 `maxBoost` 抬高时才可观测。

**② 稠密图上 `raw` 的不同取值数坍缩。**

| 图型 | 节点 | 边数 | `raw` 不同取值数 | 撞顶数 |
|---|---|---|---|---|
| 环 | 10 | 10 | 2 | 0/4 |
| 环 | 20 | 20 | 2 | 0/4 |
| 完全图 | 8 | 28 | **1** | 0/7 |
| 完全图 | 12 | 66 | **1** | 0/11 |

⇒ 在完全图上所有受益卡的 `raw` **完全相同**，截断排序退化成按 `id` 取
（`id` 是内容哈希，与相关性无关）。这正是缺陷二十二/三十二修过一次的形状。

### 2.9 写入侧打分

#### 门控 `gateTurn`（五条通道，任一放行）

```text
1. userSignals       — 用户侧命中信号词
2. userDue           — 用户侧命中到期词
3. assistantSignals  — 助手侧命中信号词（且 assistantText ≥ minAssistantChars = 40）
4. userLong && assistantLong  — 双方都长（≥ minTextChars = 6 / minAssistantChars = 40）
5. emotionalPass     — 用户侧 emotional ≥ emotionalGateThreshold = 0.28
```

**缺陷二十八的教训**：情绪通道原本**不在**这五条里，导致
「我快崩溃了」被四道串联闸全部挡掉，实测情绪句通过率 **1/10**，
且**高情绪组 17% < 低情绪组 43%（反相关）**——情绪越强越留不下来。

#### 显著性 `computeSalience`

```text
chars = 句子字符数
lengthScore = chars < 8  ? 0.15
            : chars < 20 ? 0.50
            : chars <= 80 ? 1.00
            : 0.70
signalScore = min(1, |signals| / 3)
entityScore = min(1, |entities| / 3)

infoRaw = lengthScore × 0.42 + signalScore × 0.36 + entityScore × 0.22
emoRaw  = clamp01(emotional)

salience = min(1, max(infoRaw, emoRaw))        ← max，不是加权和
```

**为什么是 `max` 而不是加权**：情绪项与信息项是两条**独立**的「值得记」理由。
加权会让决策句降 18%（实测），`max` 则保证加新通道时不动原有分数。

写入阈值：`salience < 0.25` 丢弃。

#### 情绪强度 `computeEmotional`

```text
strong = 强情绪词命中数（词表来自 config.extraction.emotionalStrongKeywords）
medium = 中情绪词命中数
marks  = 感叹号与问号个数

emotional = clamp01(min(1, strong × 0.40 + medium × 0.18 + marks × 0.12))
```

**缺陷二十八**：词表原本写死在正则里，「失望 / 慌 / 焦虑 / 委屈 / 疲惫」
一个都不算数，情绪通道被系统性低估——不报错、不崩溃，只是安静地少记东西。

#### 置信度 `computeConfidence`

```text
base = fromUser ? 0.85 : 0.62
if 命中「可能|也许|大概|或许|不确定|好像|似乎|据说」: base -= 0.25
if 命中「确定|一定|实测|验证过|确认|确实|必然」:     base += 0.12

confidence = clamp(base, 0.05, 1.0)
```

**助手侧基础置信度 0.62 低于用户侧 0.85**：用户原话是事实，助手输出是推断。

### 2.10 衰减 `decayStrength`

```text
decayStrength(card, now, config) =
    clamp01(card.strength × 0.5^(elapsed / effectiveHalfLife))

elapsed = max(0, now − card.updatedAt)
```

`decayCard` 在强度未变时**返回同一个对象引用**（不是拷贝），
这样调用方可以用 `===` 判断是否发生衰减。

### 2.11 归档 `applyArchiveRatio`（FR-C4）

```text
cap = floor(floor(totalActive) × clamp01(maxArchiveRatio))     # maxArchiveRatio = 0.05

candidates.sort(按 strength 升序 → createdAt 升序 → id 升序)
return candidates.slice(0, cap)
```

**`floor` 是这里的关键**：`maxArchiveRatio = 0.05`，活跃卡 < 20 张时
`cap = 0` ⇒ **一张都不归档**。这是有意的：小库上按比例归档会让库被清空。

永不归档类别（`neverArchiveKinds`）：`feeling`、`promise`、`concept`、`experience`。
起源 L11（无编号·细节会忘）的直接承接：感受必须留。

### 2.12 摘要预算 `charBudgetOf`

```text
charBudgetOf(sourceChars, levelMaxChars, ratio) =
    max(1, min(levelMaxChars, floor(sourceChars × ratio)))

daily:   levelMaxChars = 180, ratio = 0.5
weekly:  levelMaxChars = 140, ratio = 0.5
monthly: levelMaxChars = 110, ratio = 0.5
```

`min(levelMaxChars, ...)` 保证**层越高越短**（校验强制 `daily ≥ weekly ≥ monthly`）。

**缺陷**：日摘要只有 30 字时，`floor(30 × 0.5) = 15 < 180`，
压缩逻辑其实从未生效——但「压缩比 < ratio」那条断言**依然绿**，

触上限截平、ratio 真的被乘进去）。

## 三、已解决的历史数学错误

> 这一章的意义：**这些错误的形状会重复出现**。
> 每一条都是「数学上停摆，但代码不报错、不崩溃、日志正常、测试全绿」。

### 3.1 缺陷二十：量化格永久卡死衰减

```text
衰减 w ← quantize(w × 0.98)，quantize(x) = round(100x) / 100
```

`0.02 × w` 小于半格 `0.005` 时圆整回原值 ⇒
**`w ∈ {0.01, 0.02, …, 0.25}` 共 25 个权重全是不动点**，永远衰减不下去。

**教训**：**舍入粒度比步长还粗时，机制在数学上停摆，而它不报错、不崩溃、日志正常。**

### 3.2 缺陷二十一：边权不是持久状态

`same-topic` 边**每夜重新推导**，剪枝 91 次被重建 91 次
⇒ 只接「衰减 + 剪枝」得到的是**单调消亡**，不是遗忘。

**教训**：**边权如果不是持久状态而是每夜重新推导的量，可塑性就没有意义。**

### 3.3 缺陷二十二：`same-topic` 借用去重阈值

`same-topic` 用了 `relatedSimilarity = 0.45`，而真实语料相似度
**99.9 分位只有 0.275** ⇒ 图谱恒空。

**教训**：**手写语料会放大相似度，真实文本才能定标。**

### 3.4 缺陷二十六 / 三十二：两道闸各用一把尺子

**缺陷二十六**：`absoluteThreshold` 既当闸门又当分数地板。
冲突封顶把 `total` **精确钳在阈值上**（10/161 张卡总分完全相同 `0.180000000`），
分差 0.031 → 0.000，排序退化成按 `id`（内容哈希）。

**缺陷三十二**：种子判据用 `total`、护栏用 `relevance`
⇒ 所有卡都是种子 ⇒ 受益者恒空 ⇒ `off`/`shadow`/`on` 三种模式总分**逐位相同**。

**教训**：
- **阈值低于打分的自然地板时，它恒真。**
- **一个判据方向错了，调它的数值只会让它在错的路上更精确。**
- **「阈值换尺子之后，所有拿它做乘数的护栏都要逐个复查，而它们的失效方式一律是恒真。」**

### 3.5 缺陷三十三：可塑性是空操作

`plasticityEnabled` 打开与关闭各跑 10 夜，**边权与边数逐位相同**。
三个纯函数实现齐全、55 条单测全绿、配置齐备、校验完整——
**`grep` 生产代码零调用方**。

**教训**：**「代码里有」+「测试里有」+「配置里有」+「校验里有」≠「生产路径会走到」。**

### 3.6 ⚠️ 本文档对 `docs/8` 的三处更正

> **这三处是写本文档时用探针发现的。`docs/8` 里的数字是把公式值当成了实测值，
> 或者上界推导有误。以本节为准。**

#### 更正一：档数上界 `N < (1−f)/δ` 是**错的**

`docs/8` 事实 3 声称档数上界 `N < (1−f)/δ`。实测（`δ=0.01, f=0.98, w0=0.5`）：

```text
n= 1 → 0.50
n= 2 → 0.74
n= 3 → 0.98
n≥ 4 → 0.98

档 = {0.50, 0.74, 0.98}  共 3 档
上界 (1−f)/δ = 2.00
```

⇒ **实测 3 档 > 上界 2，上界被违反。**

**原因**：`n=1` 的不动点带是 `[0, 0.74]`，`n=2` 的带是 `[0.74, 0.98]`。
两带在 0.74 处相接但几乎不重叠，起点 0.5 落在 `n=1` 的带里、`n=2` 时被推到 0.98。
**所以「档」不是「不动点带的个数」，而是「从给定初值出发能到达的终值个数」。**

正确的关系是相邻档中心差：

```text
Δw* = δ·f/(1−f)
⇒ N ≈ (1−f)/(δ·f)
```

但实测**没有一个候选公式在所有 `f` 上都对**：

| `f` | 实测档数 | `(1−f)/δ` | `(1−f)/(δf)` |
|---|---|---|---|
| 0.995 | 2 | 0.50 | 0.50 |
| 0.990 | 2 | 1.00 | 1.01 |
| 0.980 | 3 | 2.00 | 2.04 |
| 0.970 | 4 | 3.00 | 3.09 |
| 0.960 | 5 | 4.00 | 4.17 |
| 0.950 | 6 | 5.00 | 5.26 |
| 0.940 | 7 | 6.00 | 6.38 |
| 0.930 | **8** | 7.00 | 7.53 |
| 0.920 | **9** | 8.00 | 8.70 |
| 0.914 | **10** | 8.60 | 9.41 |
| 0.910 | 10 | 9.00 | 9.89 |
| 0.900 | 10 | 10.00 | 11.11 |

**关键观察**：`f ≤ 0.914` 之后档数**饱和在 10**，不再随 `f` 下降而增长。
原因：`f` 低到一定程度后，所有档都会在有限夜内衰减到 0，档数被吸收态 `0` 吃掉。

⇒ **「档数」不是由 `(f, δ)` 决定的闭式函数**，它同时依赖初值 `w0` 与迭代上限：

| `f` | `w0=0.1` | `w0=0.3` | `w0=0.5` | `w0=0.8` | `w0=1.0` |
|---|---|---|---|---|---|
| 0.98 | 3 | 3 | 3 | 3 | **2** |
| 0.95 | 6 | 6 | 6 | 6 | **5** |
| 0.914 | 10 | 10 | 10 | **9** | **9** |

⇒ **报「档数」结论时必须写明用的是哪一种定义、哪个初值、迭代多少夜。**
这是 `docs/8` 没写清的地方，也是它数字对不上的根源。

#### 更正二：吸收态占比表是公式值，不是实测值

`docs/8` 声称吸收态占比 `f=0.99 → 99%`、`0.98 → 50%`、`0.95 → 20%`、`0.90 → 10%`
（这些是公式 `1/(100(1−f))` 的值）。实测：

| `f` | 实测不动点数 | 实测占比 | 公式值 |
|---|---|---|---|
| 0.99 | 100/101 | **99%** | 100% |
| 0.98 | 75/101 | **74%** | 50% |
| 0.95 | 29/101 | **29%** | 20% |
| 0.90 | 15/101 | **15%** | 10% |

⇒ `f=0.98` 处公式 50% vs 实测 74%，**差 24 个百分点**。
偏差不是标定误差，是**模型形态不同**（公式假设连续域，实测在 101 个离散格点上）。

#### 更正三：不动点带宽度也是公式值

| `f` | `n` | 实测宽度 | 公式 `1/(100(1−f))` |
|---|---|---|---|
| 0.98 | 1 | **0.74** | 0.50 |
| 0.98 | 2 | **0.24** | 0.50 |
| 0.95 | 1 | 0.28 | 0.20 |
| 0.95 | 2 | 0.20 | 0.20 |
| 0.90 | 1 | 0.14 | 0.10 |
| 0.90 | 2 | 0.09 | 0.10 |

⇒ 公式在 `n=1` 时低估（0.50 vs 0.74），在 `n=2` 时高估（0.50 vs 0.24）。
**带宽依赖 `n`，公式没有 `n`。** 这是 `docs/8` 推导的形态错误。

### Q3：`maxHops = 2` 在默认参数下不可观测，应该怎么修？

### Q7：衰减与强化的步长必须解耦（可塑性不可行性的根）

> 这是 `docs/8` 的 Q5，也是可塑性问题的**最根本一层**。
> 详细推导见 `docs/8`；这里给出结论与本文档复核后的更正。

#### 两个算子

```text
强化 R(w) = quantize(min(1, w + δ))
衰减 D(w) = if (w <= 0) return 0
            scaled = quantize(w × f)
            return scaled < w ? scaled : stepDownWeight(w)
                    ↑ 地板：quantize(max(0, w − 0.01))
quantize(x) = round(100x) / 100          # 101 个格点
EDGE_WEIGHT_STEP = 0.01                  # 地板步长
```

#### 核心事实（实测）

**`δ` 的默认值 `0.01` 与地板步长 `EDGE_WEIGHT_STEP` 精确相等。**

于是「一次共激活」的净变化：

```text
w ← R(w) = quantize(w + 0.01)
w ← D(w) = quantize(w × 0.98)，若 scaled < w 用它，否则 w − 0.01

δ=0.01, f=0.98:
  上升 0 / 不变 75 / 下降 26        (101 格)
  「不变」区间 = [0, 0.74]，连续，共 75 个格点
```

⇒ **默认参数下，「用过一次」是零变化，且 101 个格点里 0 个上升。**

其他组合：

| `δ` | `f` | 上升 | 不变 | 下降 |
|---|---|---|---|---|
| 0.01 | 0.98 | **0** | 75 | 26 |
| 0.02 | 0.98 | 74 | 25 | 2 |
| 0.01 | 0.95 | **0** | 29 | 72 |
| 0.01 | 0.914 | **0** | 17 | 84 |

#### 请裁决

1. **`δ` 与地板步长必须解耦——但解耦到多少？**
   已知约束：
   - `δ = 0.01` 是档数最大化的唯一选择（实测 `δ=0.02` 时档数从 3 降到 2）；
   - 但 `δ = 0.01` 时「一次使用」零变化。
   ⇒ **「分辨率最高」与「一次使用有效」互相排斥。**
   请给出一个同时满足两者的方案，或证明不存在。

2. **地板步长为什么必须是 `EDGE_WEIGHT_STEP`？**
   它现在是 `quantize(max(0, w − 0.01))`，即「至少降一格」。
   若改成 `quantize(w × f)` 且**不**兜底（允许 `scaled === w`，即真的不动），
   会发生什么？缺陷二十（25 个不动点）会回来吗？
   请判断「地板」这个补丁的必要性——它是修缺陷二十的正解，还是把缺陷推到了另一处？

3. **量化精度从 0.01 提高到 0.001 是否可行？**
   101 格点 → 1001 格点。档数上界会变吗？（见 §3.6 更正一：上界公式本身是错的，
   所以请重新推导，不要套用 `docs/8` 的 `N < (1−f)/δ`。）
   代价：边权存储从 2 位小数变成 3 位小数，幂等键与日志体积会变——这算不算
   「为了一个未接线的机制改变持久格式」？

### Q8：`same-entity` 边没有度数上界，是 O(n²)（新发现）

#### 现状

`buildEdges` 对两类边处理不对称：

| 边类型 | 度数约束 | 实测 |
|---|---|---|
| `same-topic` | k-NN 双向约束，每端点 ≤ 3 | ✅ 严格 ≤ 3 |
| `same-entity` | **无任何约束** | ❌ 见下表 |

#### 实测：边数随规模的增长

场景：每卡 3 个实体，实体池 40（真实语料里实体高度重复）：

| `n` | `same-entity` | `same-topic` | 总边数 | 最大总度数 | 边数比（n 翻倍） |
|---|---|---|---|---|---|

| 100 | 579 | 150 | 729 | 15 | ×3.44 |
| 200 | 2400 | 300 | 2700 | 27 | ×3.70 |
| 400 | 9800 | 600 | 10400 | 52 | ×3.85 |
| 800 | 39600 | 1200 | 40800 | **102** | ×3.92 |

⇒ **边数 ≈ 4 倍增长 ⇒ O(n²)。**

#### 生产规模下的代价

场景：每卡 3 实体，实体池 = `n/10`（实体重复度随语料增长而升高）：

| `n` | 实体池 | `same-entity` | 总边数 | 耗时 |
|---|---|---|---|---|
| 500 | 50 | 12250 | 12999 | 85 ms |

| 2000 | 200 | 49000 | 52000 | 761 ms |
| 3000 | 300 | 73500 | 78000 | 1526 ms |
| **5000** | 500 | **122500** | **130000** | **3621 ms** |

`maxCardsPerRun = 5000`。

⇒ 生产规模下单次夜整理**光建图就 3.6 秒**，产出 **13 万条边**。

#### 极端场景：实体池很小

实体池 = 5（所有人共享同一批实体）：

| `n` | `same-entity` | 总边数 | 最大总度数 |
|---|---|---|---|
| 50 | 725 | 800 | 32 |
| 100 | 2950 | 3100 | 62 |
| 200 | 11900 | 12199 | 122 |
| 400 | 47800 | 48399 | **242** |

⇒ 接近完全图。**扩散激活在完全图上失效**（见 Q4：`raw` 取值数坍缩到 1）。

#### 请裁决

1. **`same-entity` 应该施加什么样的度数约束？**
   候选：
   - 与 `same-topic` 共用 `topicNeighbors`（简单但两类边的语义不同）
   - 新增 `entityNeighbors` 配置（多一个参数，但职责清晰）
   - 按 `|shared|/|union|` 降序取前 K（保留最强实体关联）
   - 按实体频次加权（高频实体如「项目」不该连所有人）
   请给出选择并说明它如何同时满足 P8（耗时可控）与「突触」语义。

2. **「高频实体」问题**：一个实体出现在 50% 的卡里时（如项目名），
   它产生的边几乎覆盖全图，信息量为零（类似停用词）。

   若要，它应该作用在**边的存在性**（高频实体不连边）还是**边权**（连但权重低）？

3. **`same-topic` 与 `same-entity` 的边权是否可比？**
   - `same-topic` 权重 = `similarity`（jaccard，取值 0.08~0.86）
   - `same-entity` 权重 = `|shared|/|union|`（取值 0~1）
   两者量纲相同（都是 jaccard 类），但**分布不同**。

   是否应该归一化？请说明对 §2.8 的 `raw` 分布有什么影响。

// .tmp/probe-math-facts.mjs 的核心
import { nextDecayedWeight } from '../src/core/spread.ts'
import { quantizeWeight as Q, EDGE_WEIGHT_STEP } from '../src/core/graph.ts'

const night = (w, n, d, f) => {
  let x = w
  for (let k = 0; k < n; k += 1) x = Q(Math.min(1, x + d))
  return nextDecayedWeight(x, f)
}

// n=1 时净变化分布
for (const [d, f] of [[0.01, 0.98], [0.02, 0.98]]) {
  let up = 0, same = 0, down = 0
  for (let i = 0; i <= 100; i += 1) {
    const w = Q(i / 100)
    const nw = night(w, 1, d, f)
    if (nw > w) up += 1
    else if (nw === w) same += 1
    else down += 1
  }
  console.log(`δ=${d} f=${f}: 上升 ${up} / 不变 ${same} / 下降 ${down}`)
}

### A.2 `nextDecayedWeight` 的真实实现

```ts
// src/core/spread.ts
export function nextDecayedWeight(weight: number, decayFactor: number): number {
  if (weight <= 0) return 0
  const scaled = quantizeWeight(weight * decayFactor)
  // 量化格点会让小权重永远衰减不下去（缺陷二十）。
  // 兜底：若量化后没有变小，强制降一格。
  return scaled < weight ? scaled : stepDownWeight(weight)
}
```

**这个函数就是 Q7 的核心**：`stepDownWeight` 的步长 `EDGE_WEIGHT_STEP = 0.01`
与 `reinforceDelta = 0.01` 相等，导致强化与衰减精确抵消。
