# 07 · 巩固与遗忘

> 本篇讲**记忆在夜里发生了什么**：怎么变弱、怎么被合并、怎么被压成摘要、

## 一、巩固是批处理，它和写路径是两种完全不同的东西

### 1.1 一句话

**巩固不在交互路径上。它每晚跑一次，允许慢，不允许不准。**

这和写路径（05 篇）的取向恰好相反：写路径被允许复杂但不允许阻塞回复，
巩固允许在明确的时间预算内运行，必须能暂停、重试和恢复。两条路径都可能失败，
区别在于工作单位、提交边界与失败后的恢复办法：

| 维度 | 写路径 | 巩固路径 |
|---|---|---|
| 触发 | 每一轮对话结束 | 每晚固定时刻，且一夜只跑一次 |
| 允许耗时 | 毫秒级，且在回复之后 | 分钟级，可以很慢 |
| 输入 | 这一轮的用户与助手文本 | 整个记忆库的活跃卡 |
| 输出 | 0～4 张新卡 | 一批变更（衰减、合并、归档、摘要、边） |
| 出错的代价 | 少记一句话 | **记错一批东西，且它会被后续所有召回读到** |
| 可否重跑 | 依赖稳定的操作身份，不天然幂等 | **必须按批次幂等提交**，否则同一批重试会重复累加 |
| 观测方式 | 看这一轮的产出 | 看一份**人可读的报告** |

**确定性与幂等是两个契约。** 同一输入得到同一计划叫确定性；同一计划重试不再改变已提交状态叫幂等。
确定的「访问次数加一」重复应用两次仍会加二，不能拿确定性证明幂等。

**【设计决策·待验证】巩固以批次为提交单位。** 每批固定域、逻辑批次身份、
输入日志水位、结算时刻、时区与策略版本；据此生成确定的变更计划。读取的卡版本
若在发布前变化，应重新规划或报告版本冲突，不能用旧快照覆盖新写入。

| 重试位置 | 必须达到的结果 |
|---|---|
| 计划尚未持久提交 | 重试同一输入，生成同一计划；未提交派生物不可被召回 |
| 计划已持久提交，确认丢失 | 重试返回原提交结果，不再次衰减、累加访问或推进到期 |
| 进程中途退出 | 恢复到完整提交边界；若采用分阶段提交，必须有持久检查点与可重入步骤 |

日志逐条可重放只证明每条记录可恢复，**不自动证明一整批变更原子可见**。
批次身份与各操作身份要随日志持久化，不能仅存在于进程内；相同操作身份却携带
不同负载必须报冲突。摘要的稳定标识只解决其中一类重复，不能替代这套提交契约。

### 1.2 八步总览

```text

        ┌───────────────────────────────────────────────────┐

        │    强度低于阈值者，按比例上限截断后置为归档       │

        ┌───────────────────────────────────────────────────┐

        │ ⑦ 重建索引                                        │

        │    报告只能观测它，不能把它换个名字打印           │
        └────────────────────────┬──────────────────────────┘
                                 ▼
        ┌───────────────────────────────────────────────────┐
        │ ⑧ 出报告                                          │
        │    人可读：衰减/合并/摘要/归档/边 各几张          │
        └────────────────────────┬──────────────────────────┘
                                 ▼
                    变更日志（唯一真相源，与写路径同一个）
```

**「取工作集」为什么必须存在**：单批巩固的成本必须有明确预算，
否则库越大这一夜越跑不完，而跑不完的下一夜会积压更多。
卡数上限只让「单批纳入的卡数」有上界，不能单独限制比较次数或总耗时。
代价是**超出部分的卡本批完全不参与**——
它们不衰减、不归档、不被摘要统计。这是一笔明确的账：
**宁可分批处理，也不让单批巩固变成不可完成的任务。**

**【设计决策·待验证】上限必须配公平调度。** 以持久游标轮转处理，不能每夜重新取
排序最前的同一批；记录待处理数、最老未处理时长与推进水位。取一批后的候选枚举、
派生边数和比较次数也要单独限额，否则「5000 张」仍可能产生平方级工作。
只有处理速率持续超过进入工作队列的速率，才能承诺最终轮到每张卡。

**「重建索引」为什么不在编排里**：索引住在数据面，纯函数层拿不到它。
所以第 ⑦ 步由数据面完成，报告只能**观测**它。
这里有一个必须记住的陷阱：报告里如果写一个「重建索引数 = 活跃卡数」的字段，
那个数字是**活跃卡数换了个名字**，索引一次都没重建——
而它看起来完全正常，因为两个数在大多数夜里恰好相等。

> **一个说错的观测点比没有观测点更危险，因为人会信它。**

## 二、八步的顺序：顺序不是风格，是约束

> 这一节是 07 篇的核心。它讲的不是「我们选择了这个顺序」，
> 而是「换一个顺序，某一步的产出会恒为零，而且不报错」。

### 2.1 四条顺序约束

| # | 约束 | 若违反的后果 | 这是怎么被发现的 |
|---|---|---|---|
| 1 | 蒸馏 **早于** 去重合并 | 感受产出恒为零 | 端到端测试：感受数 = 0 |
| 2 | 摘要读取**归档前固定的历史口径** | 若只读归档后的活跃卡，会漏掉发生过的事件 | 历史统计与当前状态必须分开 |
| 3 | 摘要 **晚于** 蒸馏 | 日摘要里永远没有「今天的感受」 | 顺序推演 + 摘要文本缺字段 |
| 4 | 先日分区账本，再分别生成周、月视图 | 漏掉少量日，或跨月周造成重复归属 | 自然日作为唯一时间分区基底，展示摘要可省略 |

这些约束依赖各步骤读取哪份数据。固定快照和显式依赖可以消除部分物理顺序限制；
不能把某一条编排顺序宣传成所有实现都必须遵守的数学定理。

### 2.2 约束一：蒸馏必须早于去重

这是唯一一条**被实测抓出来**的顺序约束，也是最重要的一条。

蒸馏的判据是「反复经历」——同一件事在若干张有情绪的卡里反复出现。
它的证据形态是**多张卡共享同一个主题词**。

而夜整理的去重会把高度相似的卡**合并成一张**。于是：

```text
违反顺序的链路：

三张「上线又出问题」的卡（各带强情绪）
        │
        ├── 先去重 ──→ 合并成一张「上线又出问题」
        │                       │
        │                       └── 只剩 1 张
        │
        └── 再蒸馏 ──→ 同一主题只有 1 张卡
                        1 < 重复门槛 2
                        → 这个桶不达标
                        → 感受产出 = 0
```

**「反复经历」的证据，恰好是去重要销毁的东西。** 这两步在数据上是直接冲突的：
一个要「把相似的聚起来看有几张」，另一个要「把相似的合成一张」。
谁先谁后不是偏好问题，是**证据必须先被读取，然后才能被销毁**。

这条为什么长期没被发现：**单元测试全绿**。
单元测试直接构造卡数组喂给蒸馏，从不经过夜整理的去重阶段。
只有**端到端**测试（写入 → 夜整理 → 检查产出）能看见它，
而它的观测值是一个安静的零。

```text
顺序上的代价（诚实记录）：
刚产出的感受卡会进入后续的去重候选池。
这没有害处——感受卡文本是模板句，与事件卡字面差异大，不会被误合并。
```

**推论：一条「聚合」逻辑和一条「销毁聚合证据」的逻辑放在同一批处理里时，
必须显式规定先后，并且用端到端测试守住这个先后。**
单测守不住它，因为单测跳过了那一步。

### 2.3 约束二：摘要口径不能被归档状态改写

摘要记录「这段时间发生过什么」，归档回答「现在是否默认参与召回」。
已归档事件依然发生过；把它统计进历史摘要并不矛盾。真正的错误是
摘要只扫描当下活跃视图，导致归档前后同一天的事件总数不同。

**【设计决策·待验证】在本批输入水位上固定摘要来源集合。** 来源按事件发生时间、
域和有效版本选择，排除已删除或已被修正取代的无效内容；不因自动归档而抹掉历史。
若实现只能读取会被归档改变的活跃数组，就先生成摘要，再归档。若有固定历史快照，
两步可以独立计算，最后遵守同一提交边界。

### 2.4 约束三：摘要必须晚于蒸馏

日摘要的文本结构是「范围 + 规模 + 主域 + 关键词 + 感受」。
最后一段「感受」来自当天蒸馏出的感受卡。

如果摘要在蒸馏之前跑，那么当天的感受卡还不存在，
日摘要里那一段**永远为空**：

```text
摘要在前：日摘要里「感受」一段恒为空
          → 「今天的感受」在日摘要里永远缺席
          → 而它恰恰是起源里最该被留下的那一层

摘要在后：日摘要能统计到本轮刚蒸馏出的感受
          → 「今天发生了什么」与「今天感受到了什么」在同一张卡上
```

**这两条约束（2.3 与 2.4）把摘要夹在了蒸馏和归档之间**：

```text
       蒸馏  ──→  摘要  ──→  归档
         ↑                  ↑
    摘要要读到它        归档不能改写来源口径
```

### 2.5 约束四：日作为时间分区基底

既有三级串联设想是「日 → 周 → 月」。但自然周可能跨月，
把整周归给某一个月会漏计另一个月，把它放进两个自然月又会重复计数。

**【设计决策·待验证】先固定日分区账本，再由账本分别汇入周与月。**
每个自然日保留有效来源标识与修订、覆盖水位、闭合状态；即使来源少于展示门槛、
不生成日摘要文本，也不能省略这个统计基底。所有窗口统一采用已固定时区下的
左闭右开区间；每个日分区只归属一个自然周和一个自然月。
周与月是同一日基底的两种视图，不把周摘要再计入月摘要，也不只汇总可展示的日文本。

```text
原始事件 → 日分区账本 ─┬→ 可选日摘要
                      ├→ 周摘要
                      └→ 月摘要
```

上层必须读取日分区账本的**有效版本集合**，统计来源去重后累加；
关键词按同一策略从有效来源分批重算，不能对截断后的日摘要关键词再假称完整统计。
某日补写、修正或删除后，重算覆盖该日的周、月视图；不在旧文本上再加一份。
未到结束边界或来源水位尚未追齐的窗口必须标为暂定；迟到事件会产生新修订。

### 2.6 结论句

> **顺序不是风格，是约束。**
> 一处顺序错，某一步的产出恒为零；而它不报错、不崩溃、日志正常，
> 单测还全绿——因为单测从不经过那一步。

三条可用于任何批处理系统的判据：

1. **凡是「聚合」与「销毁聚合证据」共存，必须显式定序，并用端到端测试守住。**
2. **凡是「统计」与「判定重要性」共存，固定历史来源口径**——历史不能被当下状态改写。
3. **凡是「上层依赖下层」的层级结构，必须让上层能读到本轮刚产出的下层。**

## 三、去重与合并

### 3.1 判据

```text
相似度 = 两个词项集合的交集大小 / 并集大小
重复判据：相似度 ≥ 0.86
```

0.86 是一个**很严**的阈值。它的含义是「几乎逐字相同」，
而不是「说的是一件事」。为什么这么严：合并是**不可逆的破坏性动作**
（虽然可溯源，但视图上两张卡变一张），宁可漏合并，
不要错合并——错合并会把两件不同的事永久粘成一件。

两个必须区分的量：

| 量 | 公式 | 它回答的问题 |
|---|---|---|
| 交集比并集 | 交集 / 并集 | 「这两张卡有多像」——对称 |
| 交集比自身 | 交集 / 其中一张的大小 | 「短的那张是否被长的那张包含」——不对称 |

**这两个量不能互换。** 一张 5 个词项的卡被一张 50 个词项的卡完全包含时：
前者是 0.10（5 / 50），后者是 1.00（5 / 5，完全包含）。
用错量会导致「长卡吞掉所有短卡」或者「短卡永远不被合并」。

### 3.2 分组：连通只提供候选，不证明重复可传递

集合相似度达到阈值的关系**不传递**。例如甲含词项 1～10，乙含 1～11，
丙含 2～11：甲乙与乙丙都是 10/11≈0.909，甲丙却只有 9/11≈0.818。
阈值为 0.86 时，前两对达标，后一对不达标。把并查集的连通分量整组自动合并，
会让渐变文本沿链条吞并不同内容。

**【设计决策·待验证】并查集只生成待核对组件，实际合并组要求全对达标。**
组件内按创建时间升序、再按标识升序处理；一张卡只有与组内每张卡都达到阈值
才可加入，若有多个可加入组则取最早建立的组。这是保守且确定的选择，
可能漏合并，但不会靠传递闭包自动放宽成对判据。

相似度也不等于语义等价：域、事实时段、否定与修正关系不兼容的卡不得自动合并。
组内最小成对相似度只表示词面紧密程度，不能解释成「内容正确的概率」。
对含 m 张卡的组件，全对核验最坏需要 m(m−1)/2 次比较；达到比较预算就保留未决卡，
不能为了赶完而把整个组件强制合并。

### 3.3 组内代表与合并规则

一组卡合并成一张，代表是**组内最早创建的那张**（同龄按标识升序）。
选最早而不是最强，理由是：合并要保留「这件事第一次是什么时候发生的」，
而最早创建时间表示首次记录时刻。原始事件仍须保留，不能以代表卡替代完整溯源。

合并后各字段的取法：

| 字段 | 取法 | 理由 |
|---|---|---|
| 标识 | 代表卡的标识 | 只保证代表身份稳定；操作幂等仍依赖批次与操作身份 |
| 文本 | 组内**最长**的那条，再按 200 字截断 | 最长的信息量最大 |
| 归一化文本 | 由实际保留的文本重新生成 | 文本与检索表示必须对应；完整原文沿来源查回 |
| 强度 | 取**最大** | 合并不能把强卡拉成弱卡 |
| 显著性 | 取最大 | 强烈的记忆不能因为合并而稀释 |
| 情绪强度 | 取最大 | 同上 |
| 置信度 | 取最大 | 同上 |
| 访问计数 | 去重后的使用事件数 | 只有来源使用事件互不重叠时，才可直接求和 |
| 创建时间 | 代表卡的 | 溯源 |
| 更新时刻 | 组内最大 | 最近一次变化 |
| 标签 / 实体 | 并集去重（大小写不敏感） | 跨层次关联不能丢 |
| 冲突集合 | 并集，去掉自己 | 冲突不能因为合并而消失 |
| 修正记录 | 全部保留，按时间升序 | 可查改过什么 |
| 合并溯源 | 被并入的其余标识（含它们此前并入的） | **合并后仍能追回原始事件** |

**「取最大」与「求和」的区分是刻意的**：强度、显著性、情绪、置信度是
**状态量**，合并后应当代表「这组里最强的那次经历」；访问计数是**累计量**，
合并后应当代表「这件事被独立确认使用过多少次」。
代表卡再次和已经并入的来源相遇时，不能重复累加其访问；只有一个无来源计数器时，
无法证明简单求和安全，应保留各来源计数或使用去重的使用事件身份。

**取最小是错的**：一张强卡和一张弱卡合并后变弱，等于「因为重复，所以更容易被忘掉」——
方向反了。

**溯源为什么必须保留合并链**：合并是可逆的视图操作，不是删除。
一张卡被合并后，它的标识仍记在代表卡的合并溯源里，沿着它可以追回原始事件，
一直追到事件日志的某一条。**「忘掉」不等于「销毁证据」**，这是 FR-C2 的内容。

### 3.4 摘要卡为什么不参与去重

这是一条必须写清的例外，因为它的成因很反直觉。

摘要卡的文本是**模板化的统计句**：

```text
某日：7 条记忆，主要涉及工作，关键词 部署、回滚、灰度、报错
次日：5 条记忆，主要涉及工作，关键词 部署、回滚、灰度、报错
```

两句话的字面相似度**极高**——大部分字符完全相同，只有日期和数字不同。
如果它们参与去重：

```text
第 1 天：日摘要甲
第 2 天：日摘要乙  ← 与甲相似度 ≥ 0.86，被判重复
        ↓
        甲与乙合并成一张
        ↓
第 3 天：日摘要丙  ← 与合并后的那张相似，又被合并
        ↓
        「每天一张日摘要」在几轮之后只剩一张
        ↓
        层级压缩被它自己的去重逻辑摧毁
```

【实测】两天的日摘要确实进了同一分组。

**为什么不能靠调高阈值绕开**：把阈值从 0.86 提到 0.95，
两天的摘要仍然会合并（它们确实几乎逐字相同）；而 0.95 会同时放过
**真重复的事件卡**——那些「同一件事换了个说法」的卡相似度大多在 0.86～0.95 之间。

```text
调阈值：摘要仍然合并，真重复反而漏掉   ← 两头都变差
排除摘要：摘要不参与，事件卡判据不动     ← 只修该修的那一处
```

**这是「例外」而不是「特判」的区别**：摘要卡不是「记忆内容」，
它是对记忆内容的**统计**。统计句之间的字面相似度不表达「说的是同一件事」，
而重复判据的语义前提正是「字面相似 ⇒ 说的是同一件事」。
**判据的语义前提不成立的地方，必须排除，不能调参。**

同理，参与去重的候选池还要排除三种：非活跃的、已被合并的、摘要卡。
少排一种，都会让已作废的视图重新进入合并流程。

## 四、三层摘要：压缩必须是算术上的必然

### 4.1 为什么必须真的压缩

最容易犯的错是**把当天所有卡的文本拼起来当摘要**。

那不是摘要，是**日志**：信息量与原文相等，压缩比 1:1，
只是换了个地方存，还多了一份要维护的东西。而且它更糟——
日志至少是完整的，拼接还丢掉了原文的结构。

**判据很简单：摘要的字符数必须显著小于来源总字符数。** 但「显著小于」
不能靠自觉，必须变成算术上的必然。

### 4.2 两道闸

```text
闸一（算术闸）：
    预算 = 取较小者( 层级字符上限, 向下取整(来源总字符数 × 目标压缩比) )
    预算不足最小完整语义单元时跳过展示；其余按预算输出统计量与关键词

闸二（配置闸）：
    目标压缩比必须满足 0 < 比例 < 1
    层级字符上限必须「越高越短」：月 ≤ 周 ≤ 日
    下级数量必须 ≥ 2
```

**算术闸只保证长度预算，不保证语义保真。** 来源长度为整数 N≥2、比例 r在(0,1)内且
字符上限为正整数时，预算 B≤⌊Nr⌋<N，且 B/N≤r。N≤1或预算不足时跳过展示；
日分区账本仍然保留，不能因没有摘要文本而丢掉上层统计来源。
「显著更短」还需给出压缩目标，不能只靠小于号。

| 层级 | 字符上限 | 目标压缩比 | 实际预算 |
|---|---|---|---|
| 日 | 180 | 0.5 | 取较小者(180, 向下取整(来源字数 × 0.5)) |
| 周 | 140 | 0.5 | 取较小者(140, 向下取整(来源字数 × 0.5)) |
| 月 | 110 | 0.5 | 取较小者(110, 向下取整(来源字数 × 0.5)) |

**预算不保底为1。** 例如N=2、r=0.1时，强制预算为1会得到0.5的压缩比，
突破0.1目标。预算为0时显式报告「预算不足，未展示」，不创建空摘要卡。

【推导】一天按 12 张卡、每张约 30 字算，来源约 360 字，
日摘要预算 = 取较小者(180, 180) = 180，压缩比 0.5。若来源只有 100 字，
预算 = 50，这是预算演算；实际是否生成还要经过来源门槛。
预算与来源之比**不超过** 0.5，触及绝对上限后会继续下降，实际文本还可能更短。

**渲染只输出统计量与关键词，绝不拼接来源原文。** 结构固定为
「范围 + 规模 + 主域 + 关键词 + （可选）感受」，每段都可独立省略，
若预算连最小完整语义单元都容纳不了，就跳过摘要，不能截成残缺词句。

抽取关键原句也能压缩，模板统计也可能遗漏重要事实；**不拼接是本设计的取舍，
不是压缩成立的必要条件**。长度合格后仍须核对来源覆盖、数字一致和关键事实保留。

### 4.3 配置闸为什么比代码自律更硬

```text
代码里自律：「我记得预算不足就跳过」「我记得别拼接原文」
配置层拒绝：压缩比 ≤ 0 → 加载期失败
            压缩比 ≥ 1 → 加载期失败
            上层比下层长 → 加载期失败
            下级只有 1 个 → 加载期失败
```

**差别在于「能不能配出一个假压缩」**：

| 做法 | 假压缩能不能被配出来 | 谁来发现 |
|---|---|---|
| 只在实现里自律 | 能（改一行就配出来了） | 靠人读代码，或者靠测试断言 |
| 配置层拒绝 | **不能**（加载期就失败） | 加载期自己 |

**配置层的拒绝比实现里的自律更硬**，因为它把「不可能」写进了**可配置空间的边界**，
而不是写进某一段代码的行为。代码可以改，边界不会自己松掉。

这条设计有一个副产品：**它让「压缩比」这条测试变得有意义**。
如果配置允许压缩比 ≥ 1，那么「压缩比 < 1」这条断言就是在测一个
本来就不可能失败的性质——**无牙断言**。

### 4.4 一个曾经绿在巧合上的测试

这里必须记一条方法论教训，因为它的形态非常普遍：

```text
测试：日摘要的压缩比 < 目标压缩比
观测：日摘要渲染出来只有 30 字，远小于任何预算
结果：通过

反向验证：把「按比例算预算」改成「预算恒等于层级上限」（彻底不做比例压缩）
预期：这条断言变红
实际：依然绿
```

**为什么绿**：日摘要只有 30 字，而层级上限是 180 字。
把预算公式整个删掉，30 字仍然远小于 180 字，断言照样成立。
**这条测试守的不是「压缩逻辑正确」，是「这一天的摘要恰好很短」。**

只有直接断言**预算函数本身**的用例变红了。补上的规则级用例有三条：

| 用例 | 断言 | 它守的是什么 |
|---|---|---|
| 来源翻倍 | 未触上限时按比例增长，允许取整差一字 | 比例真的被乘进去了 |
| 触上限 | 预算被截平在层级上限 | 上限真的生效 |
| 极小来源 | 允许预算为0并显式跳过，不创建空卡 | 不用保底突破目标压缩比 |

> **反向验证不只是确认「会红」，它还能反过来暴露哪条测试是装饰。**
> 一条测试如果在「被测逻辑被整个删掉」时仍然绿，它守的就不是那个逻辑。

### 4.5 什么时候不该产出摘要

日摘要有一个来源门槛：**当天来源总字符数低于 120 时不产出**。

这是成本与语义完整度的设计门槛，不是「短原文在数学上不可压缩」。
固定模板的开销可能抵消收益，硬截短又可能丢掉唯一事实，所以允许不生成。

```text
来源 100 字 → 预算 = 向下取整(100 × 0.5) = 50 字
             但「某日：1 条记忆，主要涉及工作，关键词 X」本身就接近 40 字
             → 字符数已减半以上，但统计模板仍可能丢掉关键细节
             → 不如不产出
```

周摘要与月摘要也可设展示门槛：**有效日分区数量 ≥ 2**。
该门槛只决定要不要展示周/月文本，不决定该日事实是否进入统计基底。
只有一天有记录时可以省略上层文本；账本与来源依赖仍须保留，以便迟到材料到来后重算。

## 五、摘要的身份、修订与来源依赖

### 5.1 三个现有字段就够

摘要卡的层级不靠新字段，靠三个已经存在的字段：

| 信息 | 存在哪 | 怎么读回来 |
|---|---|---|
| 「这是一张摘要」 | 类型字段 = 摘要 | 类型判断 |
| 「它是哪一级、属于哪个时间」 | 标签首项：`daily:<日期键>` / `weekly:<周一日期键>` / `monthly:<年月键>` | 按冒号切分 |
| 「它压了哪些卡」 | 合并溯源字段 = 被压卡的标识列表 | 直接读 |
| 「它来自哪一级」 | 来源指针的事件类型：「日摘要」事件类型 等 | 读事件类型 |

### 5.2 为什么不加字段

**卡是契约层。每加一个字段，所有投影、重放、序列化、查询路径都要跟着改。**
而层级信息本来就完整存在于标签与来源里——加字段等于把同一份事实存两遍，
两遍之间必然漂移。

更实际的理由：**摘要卡不是特殊卡。** 它走的是同一条写入路径、同一套幂等、
同一个重放逻辑。一旦为它加一个专属字段，所有通用路径都要开始分支判断
「这是不是摘要」——分支每多一处，就有多一处会漏判。

**「用现有字段承载新语义」是一种能力，不是妥协。** 它要求字段的语义足够宽
（「合并溯源」既能表达合并也能表达压缩），也要求读写两侧共用同一个解析入口——
否则写的时候按 `daily:` 打标签、读的时候按「日:」解析，就是两个真相源。

### 5.3 同一窗口的修订不能变成多份活跃摘要

内容派生标识只能保证**同内容重复提交**不多建卡。迟到事件让摘要文本改变后，
内容标识也会改变；若不撤下旧版，同一天就可能同时存在两张有效摘要。

**【设计决策·待验证】区分逻辑摘要身份与内容修订。**
逻辑身份由域、层级、固定时区下的窗口确定；日分区账本同样有稳定窗口身份。
修订由来源标识及版本的有序集合、
策略版本与产出内容共同确定。同一逻辑摘要只有一个当前有效修订，旧修订可追溯。
相同操作重试不能新增修订，不同操作允许将内容从甲改乙后再改回甲。

来源关系是依赖关系，不是「这些卡已经重复」的合并关系。即使共用一个存储载体，
也必须能区分关系类型，不能把摘要来源当成被合并卡从活跃视图中剔除。

**【设计决策·待验证】删除与修正沿来源依赖闭包传播。** 原始卡被显式删除后，
依赖它的摘要、感受、实体边和索引必须先变为不可见，再从剩余有效来源重算；
来源不足则撤回产出。只保留来源标识列表，却不执行反向失效，不构成删除闭环。
自动归档仅改变默认召回资格，不等同于删除，不触发抹除历史统计。

重新生成派生物时必须检查来源的删除状态及版本，防止旧批次恢复或日志重放把已删除内容
重新带回。逻辑不可见与历史日志、备份的物理净化是不同承诺，必须分别验收。

### 5.4 层级字段承载表

| 层级 | 标签首项 | 来源指针的日期键 | 事件类型 | 字符上限 |
|---|---|---|---|---|
| 日 | `daily:<日期键>` | 该自然日的日期键 | 「日摘要」事件类型 | 180 |
| 周 | `weekly:<周一日期键>` | 该周周一的日期键 | 「周摘要」事件类型 | 140 |
| 月 | `monthly:<年月键>` | 该月的年月键 | 「月摘要」事件类型 | 110 |

**来源指针里的序号用来表达层级**（日 0、周 1、月 2），
这样排查时看来源就能看出层级，不必去解析标签。这是冗余，但冗余在这里是好事：
**排查时多一条可读线索，比少一条好。**

## 六、感受蒸馏

### 6.1 它在做什么，以及它做不到什么

**先说做不到的**，防止后面所有描述被误读：

```text
它做不到：
  ✗ 不知道「被领导夸」和「被领导骂」在情绪上相反
    （情绪强度只度量「有多浓」，不度量「是正还是负」）
  ✗ 不做因果推断（主题共现是相关性，不是「因为 A 所以 B」）
  ✗ 不会随时间改变「对同一件事的看法」

它能做到：
  ✓ 留下「哪些处境反复牵动过我」这一层
  ✓ 让细节衰减之后仍有东西可回忆
```

所以它的产出文本刻意写成「X 这件事反复牵动我的情绪」，
**绝不写「我对 X 感到难过」**——后者是它给不出的判断。
**写一个判断不出的情绪名，就是让文本撒谎。**

### 6.2 四步链路

```text
① 筛候选：情绪强度 ≥ 0.28，且不是蒸馏自己的产物
        ↓
② 分桶：按主题词项把候选卡聚成桶
        ↓
③ 达标：桶内张数 ≥ 2（这就是「反复」的度量）
        ↓
④ 渲染：取情绪最强的 3 个桶，各渲染一句
```

**候选门槛 0.28 与写入侧的情绪通道阈值是同一个数**，这不是巧合。
它们回答的是同一个问题——「这一轮够不够算有感受」。
两处取不同的数，会在「能进来」和「能被蒸馏」之间留出一条
**谁都不负责的缝隙**：写进来的卡全都够不上蒸馏门槛，而没有任何一处会报错。

**「≥ 2 次」为什么是「反复」的下限**：一次是经历，两次是模式。
门槛是 2 而不是 3，因为一次夜里能达到 3 次同主题的概率不高，
门槛太高会让蒸馏在稀疏使用下恒为零——那是另一种形态的「机制恒空」。

### 6.2.1 桶的排序与产出上限

达标桶可能多于产出上限，所以要排序取前 3：

| 优先级 | 排序键 | 方向 | 理由 |
|---|---|---|---|
| 1 | 桶内平均情绪强度 | 降序 | 情绪最浓的处境最该被留下 |
| 2 | 桶内张数 | 降序 | 同情绪下，反复得更多次的更成模式 |
| 3 | 主题词 | 升序 | 兜底，保证结果与遍历顺序无关 |

**第三键必须存在。** 前两键相等在真实语料里很常见（两张卡、情绪分相同），
没有第三键时「这一夜产出哪三条感受」取决于集合遍历顺序，
而遍历顺序在重放时可能不同——那会直接违反「同一输入十次结果逐位相同」。

**产出上限是 3，不是「全部达标桶」。** 感受卡是给人读的，
一夜产出二十条「这件事反复牵动我的情绪」等于没有感受。
上限的作用不是省成本，是**让产出保持可读**。

### 6.2.2 渲染：只报强度，不报判断

模板固定为：

```text
「<主题词>」这件事反复牵动我的情绪，前后经历了 <次数> 次，每次感受都<强度词>
```

强度词只有三档，由桶内平均情绪强度决定：

| 平均情绪强度 | 强度词 |
|---|---|
| ≥ 0.7 | 很强 |
| ≥ 0.4 | 明显 |
| 其余 | 轻微 |

**模板里没有一句引用来源原文。** 这是刻意的：引用会让文本看起来更真实，
但引用的是**某一次**的感受，而这张卡声称的是**反复出现的模式**。
用一次的原话去支撑一个模式判断，是拿证据当结论。

而且引用还有一个具体的风险：模板说的是「反复牵动情绪」（不表态），
引用的原话可能写着「特别开心」（表了态）——**文本会替实现表态**，
而实现根本不知道那次是开心还是难过。

**感受文本长度也受上限约束（120 字）。** 主题词过长时截断，
保证一条感受不会因为主题词本身很长而变成一段话。

**「反复牵动我的情绪」这个措辞不是文风，是能力边界。** 它只声称
「这件事与强情绪反复共现」，不声称「这件事让人开心或难过」——
后者规则版给不出（见 6.1）。

### 6.3 第一个坑：主题词的粒度

**现象**：候选卡 5 张，情绪全部达标，桶数 = 0，产出 = 0。

**根因**：归一化会把**所有标点与符号替换成空格**。于是「按空格切分」得到的是：

```text
原文：我今天特别开心，这个项目终于跑通了，感觉超级爽
归一化：我今天特别开心 这个项目终于跑通了 感觉超级爽
按空格切：["我今天特别开心", "这个项目终于跑通了", "感觉超级爽"]
```

切出来的是三个**整段长句**，不是词项。两张不同的情绪卡之间
几乎不可能共享一个整段长句，于是**桶数恒为 0**。

**正确的粒度是二元组**：中文按相邻两字切（「线性代数」→ 线性 / 性代 / 代数），
英文按整词切，再过一遍停用词表。

```text
「我今天特别开心」→ 今天 / 天特 / 特别 / 别开 / 开心 …
两张卡共享「开心」的概率，远高于共享整句的概率
```

**还有一个入参陷阱**：分词函数的约定是「输入已归一化的文本」
（它按空格切段，并假定段内没有标点）。传原文会让标点留在段里，
二元组跨标点边界生成——【实测】产出「，这」「了，」这种主题，
感受卡写成「『，这』这件事反复牵动我的情绪」。

**那不只是难看：主题词是判据。一个假主题会让两张本来无关的卡聚成桶。**

### 6.4 第二个坑：判据读标签，不读事实

**现象**：修好粒度之后，候选集又空了。5 张卡情绪全部达标，
但其中 4 张被判成「不参与蒸馏」，剩 1 张 < 门槛 2，直接返回空。

**根因**：规则写的是「感受卡本身不参与再蒸馏，否则会形成感受生感受的自激循环」，
而实现判的是**分类器给出的类型标签**：

```text
注释承诺的是：「感受卡本身」（= 蒸馏产物）
实现判的是：  类型 == 感受（= 分类器的输出）

在旧数据上两者恰好等价——因为当时原话几乎不会被判成「感受」
（情绪通道被四道闸挡着，见 05 篇第五章）。

修好情绪通道之后：
  真实情绪句全部被判成「感受」
  → 这些原话卡被这条规则一起排除
  → 候选集又空了
```

**修法：判据改成「它是不是蒸馏产物」——这是数据层可见的事实**
（派生卡的来源会话标识固定为一个特定值，事件类型固定为 「巩固/感受」事件类型）。

| 判据 | 来源 | 会不会被上游改动影响 | 结果 |
|---|---|---|---|
| 类型 == 感受 | 分类器的输出 | **会**（分类器一改，判据静默失效） | 候选集被清空 |
| 来源会话标识 == 蒸馏专用值 | 写入时确定的事实 | 不会 | 候选集正常 |

> **判据要读数据层的事实，不要读标签。**
> 用标签当判据，等于把两个模块耦合在一起，而上游一改下游就静默失效。

**配套纪律：那个「蒸馏专用值」必须由写入方和读取方共用同一个常量。**
两处各写一份字面量就是两个真相源，改一处忘一处会让判据静默失效。

### 6.5 第三个坑：主题词是判据，不是标签

**现象**：产出终于非零了，但文本是

```text
[感受]「有点」这件事反复牵动我的情绪，前后经历了 2 次，每次感受都明显
[感受]「报错」这件事反复牵动我的情绪，前后经历了 2 次，每次感受都明显
```

第二条是对的。**第一条在说假话**——「有点烦」和「有点慌」不是同一件事，
它们只共享一个程度副词。

**根因**：二元组切分没有词典，靠停用词表过滤噪声。原表收了
「的 / 了 / 是 / 很 / 这个 / 那个」这类虚词，但**没有收
「有点 / 有些 / 非常 / 特别 / 感觉 / 觉得」这类程度副词与感知动词**。

它们有两个致命特点：

| 特点 | 后果 |
|---|---|
| 区分度为零（几乎每句情绪表达都能带一个） | 它们必然出现在大多数桶里 |
| 恰好高频出现在情绪句里（「有点烦」「有点慌」「感觉很累」） | 它们**最容易**聚成桶 |

**为什么这不是「难看」而是判据错误**：

```text
两张卡共享「有点」
        → 聚成同一个桶
        → 桶内张数 ≥ 2
        → 判定「这件事反复牵动情绪」
        → 产出感受卡
```

一旦判据选错，**后面整条链路都在为一个假前提服务，而每一步都执行成功**：
不报错、不崩溃、产出非零、格式完全正确。
**唯一能发现它的是读一遍产出的文本。**

**修在哪：停用词表一处，不在主题词提取里另加一层过滤。**

理由和 6.4 是同一条：**停用词表已经是「什么不算词项」的唯一真相源。**
另开一份就是两个真相源，将来加词必然漏掉一处。
而且检索侧同样不该把「有点」当查询词——**修在一处，两处同时受益**。

**效果与一个反直觉的数字**：

```text
修复前：产出 2 条（「有点」假主题 + 「报错」真主题）
修复后：产出 1 条（「报错」真主题）
```

产出**从 2 降到 1**。这不是退化，是去掉了一条假的。
**「产出变多」和「产出变对」是两件事**——只看数量会把这条修复当成回归。

**配套的反向对照**：只测「副词不聚桶」是半个测试——
把分桶整个关掉也能让它绿。必须配一条「真实主题词仍然能被聚出来」。

### 6.6 三个坑的共同形态

```text
第一个坑：粒度错     → 桶数恒为 0        → 产出 0
第二个坑：判据错     → 候选集被清空      → 产出 0
第三个坑：词表漏项   → 桶是真的，内容是假的 → 产出非零但错
```

**前两个坑的观测值一模一样。** 修好第一个，第二个的零还在；
修好第二个，第三个的假才暴露出来。

**这说明「重跑一次看看」永远无法区分它们**——必须逐层设观测点：
候选数、桶数、达标桶数、产出数，四个数分别看，才知道断在哪一步。

而第三个坑连「逐层观测」都发现不了，因为**每一层的数字都合理**。
只有读产出的文本才能看见。

> **「非零」只证明链路通了，不证明链路对了。**
> 修好一个「产出恒为零」的问题之后，必须读一遍产出的内容。

## 七、衰减与归档

### 7.1 衰减公式

```text
有效半衰期 = 基准半衰期 × 情绪因子 × 访问因子

情绪因子 = 1 + 情绪强度 × (情绪加成 − 1)      情绪加成 = 2.0
访问因子 = 1 + 取较小者(1, ln(1 + 访问计数) / ln(21))
访问计数为非负整数，达到20次时饱和
基准半衰期 = 14 天

经过时间 = 取较大者(0, 当前时刻 − 独立强度结算时刻)
新强度 = 夹取到[0,1]（ 旧强度 × 0.5 ^ (经过时间 / 有效半衰期) ）
```

**三个参数各自的作用**：

| 参数 | 值 | 作用 | 效果 |
|---|---|---|---|
| 基准半衰期 | 14 天 | 普通记忆的遗忘速度 | 两周掉一半 |
| 情绪加成 | 2.0 | 情绪强的记忆忘得慢 | 情绪满值时半衰期翻倍到 28 天 |
| 访问饱和点 | 20 次 | 被使用的记忆忘得慢，增益有上限 | 访问因子在[1,2]内 |

【推导】情绪强度 1.0、访问 0 次：有效半衰期 = 14 × 2.0 × 1 = 28 天。
情绪0、访问5次：14×(1+ln6/ln21)≈22.239天。
两者兼有：14×2×(1+ln6/ln21)≈44.478天。
情绪满值且访问达到20次后：14×2×2=56天，即默认参数下有效半衰期上界H=56天。

情绪与独立使用证据都可延长寿命，但类别标签不直接决定半衰期；
感受卡永不自动归档是另一条生命周期策略，不能用它反推半衰期至少翻倍。

**【设计决策·待验证】强度必须有独立的结算时刻。** 通用更新时间、最后访问时间
不一定意味着强度已结算，不能取三者最大值代替。写标签或记一次访问就重置衰减起点，
会把已经过去的时间静默抹掉。只有结算成功才推进强度时钟。

在半衰期固定且不做中途量化时，指数衰减满足分段合成：

```text
先在 t1 衰减一次，把快照时刻置为 t1；再在 t2 衰减一次
结果在实数运算下 = 从 t0 直接衰减到 t2；浮点末位不保证相同
```

情绪或访问计数改变半衰期时，必须先按旧参数结算到变更时刻，再用新参数计算后续区间。
一般形式为：强度 = 初始强度 × 2 的「各区间经过时间 / 各区间半衰期之和的相反数」次方。
不能把变更后的半衰期追溯应用到全部历史。本节统一采用09的对数饱和访问策略，
默认H=56天；变更情绪倍数等参数后必须重新计算H，不能沿用旧容量结论。

漏夜后按真实经过时间补结算，而不是补乘固定「每夜因子」。重放固定事件顺序和计算路径；
若要求逐位一致，就统一运算路径，不能把数学等价的闭式与逐段计算混用。

**时间倒流（当前时刻早于结算时刻）时原样返回当前强度，且不回拨结算时钟。**
若回拨结算时刻，后续会重复结算已处理区间，使重放结果依赖处理顺序；回填历史事件应走显式重算。

### 7.2 归档的五个条件

一张卡要被自动归档，五个条件必须**全部**满足：

| # | 条件 | 不满足时的含义 |
|---|---|---|
| 1 | 自动归档开关打开 | 全局关掉了自动归档 |
| 2 | 状态是活跃 | 已归档的不重复归档 |
| 3 | 未被人工钉住 | **人工豁免优先级最高** |
| 4 | 类型不在永不归档清单里 | 类别豁免 |
| 5 | 强度**严格**低于 0.08，且没有未到期事项 | 还没到该忘的程度 |

**强度用「严格小于」而不是「小于等于」**：阈值本身的含义就是
「低于它才算忘掉」，等于阈值时还不算。

**「没有未到期事项」为什么是必要条件**：一条明天要提醒你的承诺，
哪怕强度已经掉到 0，也不能归档——归档意味着它从活跃视图里消失，
提醒就再也不会响了。**遗忘不能吃掉还没兑现的承诺。**

### 7.3 四类永不归档

| 类型 | 为什么永不归档 | 若不排除会怎样 |
|---|---|---|
| 感受 | 起源要求「细节会忘、只留感受」——感受是留下的那一层 | 系统把唯一该留下的东西也忘掉，只剩空白 |
| 承诺 | 未兑现的承诺忘掉 = 失信 | 提醒失效，用户以为系统记住了 |
| 概念 | 概念是长期知识，不是一次经历 | 反复重学同一件事 |
| 经验 | 经验是从多次经历里提炼的，本就稀缺 | 提炼的成果被当普通事件衰减掉 |

**这四类的共同点：它们的价值不随「最近是否被想起」下降。**
衰减假设「不用的记忆该淡」，而这四类恰恰是「不用也该在」的。
**把衰减假设套到不适用它的类别上，就是系统性地丢最重要的东西。**

### 7.4 单次归档比例上限：必须向下取整

```text
单次上限 = 向下取整( 向下取整(活跃卡总数) × 单次归档比例 )
单次归档比例 = 0.05
```

**为什么要向下取整**：向上取整会让「活跃卡 1 张、比例 5%」算出 1 张上限，
于是**唯一一张卡被归档，库空了**。向下取整保证「比例不到一张时，一张都不归档」。

【推导】由这个公式可以算出「少于多少张时永远不归档」：

```text
需要 向下取整(总数 × 0.05) ≥ 1
即 总数 × 0.05 ≥ 1
即 总数 ≥ 20

结论：活跃卡少于 20 张时，单次归档上限恒为 0，一张都不会归档。
```

**这不是失效，是刻意的设计。** 小库没有膨胀压力，不需要归档。
一个只有 12 张卡的库，靠 5% 的比例归档是「按比例削小库」，
小库也可能全是多年旧卡；「少于 20 张不自动归档」是保守策略，不能解释成这些卡都还年轻。

**这条性质容易被误读成「归档功能没生效」**：新建的库跑一夜整理，
归档 0 张，看起来像没工作。**其实它正确地工作了——只是这个库还不需要遗忘。**

### 7.5 归档决策流程

```text
        遍历活跃卡
             │
             ▼
    ┌──────────────────┐
    │ 被人工钉住？       │──是──→ 不归档（人工豁免最高）
    └────────┬─────────┘
             │否
             ▼
    ┌──────────────────┐
    │ 类型是永不归档四类？│──是──→ 不归档
    └────────┬─────────┘
             │否
             ▼
    ┌──────────────────┐
    │ 有未到期事项？     │──是──→ 不归档（还没兑现的承诺）
    └────────┬─────────┘
             │否
             ▼
    ┌──────────────────┐
    │ 强度 < 0.08？     │──否──→ 不归档（还不够弱）
    └────────┬─────────┘
             │是
             ▼
        进入候选池
             │
             ▼
    ┌────────────────────────────────┐
    │ 排序：强度↑ → 创建时间↑ → 标识↑│
    └───────────────┬────────────────┘
                    │
                    ▼
    ┌────────────────────────────────┐
    │ 截断到 向下取整(总数 × 0.05) 张│
    │ 上限为 0 时一张都不归档        │
    └───────────────┬────────────────┘
                    │
                    ▼
            置为归档状态
        （只改状态，不删数据，可随时恢复）
```

**排序键为什么是「强度升序 → 创建时间升序 → 标识升序」**：

- 强度升序：最弱的先归档，这是主判据。
- 创建时间升序：强度相同时先归档**更老的**。老的、弱的，才是该被忘掉的。
- 标识升序：兜底，保证结果与遍历顺序无关。

**第三键不是装饰**：批量导入的卡强度常常完全相同（同一批算出来的），
没有第三键时归档哪几张取决于遍历顺序，而遍历顺序在重放时可能不同。

### 7.6 归档是可逆的

归档只改状态，不删数据。被归档的卡：

- 不再进入召回候选池（活跃视图里看不到它）。
- 仍然在库里、仍然可查、仍然可以被显式恢复。
- 它的边仍在，图谱结构不变。

**「忘得掉」不等于「销毁」**。这是 FR-C2 的原文要求：
遗忘必须是可逆的。理由很实际：归档判据是「强度低」，
而强度是算出来的——算错了、参数配错了、用户改主意了，都必须能恢复。

**「可逆」是「敢自动归档」的前提。** 一个不可逆的自动删除机制，
没人敢打开它。

## 八、连边：只补不存在的边

### 8.1 四类边

| 关系 | 怎么来 | 有没有度数上限 |
|---|---|---|
| 同主题 | 推荐：相似度≥0.08的候选按权重及端点确定排序，双端均有额度才接边 | 每端最多3条，主题无向边≤⌊3n/2⌋ |
| 同实体 | 共享同一个实体 | 无（实体相同的全连） |
| 取代 | 新卡与旧卡冲突且更新 | 无 |
| 蒸馏 | 感受卡连回它的来源事件卡 | 无 |

既有主动提名再取对称并集的方案只保证主动提名≤3和总边≤3n，不能保证单点度≤3。
**【设计决策·待验证】推荐双端限度贪心**：每接一条边同时消耗两个端点的额度，
主题与实体投影各用每端3条额度，合并后每点至多6条；显式来源关系另计，不能混入该界。

**「同主题」的度数上限为什么必须存在**：主题相似度是一个稠密的量，
一批卡可能大量共享词项，但无交集时相似度为零。不限制连边预算的话，边数最坏随卡数平方增长，
图退化成全连接图——**等于没有图**。

【实测】主题相似度下限取 0.05 时平均度数 10.09，取 0.08 时 3.75。
平均度数不足以判断是否全连接，还须知道节点数与度分布。抽样读原文确认 0.08 附近
连出的边语义大多成立。

共享实体表示存在可查询的关联，不保证讨论同一事实，也不要求把桶内所有卡物化成完全图。
**【设计决策·待验证】保留完整的实体到卡映射，查询时按资格和相关性取有界邻居；**
实体桶可完整保存，而单次扩展与物化边另设预算。这样保留关联事实，且不为高频实体
支付平方级永久边存储；近似扩展漏召回的代价必须单独测量。

### 8.2 只补不存在的边

连边的动作是「补齐」，不是「重建」：

```text
对每条算出来的边：
    若这条边已经存在 → 跳过（不更新权重）
    若不存在        → 追加一条新建边的操作
```

**为什么不重建**：重建会把**已有的权重**冲掉。
边权是随时间演化的量（衰减、剪枝、强化），重建等于每晚把权重归零重算，
那些演化就全部失效了。

这条性质有一个重要推论：**「连边」这一步本身不改变任何已有边的权重。**
它是结构维护，不是强度维护。把两者混在一起，会让「今晚的图和昨晚的图
哪些不一样」变得无法解释。

### 8.3 边的身份与更新幂等分开

边身份由端点、关系及方向约定确定，权重变化仍是同一条边。
**边标识相同不意味着更新应被丢弃**；把边标识直接当更新操作的幂等键才会丢数据。

**【设计决策·待验证】每次状态变更有稳定的操作身份，并校验负载指纹。**
同一操作重试返回原结果；不同操作即使写同一边、甚至把权重改回以前的值，也要接受；
同一操作身份携带不同权重则报告冲突。边更新还需校验预期版本，避免覆盖并发强化。

剪枝也须留下有版本的抑制依据：如果仅删除边，下一夜的「只补不存在的边」
会把它按初始权重建回来。结构规则或有效来源变化后可以重新评估；
不能让相同证据在每夜重复复活被遗忘的关系。

## 九、时间：到期推进

### 9.1 为什么到期必须推进

一条每日提醒响过之后，必须把到期时刻推进到下一次。否则：

```text
第一天 09:00 提醒响过，到期时刻仍是 09:00
第二天 09:00，到期查询返回同一个到期时刻
        → 被「这条已经提醒过」的过滤掉
        → 第二天永远不响
        → 每日提醒在响过一次之后永久静默
```

**这是「到点无需用户输入自行接力」在重复场景下的真实形态**，
也是这条需求最容易被漏掉的一半：单次提醒很容易测对，
重复提醒的失败方式是**第二次之后全部静默**，而第一次是成功的。

### 9.2 五种重复方式

| 重复方式 | 推进规则 |
|---|---|
| 一次性（或缺省） | 响过即结束，没有下一次 |
| 每日 | 按本地自然日 + 1 天，保留原钟点 |
| 每周 | 按本地自然日 + 7 天，保留原钟点 |
| 定时表达式 | 重新解析表达式，从当前时刻起重新求下一次 |
| 表达式无法解析 | 没有下一次（不抛错） |

**为什么按本地自然日推进，而不是加固定的 24 小时毫秒数**：

夏令时切换日一天可能是 23 或 25 小时。加固定毫秒数会让
「每天早上九点」在切换后变成八点或十点，**且此后永久偏移**。
所以必须按「本地日期 + N 天 + 原钟点」重建时刻。

**为什么推进用循环而不是单次判断**：宿主可能停摆数天，
重新上线时到期时刻已经落后好几轮。单次判断只推进一天，
于是接下来几天会**连续补发**同一批提醒。循环一次跳到「严格晚于当前时刻」的下一次，
只提醒一次。

**循环必须有上限**（默认 400 轮）：防止时钟异常（例如当前时刻被设成 1970 年）时死循环。
超过上限返回「没有下一次」，当作放弃。

### 9.3 定时表达式（cron）四条语义

| 语义 | 规则 | 为什么容易错 |
|---|---|---|
| 日与周同时受限 | **或**关系（任一匹配即命中） | 与直觉相反：多数人以为是「与」 |
| 周字段的 0 与 7 | **都是周日** | 两个值同义，漏一个就少一天 |
| `a/n` 形式 | 从 a 起、到最大值、步长 n | 不是「每 n 个单位」 |
| 搜索窗口 | 366 天内找不到就返回「没有下一次」 | 不是抛错 |

**「日与周同时受限取或」是标准语义，但几乎所有人第一次都会写错。**
写成「与」的话，`0 9 1 * 1`（每月 1 号**且**周一）会变成一个几乎永不触发的表达式，
而它的本意是「每月 1 号**或**每周一」。

**为什么搜索窗口是 366 天**：最稀疏的合法表达式是「2 月 29 日」
（闰年才有），间隔最长 8 年。但 8 年的窗口会让一次解析耗时不可控。
366 天覆盖了绝大多数真实用法，超出的返回「没有下一次」——
**宁可承认解析不出来，也不要卡住。**

**窗口不够与参数错位是两件事**：曾经把「没说钟点时按几点算」
误当成「向后找多少天」传进来，于是 `0 9 29 2 *` 只找 9 天就放弃，
用户看到「解析不出来」，而真正的原因是搜索窗口被另一个参数顶掉了。
**参数含义错位不会报错，只会让功能在一个看似无关的场景里失效。**

### 9.4 到期推进决策流程

```text
        提醒已触发，需要推进到期时刻
                    │
                    ▼
        ┌───────────────────────┐
        │ 重复方式是一次性？      │──是──→ 没有下一次，结束
        └───────────┬───────────┘
                    │否
                    ▼
        ┌───────────────────────┐
        │ 重复方式是定时表达式？  │──是──→ 重新解析表达式
        └───────────┬───────────┘         │
                    │否                    ├─ 解析失败 → 没有下一次
                    ▼                      └─ 从「当前时刻」起在 366 天内
        ┌───────────────────────┐            求下一次命中
        │ 计算步长（每日 1 / 每周 7）│            ├─ 找到 → 推进到该时刻
        └───────────┬───────────┘            └─ 没找到 → 没有下一次
                    ▼
        ┌───────────────────────────────────┐
        │ 循环：本地日期 + 步长 + 原钟点    │
        │ 直到结果严格晚于当前时刻          │
        │ 超过 400 轮 → 放弃，返回没有下一次│
        └───────────────┬───────────────────┘
                        ▼
                  推进到新时刻
```

**「严格晚于当前时刻」是这条流程的核心**：等于当前时刻不算推进——
那会让「刚刚响过的这一秒」再次命中，形成同一秒内的重复提醒。

## 十、容量边界：活跃视图、持久数据和注入预算分别算账

### 10.1 四种边界不能互相代替

| 对象 | 真正的边界 | 不足以证明它的条件 |
|---|---|---|
| 单次注入 | 完整渲染后的实际词元预算与条数上限 | 库规模变小、字符数估算 |
| 单批整理 | 工作集、比较次数、边扩展与时间预算 | 只限制卡数 |
| 活跃视图 | 有界流入、有限有效寿命、公平处理、足够归档能力 | 只有衰减阈值 |
| 持久存储 | 日志轮转、检查点、保留期及明确的净化策略 | 归档，因为归档不删除记录 |

焦点包预算应当在库增长前就独立生效。活跃卡越多会增加搜索和维护代价，
但只要完整渲染后的词元预算正确执行，就不能直接推出注入长度随库无限增长。
连续 50 轮的长度波动是固定工作负载下的回归观察，也不能证明长期容量稳定。

### 10.2 什么时候可以推导活跃规模上界

**【推导】** 假定每天最多新增 Λ 张可归档卡，初始强度不超过 1，
有效半衰期有上界 H，阈值 θ∈(0,1)，且没有后续增强。
经过 L = H×log₂(1/θ) 天到达阈值，严格低于阈值还需要再经过正时间。
若公平调度保证到阈值后最多 D 天完成归档，则稳态可归档活跃规模
至多约为 Λ×(L+D+1)；「+1 天」覆盖按日离散调度。初始存量是过渡项。

这些前提任何一条失效，上界就不能引用：持续增强会重启寿命；改用无界访问加成
会取消 H；固定挑前 5000 张会取消 D；每天写入不限轮数会取消 Λ。
永不归档类别及人工钉住卡单独记为 P(t)，总活跃量为可归档活跃量加 P(t)。
若 P(t) 无上限，总量仍可无限增长。不能用事件卡的归档机制证明整个库有界。

### 10.3 处理能力与归档比例

设每夜最多处理 W 张，允许归档比例为 p，活跃量为 A，
则实际归档数不超过「工作集中已满足条件的张数、W、⌊pA⌋」三者最小值。
**这是能力上界，不是保证每夜会归档这么多。** 稳态至少要求长期平均归档流出
不小于进入可归档池的流入，并保证每张到期卡能被公平处理。若 Λ≥W，
单靠一夜一批不可能持续消化新增；应分批追赶、降低流入或明确容量失败。

5% 仍然是限制单批误操作范围的护栏，不是净化磁盘的机制。
少于 20 张时比例上限为零也是既有保守策略，应直接暴露「因比例下限未归档」。
**【设计决策·待验证】分别报告活跃量、豁免量、归档积压、最老未处理时长、
日志与检查点字节数，按各自容量目标告警，不再用一个「库有界」状态覆盖所有对象。**

## 十一、巩固层的诚实边界

### 11.1 已经成立的

| 性质 | 状态 | 靠什么保证 |
|---|---|---|
| 顺序约束被守住 | 成立 | 端到端用例覆盖「蒸馏在去重之前」；其余三条有结构保证 |
| 摘要同内容去重 | 既有材料声称成立 | 只证明同内容不多建卡；整批幂等、修订替换仍按本篇新增契约验收 |
| 长度预算 | 有条件成立 | 正比例、小来源跳过、整数上限；语义保真另验 |
| 配置层拒绝假压缩 | 成立 | 压缩比 ≥ 1、层级倒挂、下级数量 1 都在加载期失败 |
| 摘要不参与去重 | 成立 | 候选池显式排除，且有用例守住 |
| 归档可逆 | 成立 | 只改状态，恢复路径存在 |
| 四类永不归档 | 成立 | 判据在归档入口，且有类别用例 |
| 小库不归档 | 成立 | 向下取整，少于 20 张时上限恒为 0 |
| 到期推进不静默 | 成立 | 一次性 / 每日 / 每周 / 表达式各有推进用例 |

### 11.2 明确的边界

**边界一：感受蒸馏只度量强度，不度量极性。**

「开心」和「难过」得到同一个分数。产出的感受文本只能说
「这件事反复牵动我的情绪」，**绝不能说「让我开心」**。

有一条测试**故意断言这个局限存在**：极性相反、强度相同的两件事
会被蒸馏成同一条感受。将来若引入极性，它会变红，提醒同步更新文档。
**把局限写成断言，比写在注释里可靠。**

**边界二：蒸馏是规则版，不是真的在「理解」感受。**

它做的是「情绪词密度筛选 + 主题共现统计 + 模板拼接」。
它留下的是「哪些处境反复牵动过我」这一层，不是「我对它是什么感觉」。

**在任何文档与汇报里都该称它为「规则版感受蒸馏」，不该称它「理解了用户情绪」。**
规则版感受远好于没有感受，但美化它会让人误判系统能力。

**边界三：小库归档数恒为 0 是设计，不是失效。**

活跃卡少于 20 张时，任何一夜的归档数都是 0。
这条性质容易被误读成「归档没生效」，需要在使用说明里写明。

**边界四：连边不更新已有边的权重。**

这是「只补不存在的边」的直接后果，也是当前的设计选择。
它意味着边权在建成之后**只会被衰减和剪枝改变，不会被重新计算改变**。
一旦引入「强化」路径，必须分开边身份、操作身份和版本，不能靠把权重塞进边身份
来避免幂等冲突。剪枝后重建也须遵守抑制依据。

**边界五：单夜工作集之外（超过 5000 张）的卡完全不参与。**

它们不衰减、不归档、不进摘要。在超大规模库上，这意味着
「越老的卡越可能长期不被处理」——因为它们排在后面的工作集里。
本文没有规模分布证据，不能声称尚未触及。推荐的持久轮转与容量告警尚待验证；
单批上限只限制本批，不能证明所有卡最终都会处理。

**边界六：「重建索引」这一步不在纯函数编排里。**

报告只能观测它，不能把它换个名字打印。**如果报告里有一个
「重建索引数」的字段，必须确认它是索引真的重建后的观测值，
而不是活跃卡数换了个名字。** 后者在大多数夜里恰好相等，
所以它能长期骗过所有人。

### 11.3 三条可带走的判断

**判断一：批处理的顺序必须被当成约束，而不是风格。**

一处顺序错，某一步的产出恒为零；而它不报错、不崩溃、日志正常、
单测全绿——因为单测从不经过那一步。**只有端到端能守住顺序。**

**判断二：压缩必须由算术和配置共同保证，不能由自觉保证。**

「实现里记得按比例算」是自律；「配不出压缩比 ≥ 1」是边界。
**边界比自律硬，因为自律会被下一次重构改掉。**

**判断三：判据要读事实，不要读标签。**

「这张卡是不是蒸馏产物」是写入时确定的事实；
「这张卡的类型是不是感受」是分类器的输出，会被上游改动影响。
**用标签当判据，等于把两个模块耦合在一起，而上游一改下游就静默失效。**
