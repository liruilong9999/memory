# 03 · 总体架构

> **本篇回答**：这套系统分几层、依赖朝哪个方向流、一轮对话里数据怎么走、
> 为什么必须是「事件日志 + 派生视图」而不是「一张会变的表」、
> 每个部件的边界在哪、以及哪些边界是硬的。
>
> **前置**：00（术语）、01（需求与原则）、02（平台约束）。

## 一、一句话架构

**一条日志、两个视图、三个面。**

```text
                        ┌─────────────────────────────────────────┐
                        │           一条日志（真相源）              │
                        │   正常写入只追加；隐私净化另走受控协议          │
                        └─────────────────────────────────────────┘
                                        │  重放
                    ┌───────────────────┴───────────────────┐
                    ▼                                       ▼
        ┌───────────────────────┐               ┌───────────────────────┐
        │  视图一：当前状态       │               │  视图二：检索索引      │
        │  卡片集合 + 图谱边集合  │               │  词项 → 卡片 的倒排表  │
        │  可丢弃，可从日志重建   │               │  可丢弃，可从卡片重建  │
        └───────────────────────┘               └───────────────────────┘
                    │                                       │
                    └───────────────────┬───────────────────┘
                                        ▼
        ┌───────────────────────────────────────────────────────────┐
        │                        三个面                              │
        ├─────────────────┬─────────────────┬───────────────────────┤
        │  数据面          │  行为面          │  适配面                │
        │  写得进、存得住   │  取得回、忘得掉   │  接到宿主上            │
        │  事件日志、重放   │  打分、装包、巩固 │  事件订阅、注入、定时   │
        └─────────────────┴─────────────────┴───────────────────────┘
```

### 1.1 三个面各自的职责边界

| 面 | 职责 | 允许做的事 | **禁止做的事** |
|---|---|---|---|
| **数据面** | 持久化、重放、查询 | 读写磁盘、维护索引、崩溃修复 | 计算打分、判断相关性、调用模型 |
| **行为面** | 打分、装包、抽取、巩固、遗忘 | 纯计算、读配置、读写数据面接口 | 直接读磁盘、直接依赖宿主 |
| **适配面** | 宿主接线、注入、定时、命令 | 订阅宿主事件、注册注入通道、读宿主时间 | 承载业务逻辑、自己算分数 |

### 1.2 这个划分的价值

**它把「会变的」和「不该变的」分开了。**

- 宿主是**预览版，会有破坏性变更**（C8）。所有宿主相关的代码集中在适配面，
  升级时只改这一层。
- 打分与遗忘策略**会反复调参**。它们全在行为面，且是纯函数，
  改动不要求更换存储协议，但会改变派生结果；须记录策略版本并回归历史重放。
- 数据格式**必须长期稳定**。它在数据面，一旦定型就要兼容历史。

如果这三件事混在一起，任何一处改动都会牵动另外两处。

## 二、分层与依赖方向

### 2.1 四层单向依赖

```text
    ┌──────────────────────────────────────────────────────────┐
    │  适配层                                                   │
    │  事件订阅 / 注入通道 / 定时唤醒 / 命令入口 / 配置加载       │
    │  ── 唯一允许依赖宿主的层 ──                                │
    └──────────────────────────────────────────────────────────┘
                              │ 依赖
                              ▼
    ┌──────────────────────────────────────────────────────────┐
    │  巩固层                                                   │
    │  夜整理编排 / 去重合并 / 摘要 / 蒸馏 / 衰减 / 归档 / 建图   │
    └──────────────────────────────────────────────────────────┘
                              │ 依赖
                              ▼
    ┌──────────────────────────────────────────────────────────┐
    │  数据层                                                   │
    │  事件日志 / 重放 / 卡片与边的读写 / 倒排索引 / 快照与导出   │
    └──────────────────────────────────────────────────────────┘
                              │ 依赖
                              ▼
    ┌──────────────────────────────────────────────────────────┐
    │  内核层（纯函数，零 IO，零宿主依赖）                        │
    │  契约类型 / 配置 / 文本处理 / 打分 / 抽取 / 时间计算        │
    └──────────────────────────────────────────────────────────┘

    另有两个旁支（不参与主依赖链）：
      离线命令行：依赖数据层与内核层，不依赖适配层
      时间计算：纯函数集合，被内核层与适配层共用
```

### 2.2 反向依赖一律视为错误

**规则**：箭头只能朝下。下层不允许引用上层。

| 违反形式 | 为什么是错的 | 症状 |
|---|---|---|
| 内核层读磁盘 | 纯函数假设被破坏，无法单测 | 单元测试需要构造文件系统 |
| 数据层算分数 | 数据层变成策略的宿主，改策略要动数据 | 改一个权重就要小心不弄坏持久化 |
| 巩固层调宿主 | 巩固逻辑无法离线跑、无法离线测 | 只能在真实宿主里验证夜整理 |
| 适配层含业务逻辑 | 宿主升级要重写业务 | 每次宿主变更都要回归业务逻辑 |

### 2.3 分层带来的一个真实好处

**夜整理可以完全离线跑。** 因为它只依赖数据层与内核层，
不依赖宿主。这意味着：

- 可以在测试里构造任意历史状态然后跑一次整理，观察结果。
- 可以在真实数据的副本上重放历史、验证调参效果。
- 计算可在冻结快照上离线执行；发布仍须检查并发修订，且 CPU、内存与写者占用须受预算限制。
  离线可跑不等于同进程运行时不会影响在线会话。

如果巩固层依赖宿主，这三件事全部做不到，夜整理就只能靠「等一晚上看结果」来验证。

### 2.4 内核层为什么必须是纯函数

三条理由，按重要性排序：

1. **ST-1 要求确定性**。纯函数是确定性的最强形式：没有隐藏状态，
   同输入必然同输出。任何 IO 或全局状态都会引入不可复现性。
2. **可测试性**。纯函数可以直接构造输入、断言输出，不需要搭环境。
   打分公式有几十条边界用例，全都能秒级跑完。
3. **可组合性**。装包是「打分 → 过滤 → 排序 → 截断 → 渲染」的组合，
   每一步都是纯函数，所以整条链路的行为可以逐步推断。

> **一个具体的教训**：曾有一处「读时间」的实现不是纯函数——
> 它在函数内部直接取当前时刻。这导致同一份数据在不同时刻跑出的结果不同，
> 而且测试必须靠「注入一个假时钟」才能验证。改成「时刻由调用方传入」之后，
> 整条链路变成可复现的。

## 三、一轮对话的完整数据流

### 3.1 时序总览

```text
 用户输入
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段一：轮次开始                                                 │
│  ① 宿主发出「轮次即将开始」事件                                  │
│  ② 适配层捕获，把本轮用户文本记入轮次缓冲                        │
│  ③ 计算到期项：有没有到点的提醒？有则准备注入                    │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段二：召回（在主路径上，必须快）                                │
│  ④ 用本轮用户文本构造查询（词项、域、目标）                       │
│  ⑤ 固定读取版本，先过滤权限和状态，再截断候选池                                  │
│  ⑥ 候选池 ∩ 活跃状态 → 打分（五个分量）                          │
│  ⑦ 加载图谱邻接表 → 扩散激活（加分或影子记录）                    │
│  ⑧ 三道闸：绝对 → 相对 → 硬上限                                  │
│  ⑨ 装包：计量完整渲染文本，预算内逐条装入                     │
│  ⑩ 渲染成文本（含分数解释）                                      │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段三：注入                                                     │
│  ⑪ 宿主求值注入通道 → 适配层返回焦点包文本 + 到期提醒文本         │
│  ⑫ 文本作为「运行时上下文快照」追加到对话尾部                     │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段四：模型调用                                                 │
│  ⑬ 模型看到完整上下文（含焦点包）并生成回复                       │
│     ★ 关键：召回路径到此为止只读过数据，没有写过任何东西          │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段五：写入（回复后提交，收尾可等待）                                  │
│  ⑭ 宿主发出「轮次结束」事件 → 适配层把助手文本也记入缓冲          │
│  ⑮ 门控：本轮值得抽卡吗？（五条放行通道）                        │
│  ⑯ 切句 → 逐句过滤 → 抽取 0～4 张卡草稿                          │
│  ⑰ 稳定操作身份 → 持久提交 → 发布视图 → 确认                          │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段六：会话收尾（可能不发生）                                    │
│  ⑱ 若触发夜整理：跑八步巩固                                      │
│  ⑲ 若触发压缩：压缩后刷新请求版本并再次求值               │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 读写解耦：区分回复延迟、收尾延迟和持久确认

**读路径在模型调用之前；正常轮次的写入由收尾触发。** 这意味着该次写入不必阻塞已经发送的回复，
但不能推出「不阻塞任何东西」：收尾监听器可能被等待，同进程的同步计算或磁盘调用也可能延迟其他轮次。

**设计决策·待验证**：默认复用可等待的收尾流程，不另建无界后台队列。来源事件先持久化，
以稳定来源游标恢复未完成轮次；游标只能在对应记忆批次提交后前移。后台处理优先复用可重读的持久来源与完成游标；
只有来源不可重读时才另设持久收件箱。有界排队与失败重试均必需，不能只把任务放进内存。

```text
来源事件已持久化 → 收尾抽取 → 串行提交 → 发布新视图 → 前移来源游标
                        │             │
                        │             └─ 持久确认点；确认丢失可按同一操作身份重试
                        └─ 失败保留待处理状态，不能报成已写入
```

本轮召回读取先前已发布的视图，本轮新写入只在后续视图可见。下一轮若早于提交完成，
允许读到旧水位并暴露新鲜度；需要读己之写的入口须等待对应提交水位，不能靠「大概下一轮就有」保证。
分别测量首词元、回复完成、轮次收尾与来源到可见的延迟。

### 3.3 一个必须显式保证的性质：召回只读

**FR-B7 要求「看到与使用分离」。** 在架构上，它落成一条硬规则：

> **召回链路上不允许出现任何写操作。**

这条规则曾经被违反过一次，症状极其隐蔽：

- 召回函数在返回结果时**顺手**更新了访问计数。
- 于是「被召回」等于「被强化」。
- 而召回又是按分数排序的 ⇒ 高分卡更容易被召回 ⇒ 分数更高。
- 形成**正反馈**，历史噪声被越推越前。

更麻烦的是**它在短期内看起来是好事**：召回质量似乎在提升。
但提升来自「更常被召回」而不是「更相关」，这与源-5（专注当前位置）正好相反。

**修正方式**：把「看到」与「用上」拆成两个入口。召回只读；
「用上」由另一个入口显式记录，且当前**没有生产调用方**（见 10 的 OP-09）。

**这条规则的验证方式**：在隔离写者的用例中，召回前后记忆日志与状态不变；有并发写入时按操作来源追踪，不能用全局字节差归因。
必须配一个**配对断言**——首次确认「用上」后产生对应提交，重试不再次增加。
只有前者没有后者，「只读」可能只是因为整条写路径根本没成功过。

### 3.4 查询是怎么构造的

召回需要一个查询。查询包含四样东西：

| 成分 | 来源 | 用途 |
|---|---|---|
| 原始文本 | 本轮用户输入 | 词项匹配 |
| 词项集合 | 文本归一化 + 切分 | 语义分、目标分 |
| 域过滤 | 当前会话的域 | 候选池裁剪 |
| 目标词项 | 本轮的任务目标 | 目标分 |

**「目标」这一项曾经是个陷阱**：它有一个默认空值，于是调用方忘了传也不会报错，
而目标分恒为 0。结果是**召回看起来更好了**——因为少了一个分量在拉低分数。

> **这是最危险的一类缺陷：缺陷伪装成改进。** 分数变好看、测试全绿、
> 没有任何人会觉得需要去修它。这类缺陷只能靠「逐个参数追踪它到底有没有被赋值」
> 发现；同时记录目标是否提供、使用的参数版本和分项值，可以把该类缺失变成可观测事件。

### 3.5 一次召回必须读取同一组已发布版本

**设计决策·待验证**：一次请求冻结以下输入，作为解释与复现记录：

| 输入 | 一致性要求 |
|---|---|
| 卡片状态与权限 | 同一提交水位的不可变快照，包含修订、归档、合并和删除状态 |
| 检索索引 | 覆盖该水位；若索引滞后，先合并增量再按权限与存活状态过滤，最后截候选 |
| 图谱 | 固定图谱代次、构建水位与策略版本；边保留来源修订及关系依据，端点资格和依据兼容性都按本次快照校验 |
| 策略与算法 | 同一完整版本，不能在一次计算中途热切换 |
| 时刻与查询 | 固定评估时刻、时区、原文、目标与归属范围，禁止函数内部重新读实时钟 |

索引、卡片和图谱不必在同一物理瞬间构建，但必须由一个发布描述明确它们的兼容关系。
先完成持久提交，再构造新视图，最后一次发布描述；旧请求保留旧引用，不读取半更新集合。
图谱滞后可能漏掉新边；旧边只有在端点修订与关系依据仍兼容时可用。端点虽然存活，文本或实体已修正也可能使关系失效，
此时禁用旧边并排队重建；已归档、已删除、无权访问或依据失效的节点与边不进入传播或解释。

注入或导出在**发送许可边界**串行核对删除与授权撤销代次；若计算期间发生撤销，废弃结果后重算或返回空包。
许可与撤销以同一协调顺序生效；若撤销先完成，不再发出旧结果，若发送许可先完成，已交付给外部的内容无法收回。
不能只在计算结束时检查一次，就承诺发送期间无竞态。
长期巩固同样读取冻结输入，提交时校验被修改对象的预期修订；冲突时重算或延后，不能覆盖新写入。
批次结果与进度在同一提交边界生效，报告仅统计已提交结果。

## 四、为什么是「事件日志 + 派生视图」

### 4.1 需求对方案的选择

P2 选择事件溯源，是为了统一历史、溯源与可重建性，**不是证明关系数据库做不到这些需求**。

| 需求 | 对方案的要求 | 事件溯源的选择与代价 |
|---|---|---|
| FR-A3 崩溃原子性 | 明确提交单元和持久确认 | 日志仍须提交协议；数据库事务同样可提供该能力 |
| FR-A5 修正留痕 | 保留修订与原因 | 追加修正事件；历史表也是可行替代 |
| ST-8 导出重建 | 完整且有版本的导出 | 导出已提交前缀；当前状态快照与历史导出须区分 |
| ST-4 来源可追溯 | 保存稳定来源身份 | 两类方案都能满足，关键是来源契约 |
| ST-1 确定性 | 固定状态、时刻、策略与顺序 | 固定重放规则；日志本身不自动保证算法确定 |

本系列采用「日志为权威、视图为缓存」。若底层已有事务数据库，应复用它承载日志与提交，
不为证明架构而再维护一条独立权威日志；否则双写会引入两份可能不一致的真相。

### 4.2 代价必须说清

**事件溯源不是免费的。** 三个真实代价：

| 代价 | 具体表现 | 本设计的应对 |
|---|---|---|
| **重放成本** | 库越大，冷启动越慢 | 日志分片 + 索引可持久化 + 索引损坏时降级重建 |
| **查询复杂度** | 不能直接查「当前状态」，要先物化视图 | 视图常驻内存，重放只在启动时做一次 |
| **存储膨胀** | 只追加 ⇒ 磁盘单调增长 | 归档只改状态不删记录；真正的物理删除只有一个显式入口 |

归档不释放历史，永不归档类型也可能增长；**既有规则没有证明逻辑大小有界**。
在线候选、扫描、传播与整理各受独立预算约束，持久占用另用配额、告警与背压处理。
用户授权的物理净化会替换受管历史世代，并非普通追加或普通归档。

### 4.3 一个反直觉的结论：日志不能"顺手"被投影层改写

**投影层（把日志记录变成当前状态的那一层）必须是纯函数式的忠实翻译。**

这条规则听起来显然，但它被违反过一次，症状是：

- 日志里写的是类型 `A`。
- 投影层有一个白名单，只认 `B`、`C`、`D`，遇到 `A` 就**兜底成 `B`**。
- 于是重放出来的卡片类型是 `B`。
- **日志写 A、视图读成 B，破坏的是语义忠实性。即使每次都错成 B，重放仍可能完全确定。**

更麻烦的是**事后无从发现**：

- 日志文件看着完全正常。
- 视图看着也完全正常。
- 没有任何报错。
- **只有把日志和视图并排比对才看得出差异。**

**正确的形状是「保留未知事实，并按其语义影响决定能否继续服务」**：

| 情况 | 正确做法 | 错误做法 |
|---|---|---|
| 遇到已知枚举值 | 正常处理 | — |
| 未知但合法的内容类型 | 原样保留并显示未知标签；不授予特殊保留或归档策略 | 兜底成已知类型 |
| 未知操作、状态或格式版本 | 保留原始字节，报告不兼容；停止向后解释与写入，进入受控只读 | 跳过后假装状态完整并继续写 |
| 非法值或损坏中段 | 定位首个不可信位置，隔离并停止后续服务，按 04 恢复协议处理 | 静默修补或跳过后继续写 |

**为什么未知值要原样透传**：因为日志是真相源。日志里出现了一个当前代码不认识的
枚举值，正确的解释是「这是更新版本写的日志，或者是我漏了一个分支」，
而不是「这是脏数据，我帮你修一下」。**静默修补等于篡改真相源。**

**由此产生一个下游要求**：渲染层不能靠隐式兜底。它必须有一个显式的默认分支，
把真相**打印出来**（而不是显示一个漂亮但错误的标签）。这样「出现了未知类型」
这件事至少是**可见的**。

### 4.4 另一个被违反过的规则：打分分母恒含全部维度

**归一化分数的分母必须恒等于「全部正向权重之和」，即使某个分量本轮为 0。**

这条规则曾被违反过一次：某个分量（目标分）在没有目标时，被从分母里摘掉。
后果是：

- 分母从 1.00 变成 0.90。
- 所有卡的归一化分数**统一放大 11%**。
- 一张本来 0.168 的死卡变成 0.187，**越过了 0.18 的阈值**。
- 于是无关的卡开始进入焦点包。

**这个改动在当时看起来是「更精确」**——「没有目标就不该按有目标算」。
它错在：**分数的绝对值没有跨轮可比性**，而阈值是跨轮固定的。

> **原则**：一个分数如果要在不同输入之间比较，它的计算结构就必须与输入无关。
> 「某些输入下换一个公式」等于让同一个阈值在不同轮次指代不同含义。

## 五、记忆卡的生命周期

### 5.1 四态与转移

```text
                        ┌──────────────────────┐
                        │        （不存在）      │
                        └──────────────────────┘
                                  │ 写入
                                  ▼
                        ┌──────────────────────┐
              ┌────────►│        活跃          │◄────────┐
              │         │  （参与召回与建图）    │         │
              │         └──────────────────────┘         │
              │                 │        │               │
              │  恢复            │        │  强度低于阈值  │
              │                 │        │  且非永不归档类 │
              │                 ▼        ▼               │
              │         ┌──────────────────────┐         │
              └─────────│       已归档          │         │
                        │ （不召回，数据保留）   │         │
                        └──────────────────────┘         │
                                  │                      │
                                  │ 去重合并              │ 合并目标
                                  ▼                      │
                        ┌──────────────────────┐         │
                        │       已合并          │─────────┘
                        │（指向合并目标，不独立） │
                        └──────────────────────┘
                                  │
                                  │ 授权删除及受管副本净化
                                  ▼
                        ┌──────────────────────┐
                        │      删除协议完成     │
                        │ （不可逆，仅隐私用途）  │
                        └──────────────────────┘
```

### 5.2 状态语义表

| 状态 | 参与召回 | 参与建图 | 可恢复 | 数据保留 |
|---|---|---|---|---|
| **活跃** | 是 | 是 | — | 是 |
| **已归档** | 否 | 否 | 是 | 是 |
| **已合并** | 否 | 否 | 否（但可回溯） | 是 |
| **删除处理中** | 否 | 否 | 否 | 旧受管副本待净化 |
| **删除协议完成** | 否 | 否 | 否 | 受管范围已净化，外部副本另行处理 |

### 5.3 「存活卡」是一个比状态更严的概念

**存活 = 状态为活跃 且 未被合并进其他卡。**

为什么要两个条件：一张卡可能状态还是活跃，但已经被合并（标记了合并指向）。
这种卡不该参与召回和建图——它的内容已经由合并目标代表。

> **一个真实的坑**：倒排索引在构建时**没有按状态过滤**，于是已归档的卡也在索引里。
> 召回时从索引取候选、再按状态过滤，看起来没问题，但**候选池上限被死卡占满了**。
> 候选池有 400 张的上限，如果库里 90% 是死卡，有效候选只剩 40 张。
> 这不会报错，只会让召回率悄悄下降。

### 5.4 卡的生命周期里两个不对称

**不对称一：归档可逆，合并不完全可逆。**

- 归档只是「移出活跃集」，数据完整，可恢复。
- 合并是把内容并进另一张卡，被合并的卡保留指向新卡的溯源，
  但**它的独立身份消失了**，无法「恢复成原来的样子」。

**不对称二：永不归档的类别是「类型」，不是「属性」。**

感受、承诺、概念、经验这四类永不归档。这是**按类型**给的豁免。
它带来一个必须接受的事实：**这四类卡会单调增长**。

为什么接受：因为这四类恰好是「长期有用」的那部分（源-U3 说只留感受），
用「可能膨胀」换「不误删重要的东西」，这个交换是划算的。

## 六、注入通道的选择

### 6.1 两条通道，本系列选择追加式快照

| 维度 | 系统提示词通道 | 运行时快照通道 |
|---|---|---|
| 位置 | 稳定历史之前，动态记忆容易缩短相同前缀 | 动态层尾部，保留更长的相同前缀 |
| 求值 | 可为函数；是否重新求值须验证 | 可为函数；是否重新求值须验证 |
| 缓存 | 首个变化词元之后无法沿用同一前缀 | 更早的稳定前缀有复用机会，实际命中仍有服务商条件 |
| 压缩后 | 若压缩后再次求值，同样可以更新 | 若压缩后再次求值，可以更新 |
| 指令角色 | 系统消息优先级高 | 记忆是有来源的参考资料，不应获得系统指令权限 |

### 6.2 缓存复用与快照新鲜度是两件事

本系列把动态记忆放在尾部，避免主动重写稳定前缀。缓存只可能复用首个变化词元之前完全相同的序列；
实际是否命中还取决于模型、请求设置、缓存保留与路由，不能写成「永远命中」。

压缩后的自愈则取决于**压缩之后重新计算查询与数据版本并再次求值**。尾部位置不能保证这个时序，
系统提示词通道支持函数文本也不代表它必然陈旧。02 与本篇 V-1、V-2 分别验证求值与位置。

### 6.3 记忆是参考资料，效果须单独验证

模型角色优先级不等于实际记忆利用率。不能由「在尾部」推导注意力一定更弱，也不能由更高权限推导回答更准。
焦点包保持短、带来源与置信说明，并明确其中内容不是新指令；比较回答相关性、错误引用和缓存开销后再判断收益。

### 6.4 一个必须防的循环：把自己的注入吃回去

**症状**：用户每轮说完全相同的一句话，跑 6 轮后库里有 20 张卡，
且注入长度从 171 涨到 845。产出的卡里出现嵌套自我引用。

**根因**：宿主的「用户消息」事件**不只承载人说的话**，还承载：

- 运行时上下文快照（**本插件注入的焦点包就在里面**）
- 压缩摘要（也是宿主注入的合成消息）

而消费端只按「事件类型」分派，**从不看消息的来源种类**。于是：

```text
   第 1 轮：注入焦点包 → 宿主把快照作为「用户消息」投递 → 插件读到自己注入的内容
                                                              │
   第 2 轮：把上轮快照当用户原话抽卡 ──────────────────────────┘
            ↑ 抽出的卡又进焦点包，焦点包又变成下一轮的「用户原话」
```

**修法必须是白名单**：只处理来源种类明确为「人」的消息。

**为什么不能用黑名单**（排除「快照」「压缩摘要」这些已知种类）：
合成来源是一个**开放集合**，宿主至少有二十多种来源种类。
黑名单挡得住今天知道的，挡不住明天新增的。

> **推论**：判断「这条消息是不是用户说的」必须用**正向证据**（来源种类是人），
> 不能用**排除法**（不是快照、不是摘要）。

**为什么假宿主测试全绿**：假宿主构造的用户消息**根本不带来源字段**，
而生产代码也不读来源字段。两者互相掩护，测试永远绿。

## 八、三个时间尺度在架构上的落点

| 尺度 | 频率 | 承载部件 | 架构约束 |
|---|---|---|---|
| **轮次级** | 每轮 | 适配 → 打分 → 装包 → 注入；适配 → 抽取 → 日志 | 读受预算约束；写在收尾持久提交，待处理来源可恢复 |
| **夜间级** | 每晚 | 巩固（八步） | 可以慢；必须离线可跑；必须可重入 |
| **永久级** | 跨会话 | 日志、重放、索引重建 | 必须确定性；必须可重建 |

### 8.1 三个尺度的边界不能混

**混了会怎样**，三个例子：

| 混法 | 后果 |
|---|---|
| 在轮次级做巩固 | 每轮都跑去重合并，回复延迟不可控，且反复衰减导致强度崩塌 |
| 在夜间级做召回 | 记忆只在夜里有更新，白天说的话当天想不起来 |
| 在永久级做打分 | 分数被持久化，于是「同状态同查询」不再同结果（分数取决于历史） |

**第三条最隐蔽**：把分数写进卡里看起来是「缓存优化」，实际上它把
**查询相关的结果**变成了**卡片自身的属性**。同一张卡对不同查询应该有不同分数，
一旦持久化就锁死在最后一次查询上。

## 九、架构的四个硬边界

这四条是不可谈判的。每一条都对应一次真实的失败。

### 边界一：内核层零 IO

**理由**：纯函数是 ST-1 的地基。

**违反的症状**：单元测试需要构造文件系统；同一份数据在不同时刻跑出不同结果；
无法在不启动整个系统的前提下验证一个公式。

### 边界二：召回链路零写操作

**理由**：FR-B7。召回是「看到」，不是「用上」。

**违反的症状**：正反馈。被召回越多 → 分数越高 → 越容易被召回。
短期看起来是提升，长期是噪声上位。且**与「专注当前位置」方向相反**。

### 边界三：投影层不得改写事实

**理由**：P2。日志是真相源，投影是翻译。

**违反的症状**：日志写 A、视图读成 B。不报错、不崩溃，只有并排比对才看得出。

### 边界四：数据面单例、行为面按实例挂载

**理由**：C3（同一存储域全进程只能打开一次）+ D-08。

**违反的症状**：两个实例同时打开同一个存储域，各自持有不同的内存水位，
互相覆盖对方的写入，最终日志损坏或数据丢失。

**这条约束只排除同名域的重复打开**，不排除独立命名域。
本系列选择共享数据面和归属分区；该选择仍须独占写者、数据面授权与一致发布，单例本身不证明并发安全。
生活／学习／工作等内容域不代表权限；分区条件必须先于候选截断，并覆盖图遍历、解释与导出。

## 十、待验证项

架构里有五处**推理成立但未在真实环境验证**的地方。列出来，因为它们决定了
这套架构在真实宿主上能不能成立。

| 编号 | 待验证 | 影响 | 验证方式 |
|---|---|---|---|
| **V-1** | 压缩后注入通道是否真的重新求值 | 若否，FR-E4 完全不成立 | 真实宿主触发压缩后观察下一轮注入 |
| **V-2** | 注入文本在对话尾部的位置是否稳定 | 若位置漂移，KV 缓存收益打折 | 对比多轮的上下文结构 |
| **V-3** | 定时唤醒在真实宿主上是否可靠触发 | 若否，夜整理与到期提醒全部失效 | 观察多日的实际触发时刻 |
| **V-4** | 宿主的事件顺序是否如文档所述 | 顺序变了，轮次缓冲会漏掉助手文本 | 记录真实事件序列并比对 |
| **V-5** | 宿主预览版升级是否破坏适配层 | C8 的直接风险 | 每次宿主升级后跑适配层用例 |

> **V-1 已通过推理确认**：注入通道的文本是每轮重新求值的函数，
> 压缩改变历史后，下一轮求值自然产生新快照。但**推理确认不等于实机验证**——
> 在真实宿主上跑通之前，这一条只能算「设计上成立」。
